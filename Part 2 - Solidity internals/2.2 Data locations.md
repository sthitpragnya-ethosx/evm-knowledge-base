# 2.2 Data locations

> [!abstract] In one minute
> - Solidity data lives in five places: **storage** (persistent, per contract), **transient** storage (wiped at the end of the transaction), **memory** (per call frame, scratch), **calldata** (the call's read-only input) and the **stack** (value types and pointers). Reference types (arrays, `bytes`, `string`, structs, mappings) must say which one they use.
> - **Copy or alias:** storage ↔ memory, calldata → anywhere, and anything → a state variable **copy**. Memory → memory and storage → a local `storage` variable only **alias**. Value types always copy.
> - A local `S storage p` is just a slot number on the stack. A local `S memory m` is just a memory offset on the stack. Both are cheap to make. What costs gas is **copying** into them: `S memory m = s` reads every slot of `s` (a 5-slot struct cost 10,821 gas cold vs 2,323 through a storage pointer, measured).
> - `calldata` is read-only and is never copied unless you ask, so it is the cheapest parameter location for external functions. Only dynamic calldata arrays support slices `x[a:b]`. Memory arrays have a fixed length once allocated: no `push`, no `pop`.
> - Storage pointers can dangle. `Item storage it = items[i]; items.pop();` leaves `it` pointing past the array's end. Writes through it land in "dead" slots that a later `items.push()` brings back to life.
> - `delete` assigns the type's zero value. It skips mappings, so deleting a struct that contains a mapping leaves every mapping entry in place, with no warning from solc 0.8.38. `transient` state variables (0.8.28+) are value types only, with no initializer and no `constant`/`immutable`.

**Prerequisites:** [[1.4 Memory]], [[1.5 Storage and transient storage]], [[1.6 Calldata, returndata and logs]], [[2.1 Types]] · **Leads to:** [[2.3 Storage layout]], [[2.4 Memory layout]], [[2.5 ABI encoding and decoding]], [[3.5 Memory management in assembly]]

> [!note] How this note was verified
> Every snippet compiles with solc-js 0.8.38 (default `evmVersion` `osaka`, optimizer on, 200 runs). Behavior was checked by running the runtime bytecode in py-evm 0.12.1b1 (Prague rules), on both the legacy pipeline and `--via-ir`. Unless stated otherwise, both pipelines gave the same result. Gas numbers are execution gas (the message's gas, without the 21,000 base cost and calldata cost). The opcodes involved cost the same under Osaka.

## Five places data can live

Part 1 described the raw EVM areas: storage and transient storage ([[1.5 Storage and transient storage]]), memory ([[1.4 Memory]]), calldata ([[1.6 Calldata, returndata and logs]]) and the stack ([[1.3 Execution model]]). Solidity maps its variables onto exactly those areas. A **data location** is the Solidity-level label that says which area a variable's bytes live in.

Start with the intuition. Think of a contract call as a worker at a desk:

- **Storage** is the filing cabinet. It survives after the worker goes home. Opening a drawer is slow (2,100 gas cold).
- **Transient storage** is a whiteboard in the office. Every worker in the same transaction can read it. It is wiped clean when the transaction ends.
- **Memory** is the worker's notepad. It is thrown away when this call returns. It is cheap, but the more pages you use, the faster the price grows.
- **Calldata** is the sealed letter that started the job. You can read it as often as you like. You cannot write on it.
- **The stack** is the worker's hands. It holds a few small things at a time: numbers, addresses, and pointers into the other areas.

| Location | Lifetime | Scope | Writable | Read / write opcodes | Typical cost |
|---|---|---|---|---|---|
| `storage` | Forever (until overwritten) | The contract (its storage context) | Yes | `SLOAD` / `SSTORE` | 2,100 cold / 100 warm read; 2,900–22,100 write |
| `transient` | Until the end of the transaction | The contract, across all frames of the transaction | Yes (not under `STATICCALL`) | `TLOAD` / `TSTORE` | 100 each |
| `memory` | Until the current call frame returns | One call frame | Yes | `MLOAD` / `MSTORE` / `MCOPY` | 3 per word + quadratic expansion |
| `calldata` | Until the current call frame returns | One call frame | **No** | `CALLDATALOAD` / `CALLDATACOPY` | 3 per word read |
| stack | Until the variable goes out of scope | One function body | Yes | `DUPn` / `SWAPn` / `POP` | 3 or less |

Two facts follow:

1. **Only reference types carry a location.** Value types (`uint`, `address`, `bool`, `bytesN`, enums, user-defined value types, function types) are just words. As local variables they live on the stack. Writing `uint256 storage x` is a compile error: *"Data location can only be specified for array, struct or mapping types, but "storage" was given."*
2. **A reference-type local is a pointer.** The variable itself sits on the stack. It holds either a slot number (storage), a memory offset (memory), or a calldata offset and length (calldata). The data it points to lives in the named area.

The second fact is the key to everything else in this note. I checked it with inline assembly: a fresh `Item memory m = Item(1, 2)` gave `m == 0x80` (the first free memory offset) and the free memory pointer moved to `0xc0`. A `Item storage it = items[0]` gave `it.slot == 0x290decd9548b62a8d60345a988386fc84ba6bc95484008f6362f93160ef3e563`, which is `keccak256(abi.encode(0))`, the first data slot of a dynamic array at slot 0 ([[2.3 Storage layout]]).

### Where each location is allowed

| Declaration | `storage` | `memory` | `calldata` | `transient` |
|---|---|---|---|---|
| State variable | default (implicit) | no | no | value types only (0.8.28+) |
| Parameter of `external` function | **error** | yes | yes | no (parser error) |
| Parameter of `public` function | no | yes | yes | no |
| Parameter of `internal` / `private` function, library function | yes | yes | yes | no |
| Return value of `public` / `external` function | **error** | yes | yes | no |
| Return value of `internal` / `private` function | yes | yes | yes | no |
| Local variable | yes (must be assigned) | yes | yes (must be assigned) | no (parser error) |

The compiler messages, from solc 0.8.38:

```text
interface I { function f(uint256[] storage x) external; }
TypeError: Data location must be "memory" or "calldata" for parameter in external function, but "storage" was given.

function f() public view returns (uint256[] storage) { return a; }
TypeError: Data location must be "memory" or "calldata" for return parameter in function, but "storage" was given.

function f() external pure { uint256 transient x; }
ParserError: Expected ';' but got identifier
```

`calldata` has been allowed for every variable, including internal function parameters and locals, since 0.6.9 (4 Jun 2020). Since 0.5.0 an explicit location is mandatory for every struct, array and mapping variable, and uninitialized storage variables are an error.

> [!note] A `public` function with a `calldata` parameter can only be called internally with calldata
> If `g(uint256[] calldata x)` is `public`, calling `g(m)` from inside the contract with a memory array fails: *"Invalid implicit conversion from uint256[] memory to uint256[] calldata requested."* Use `memory` if internal callers need to pass memory, or split the function into an `external` wrapper and an `internal` worker.

## Assignment semantics: copy or alias

The rule fits in four lines. These are the official docs' words, and I confirmed each one by running a test contract.

1. Assignments between `storage` and `memory`, in either direction, and any assignment **from** `calldata`, create an **independent copy**.
2. Assignments from `memory` to `memory` create a **reference** (alias).
3. Assigning a storage value to a **local** `storage` variable creates a **reference** (a storage pointer).
4. Every other assignment **to** storage (for example to a state variable) **copies**.

Value types are always copied, whatever the location.

| # | Code | Kind | Result after mutating the target (`.a = 99`) | Measured return |
|---|---|---|---|---|
| 1 | `S memory m = s;` (storage → memory) | copy | `s.a` unchanged | `(m.a, s.a) = (99, 1)` |
| 2 | `S memory m2 = m1;` (memory → memory) | alias | both see 99 | `(m1.a, m2.a) = (99, 99)` |
| 3 | `S storage p = s;` (storage → local storage) | alias | `s.a` becomes 99 | `s.a = 99` |
| 4 | `s = m;` (memory → state variable) | copy | `s.a` unchanged | `(s.a, m.a) = (1, 99)` |
| 5 | `t = s;` (state variable → state variable) | copy | `s.a` unchanged | `(s.a, t.a) = (1, 99)` |
| 6 | `uint256[] memory m = c;` (calldata → memory) | copy | calldata unchanged (it cannot change) | `(c[0], m[0]) = (5, 99)` |
| 7 | `S memory e = xs[0];` (memory array element → memory) | alias | `xs[0].a` becomes 7 | `7` |
| 8 | `S storage p = s; p = t;` (re-point) | alias | `t` changes, `s` does not | `(s.a, t.a) = (1, 99)` |
| 9 | `S memory m2 = m1; delete m2;` | rebinds `m2` | `m1` untouched | `(m1.a, m2.a) = (1, 0)` |

The test contract (abridged; all ten functions are in the verification files):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract Alias {
    struct S { uint256 a; uint256 b; }
    S public s;
    S public t;

    function storageToMemory() external returns (uint256 memA, uint256 storA) {
        s.a = 1;
        S memory m = s;     // copy: two SLOADs, two MSTOREs
        m.a = 99;
        return (m.a, s.a);  // (99, 1)
    }

    function memoryToMemory() external pure returns (uint256 m1a, uint256 m2a) {
        S memory m1 = S(1, 2);
        S memory m2 = m1;   // alias: copies one stack word (the offset)
        m2.a = 99;
        return (m1.a, m2.a); // (99, 99)
    }

    function storageToPointer() external returns (uint256 storA) {
        s.a = 1;
        S storage p = s;    // alias: p is the slot number of s
        p.a = 99;
        return s.a;         // 99
    }

    function memoryToStorage() external returns (uint256 storA, uint256 memA) {
        S memory m = S(1, 2);
        s = m;              // copy: two SSTOREs
        m.a = 99;
        return (s.a, m.a);  // (1, 99)
    }

    function calldataToMemory(uint256[] calldata c) external pure returns (uint256 c0, uint256 m0) {
        uint256[] memory m = c; // copy out of calldata
        m[0] = 99;
        return (c[0], m[0]);    // (5, 99) when called with [5]
    }
}
```

Why the asymmetry? Because a pointer can only point within one area. A stack word that holds `0x80` means "memory offset 0x80". It cannot also mean "storage slot 0x80". So any assignment that crosses areas must move the bytes. Assignments that stay inside memory, or that bind a local storage name to an existing slot, can just copy the pointer.

### Some assignments are simply not allowed

| Code | solc 0.8.38 error |
|---|---|
| `S storage p = m;` with `m` in memory | `Type struct C.S memory is not implicitly convertible to expected type struct C.S storage pointer.` |
| `uint256[] storage p = s; p = c;` with `c` in calldata | `Type uint256[] calldata is not implicitly convertible to expected type uint256[] storage pointer.` |
| `c[0] = 1;` with `c` in calldata | `Calldata arrays are read-only.` |
| `t = s;` where `S` contains a mapping | `Types in storage containing (nested) mappings cannot be assigned to.` |
| `S memory x;` where `S` contains a mapping | `Type struct C.S memory is only valid in storage because it contains a (nested) mapping.` |
| `s.push(S(1));` where `S` contains a mapping | `Struct containing a (nested) mapping cannot be constructed.` |
| `uint256[] memory a = s3;` with `s3` a `uint256[3] memory` | `Type uint256[3] memory is not implicitly convertible to expected type uint256[] memory.` |

A local storage pointer can only be bound to something that already lives in storage. There is no "make a new storage object" expression: storage is allocated by the layout at compile time ([[2.3 Storage layout]]), not at runtime.

Mappings cannot be copied at all, because a mapping has no list of keys. The compiler would not know which slots to read. That is also why a mapping cannot exist in memory.

Deep copies are deep. Copying a storage struct with a `uint256[]` member to memory reads the array's length slot and every element slot. Copying a memory `uint256[][]` to storage writes every inner array. Both are supported in 0.8.38 (including calldata struct → storage, supported since 0.7.1), and both cost gas in proportion to the total data size.

## Storage pointers as local variables

A local `storage` variable is the most useful and the most dangerous tool in this note.

**What it compiles to.** The pointer is a single stack word: the slot where the value starts. For `items[i]`, the compiler computes `keccak256(p) + i * slotsPerItem` once, after the bounds check. Every later `it.field` adds a constant offset and does one `SLOAD` or `SSTORE`. That is why taking a pointer once and reading two fields is cheaper than writing `items[i].a` and `items[i].b`, which may redo the hash and the bounds check unless the optimizer manages to merge them. A named pointer makes the saving explicit instead of hoping for it.

**It must be assigned before use.** Both of these are compile errors in 0.8.38:

```text
function f() external { uint256[] storage r; r.push(1); }
TypeError: This variable is of storage pointer type and can be accessed without prior assignment, which would lead to undefined behaviour.

function f() internal view returns (uint256[] storage r) { if (a.length > 0) r = a; }
TypeError: This variable is of storage pointer type and can be returned without prior assignment, which would lead to undefined behaviour.
```

Before 0.5.0, an unassigned local struct defaulted to storage and pointed at **slot 0**. Writing to it overwrote the first state variable, often the owner. That bug class was a well-known honeypot trick. The compiler now rejects it, but the same idea comes back in hand-written assembly that sets `p.slot` from untrusted input.

**Re-pointing does not copy.** Assigning one storage pointer to another (`p = t;`) only changes which slot `p` names. Neither `s` nor `t` changes until you write through `p` (row 8 of the table).

**`delete p` is not allowed** on a local storage pointer: *"Built-in unary operator delete cannot be applied to type struct C.S storage pointer."* `delete` means "assign the zero value", and there is no zero storage object to point at. Delete the thing it points to instead: `delete items[i]`.

### Returning storage references from internal functions

Internal and private functions may take and return `storage` references. This is how libraries operate on state: OpenZeppelin's `EnumerableSet.add(AddressSet storage set, address value)` receives a storage pointer and edits the caller's set in place. It is also how you centralize a lookup with its checks:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract Registry {
    struct Item { uint256 id; uint256 amount; }
    Item[] internal items;

    error UnknownItem(uint256 index);

    // Returns a pointer, not a copy. Callers write straight to storage.
    function _item(uint256 i) internal view returns (Item storage it) {
        if (i >= items.length) revert UnknownItem(i);
        it = items[i];
    }

    function addAndBump() external returns (uint256 amount) {
        items.push(Item(1, 10));
        Item storage it = _item(0);
        it.amount += 5;           // SSTORE into items[0].amount
        return items[0].amount;   // 15
    }
}
```

Running a version of this in py-evm returned `15`, and `it.slot` was the array's first data slot. The function is `view` even though callers write through its result. Mutability is checked at the place of the write, not where the pointer was made.

Three rules for functions that return storage references:

- They can only be `internal` or `private`. A `public` or `external` function cannot return a storage reference (the error above), because the ABI has no way to encode "a slot in my storage".
- Every path must assign the return variable, or revert. The compiler enforces this.
- The pointer is only as valid as the structure it points into. If the caller then shrinks the array, the pointer dangles (see [[#Pitfalls and incidents]]).

The modern form of this pattern is the namespaced storage getter used by upgradeable contracts: `function _getMainStorage() private pure returns (MainStorage storage $) { assembly { $.slot := LOCATION } }`. That is ERC-7201, covered in [[2.3 Storage layout]] and [[4.2 Upgradeability and proxies]].

## Calldata: read-only and copy-free

A `calldata` variable is a pointer into the call's input bytes. For a dynamic array it is two stack words: the offset of the first element and the length. Nothing is copied when the function starts. Each `xs[i]` is a bounds check and one `CALLDATALOAD`. Calldata cannot be written by any opcode, so Solidity forbids assignment to its elements (*"Calldata arrays are read-only."*).

Since 0.6.9 calldata works everywhere, not just in external parameters. Internal functions can take and return calldata pointers, which lets you pass large inputs through helper functions without ever copying them:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract CalldataHelpers {
    function _tail(uint256[] calldata xs) internal pure returns (uint256[] calldata) {
        return xs[1:];  // still calldata: no copy
    }

    function tailLength(uint256[] calldata xs) external pure returns (uint256) {
        return _tail(xs).length;
    }
}
```

A local calldata variable must be assigned before use, just like a storage pointer: *"This variable is of calldata pointer type and can be accessed without prior assignment, which would lead to undefined behaviour."*

### Calldata slices `x[a:b]`

Slices (index range access) give a view of part of a calldata array: elements `a` up to but not including `b`. Either bound may be left out: `x[4:]`, `x[:4]`. A slice is still in calldata, so it costs nothing to create.

Verified behavior in 0.8.38:

| Expression (with `xs = [10, 20, 30, 40]`) | Result |
|---|---|
| `xs[1:3]` | length 2, first element 20 |
| `xs[2:2]` | length 0 (empty slice is fine) |
| `xs[3:2]` (start > end) | revert, **empty** revert data (not a Panic) |
| `xs[1:5]` (end > length) | revert, **empty** revert data |

Restrictions, each a compile error:

| Code | Error |
|---|---|
| `m[1:2]` with `m` in memory | `Index range access is only supported for dynamic calldata arrays.` |
| `x[1:]` with `x` a `uint256[3] calldata` | same message: static arrays cannot be sliced |
| `x[1:]` with `x` a `bytes[] calldata` or `uint256[][] calldata` | `Index range access is not supported for arrays with dynamically encoded base types.` |

`bytes calldata` and `string calldata` can be sliced. The classic use is splitting a selector from its arguments without copying:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract Router {
    function head(bytes calldata data) external pure returns (bytes4 sel, uint256 x) {
        sel = bytes4(data[:4]);                    // first four bytes
        x = abi.decode(data[4:], (uint256));       // decode straight from calldata
    }
}
```

Called with `0xa9059cbb` followed by the word `42`, it returned `sel = 0xa9059cbb`, `x = 42`. A slice converts to `memory` or `storage` by copying (`bytes memory m = b[1:];` compiles), since 0.7.6.

## Memory: scratch space with fixed-length arrays

A `memory` variable points into the call's memory. Solidity allocates memory by bumping the **free memory pointer** at `0x40` and never frees it ([[1.4 Memory]]). The exact byte layout of arrays, `bytes` and structs in memory is [[2.4 Memory layout]]. Here, three rules matter.

**Allocation fixes the length.** `new uint256[](n)` reserves `32 + 32·n` bytes and writes `n` into the first word. The next allocation goes right after it. There is no room to grow, so Solidity offers no growth operations on memory arrays:

```text
uint256[] memory a = new uint256[](2); a.push(1);
TypeError: Member "push" is not available in uint256[] memory outside of storage.

a.length = 5;
TypeError: Member "length" is read-only and cannot be used to resize arrays.
```

The length `n` may be a runtime value. Only storage dynamic arrays can change length (`push`, `pop`).

**Memory → memory is aliasing.** Passing a memory array to an internal function passes the pointer. The callee can modify the caller's array. This surprises people coming from languages with value structs. If you need an independent copy, copy explicitly (for `bytes`, `bytes.concat(b)` or `abi.encodePacked(b)` returns a fresh copy; for other arrays, loop or use `mcopy` in assembly).

**Memory is fresh per call, but not per allocation.** Memory starts at zero in each new frame. Within one frame, memory above the free memory pointer may be dirty from scratch use. Solidity zeroes what it allocates for `new`, but your own assembly must not assume fresh memory is clean ([[3.5 Memory management in assembly]]).

## The stack: value types and pointers

Value-type locals, function parameters and return values live on the stack, and so do the pointers for every reference-type local. The stack is the fastest location (3 gas or less per access). Its limit is reach, not size: only the top 16 items can be touched with `DUP` and `SWAP`. Too many live locals, parameters and return values gives the famous "Stack too deep" error. The causes and fixes are in [[1.3 Execution model]], and how the via-IR pipeline moves variables to memory to escape the limit is in [[3.11 Compiler IR and the optimizer]].

One stack fact matters for data locations: a `bytes calldata` or `uint256[] calldata` local takes **two** stack slots (offset and length), while a memory or storage pointer takes one. Heavy calldata-slice code hits "stack too deep" sooner.

## Transient: the fifth location

Since **0.8.28** (9 Oct 2024), a state variable can be declared `transient`. It then lives in transient storage (`TLOAD`/`TSTORE`, EIP-1153) instead of storage. It reads and writes like a normal state variable, but the value is gone at the end of the transaction. The opcode-level semantics are in [[1.5 Storage and transient storage]]. This section covers only the language rules.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract Guarded {
    bool transient locked;          // transient slot 0
    address transient lastCaller;   // transient slot 0, offset 1 (packed)
    uint256 public total;           // storage slot 0: separate numbering

    modifier nonReentrant() {
        require(!locked, "reentrant");
        locked = true;
        _;
        locked = false; // assign rather than `delete` if you support 0.8.28-0.8.33 via-IR
    }

    function bump() external nonReentrant {
        lastCaller = msg.sender;
        total += 1;
    }
}
```

Transient variables have their own slot numbering, starting at 0 and packed by the same rules as storage. The standard-json output shows it under a separate key, `transientStorageLayout`, next to `storageLayout`.

The rules in solc 0.8.38, each checked by compiling:

| Declaration | Result in 0.8.38 |
|---|---|
| `uint256 transient x;`, `bool`, `address`, `bytes32`, enum | compiles |
| User-defined value type, e.g. `U transient u;` with `type U is uint128` | compiles |
| Function type, e.g. `function(uint256) external transient fp;` | compiles |
| `mapping(uint256 => uint256) transient m;` | `UnimplementedFeatureError: Transient data location is only supported for value types.` |
| `uint256[] transient a;`, `bytes transient b;`, `string transient s;`, struct | same `UnimplementedFeatureError` |
| `uint256 transient x = 1;` | `DeclarationError: Initialization of transient storage state variables is not supported.` |
| `uint256 constant transient x = 1;` / `uint256 immutable transient x;` | `DeclarationError: Transient cannot be used as data location for constant or immutable variables.` |
| `uint256 transient x;` as a local or parameter | `ParserError` (only state variables can be transient) |
| `delete x;` on a transient variable | compiles; sets it to zero (verified: returns 0) |

The error class is worth noticing. Reference types give `UnimplementedFeatureError`, not `TypeError`. The language intends to support them later. Initializers are banned for a deeper reason: an initializer runs in the constructor's transaction, and the value would be wiped when that transaction ends.

> [!warning] Transient `delete` bug, 0.8.28–0.8.33 (via-IR only)
> Before 0.8.34 (18 Feb 2026), the via-IR pipeline could reuse one clearing helper for a transient and a persistent variable of the same type. `delete lock` could then emit `SSTORE` and zero a real storage slot. Assign zero instead of using `delete` if your code may compile with those versions. Details in [[1.5 Storage and transient storage]].

## Gas consequences of copying

Copying is where data locations cost real money. The pointer itself is free; the bytes it drags along are not.

### Storage → memory copies read every slot

A five-slot struct, read once from a cold contract in a fresh transaction:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract CopyCost {
    struct Big { uint256 a; uint256 b; uint256 c; uint256 d; uint256 e; }
    Big public big;

    function setup() external { big = Big(1, 2, 3, 4, 5); }

    function readViaMemory() external view returns (uint256) {
        Big memory m = big;   // five cold SLOADs, even though only m.a is used
        return m.a;
    }

    function readViaPointer() external view returns (uint256) {
        Big storage p = big;  // just the slot number
        return p.a;           // one cold SLOAD
    }
}
```

| Function | Legacy | via-IR |
|---|---|---|
| `readViaMemory` | 10,821 gas | 10,923 gas |
| `readViaPointer` | 2,323 gas | 2,376 gas |
| Difference | 8,498 | 8,547 |

The difference is four cold `SLOAD`s (4 × 2,100 = 8,400) plus the memory writes. The optimizer did **not** remove the unused loads in either pipeline. Each loaded word is written into the memory copy, and the optimizer does not prove that those memory words are never read, so the loads stay.

The rule: copy a storage struct to memory only when you will read most of its fields more than once. Otherwise use a storage pointer, or read the fields you need into local value-type variables.

### Calldata vs memory parameters

`sum(uint256[] xs)` and `first(uint256[] xs)` (returns `xs[0]`), with the same calldata, so the transaction's calldata cost is identical:

| `n` elements | `sum` calldata | `sum` memory | `first` calldata | `first` memory |
|---|---|---|---|---|
| 1 | 719 | 870 | 523 | 755 |
| 10 | 2,312 | 3,228 | 523 | 1,484 |
| 100 | 18,242 | 26,829 | 523 | 8,795 |
| 1,000 | 177,542 | 264,584 | 523 | 83,650 |

(Legacy pipeline. via-IR: `first` was 362 for calldata vs 602 / 1,214 / 7,355 / 70,510 for memory.)

The `first` column shows the mechanism clearly. With `calldata`, the cost does not depend on `n`: the function reads one word. With `memory`, the ABI decoder must copy all `n` words into memory before the function body runs, at about 70–83 gas per element on these numbers plus memory expansion. The decoder also validates the input as it copies. For a `uint256[]` the copy is the bulk of the cost; for an array of structs or of `bytes` it is worse, because each element needs its own offset checks.

> [!tip] When `memory` parameters still make sense
> Use `memory` when you must modify the input in place (sorting, normalizing), or when internal callers pass memory arrays. Everything else in an `external` function: `calldata`.

### `delete` on a storage array costs per element

`delete list` on a storage `uint256[]` clears the length slot and every element slot. Measured: 10 elements cost 55,893 gas of execution with a refund counter of 52,800 (11 cleared slots × 4,800). 100 elements cost 510,753 gas, with 484,800 of refunds, of which only one fifth of the transaction's gas can be paid back. Clearing is linear in length, and an attacker who can grow the array can make `delete` exceed the block gas limit ([[5.7 Denial of service and griefing]]).

## Solidity and Yul in practice

### Pick the location by what the function does with the data

| The function... | Use |
|---|---|
| Reads an external input once or a few times | `calldata` |
| Must modify an external input | `memory` |
| Reads one or two fields of a stored struct | `storage` pointer, or copy the fields into value-type locals |
| Reads most fields of a stored struct several times, writes none | `memory` copy (one read per slot, then 3-gas `MLOAD`s) |
| Updates fields of a stored struct | `storage` pointer, so writes land directly |
| Needs a per-transaction flag or counter | `transient` value-type state variable |

### Caching a struct correctly

The "copy to memory to save gas" pattern is fine for reads. It becomes a bug when storage changes after the copy and you keep using the copy. A safe shape: read into memory, compute, write back through a storage pointer, and never use the memory copy after anything that may have changed storage.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract Pools {
    struct Pool { uint128 accPerShare; uint64 lastUpdate; uint64 rate; }
    mapping(address => Pool) public pools;

    function _update(address token) internal returns (Pool memory p) {
        Pool storage sp = pools[token];
        p = sp;                                   // copy; 128 + 64 + 64 bits = one slot
        uint256 elapsed = block.timestamp - p.lastUpdate;
        p.accPerShare += uint128(elapsed * p.rate);
        p.lastUpdate = uint64(block.timestamp);
        pools[token] = p;                         // write back (copy into storage)
    }

    function deposit(address token) external {
        Pool memory p = _update(token);           // take the copy AFTER the update
        // ... use p.accPerShare here, never a copy taken before _update
        p;
    }
}
```

### Growing a memory array in assembly

Solidity will not `push` to a memory array, but assembly can, as long as it respects the free memory pointer. There are two cases. If the array is the most recent allocation, its end equals the free memory pointer and we can extend it in place. Otherwise something sits right after it, and we must copy the array to fresh memory.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

library MemArray {
    /// Append `v`. Grows in place if `a` is the last allocation,
    /// otherwise copies `a` into a new, larger allocation.
    function push(uint256[] memory a, uint256 v) internal pure returns (uint256[] memory r) {
        assembly ("memory-safe") {
            let len := mload(a)
            let end := add(add(a, 0x20), mul(len, 0x20))
            let fmp := mload(0x40)
            switch eq(end, fmp)
            case 1 {
                mstore(end, v)                 // write the new element
                mstore(a, add(len, 1))         // bump the length word
                mstore(0x40, add(end, 0x20))   // claim the word
                r := a
            }
            default {
                r := fmp
                mstore(r, add(len, 1))
                mcopy(add(r, 0x20), add(a, 0x20), mul(len, 0x20))  // Cancun+
                mstore(add(add(r, 0x20), mul(len, 0x20)), v)
                mstore(0x40, add(add(r, 0x40), mul(len, 0x20)))
            }
        }
    }
}

contract UsesMemArray {
    using MemArray for uint256[];

    function build() external pure returns (uint256[] memory a) {
        a = new uint256[](0);
        for (uint256 i; i < 3; ++i) a = a.push(i + 1);  // [1, 2, 3], grown in place
    }
}
```

Run in py-evm: starting from `new uint256[](0)` at `0x80`, three pushes returned `[1, 2, 3]` and the pointer stayed `0x80` (in-place path). When a `bytes` allocation was made between the array and the push, the result moved from `0x80` to `0x100` (copy path) and held `[0, 9]`. Always use the **returned** pointer: after a copy, the old variable still points at the old, shorter array. This is the same contract as Go's `append`. Memory-safe assembly rules and the free memory pointer protocol are in [[3.5 Memory management in assembly]].

### Reading storage pointers and memory pointers in assembly

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract Pointers {
    struct Item { uint256 id; uint256 amount; }
    Item[] internal items;

    function where() external returns (uint256 slot, uint256 memPtr) {
        items.push(Item(1, 2));
        Item storage it = items[0];
        Item memory m = Item(3, 4);
        assembly {
            slot := it.slot     // storage pointer: a slot number
            memPtr := m         // memory pointer: a byte offset
        }
    }
}
```

`slot` came back as `keccak256(abi.encode(0))`, the first data slot of a dynamic array declared at slot 0, and `memPtr` as `0xc0` in both pipelines. Not `0x80`: the `Item(1, 2)` passed to `push` was built in memory first and took `0x80`–`0xbf`. Memory is never freed within a call, so even temporaries move the next pointer. For a `calldata` array, the assembly names are `x.offset` and `x.length`. [[3.4 Interop with Solidity]] covers these suffixes.

## Pitfalls and incidents

| Date | What | Data-location root cause |
|---|---|---|
| Sep 2026 (0.8.37) | Memory byte array element delete bug, legacy pipeline, all versions up to 0.8.36 | `delete b[i]` on `bytes memory` cleared 32 bytes instead of 1 |
| 18 Feb 2026 (0.8.34) | Transient storage clearing helper collision, via-IR, 0.8.28–0.8.33 | `delete` of a transient variable could emit `SSTORE` |
| 28 Dec 2020 | Cover Protocol "Blacksmith" infinite mint, about $4.4 million cashed out | A pool struct cached in `memory` went stale after storage was updated |
| Before 0.5.0 (Nov 2018) | Uninitialized storage pointer honeypots and bugs | An unassigned local struct defaulted to `storage` slot 0 |

### Stale memory caches (Cover Protocol)

Cover's liquidity-mining contract copied a pool's data into memory, then called an update that wrote a new, much larger `accRewardsPerToken` to storage. The code went on to compute the user's `rewardWriteoff` from the **old** memory copy. The attacker drained the pool's balance to near zero so the per-token rate spiked, deposited again, and was credited rewards with almost no write-off. The contract minted about 40.8 quintillion COVER (40,796,131,214,802,500,000 per Mudit Gupta's analysis). Simplified shape:

```text
Pool memory pool = pools[token];            // copy
updatePool(token);                          // writes pools[token].accRewardsPerToken
miner.rewardWriteoff = miner.amount * pool.accRewardsPerToken / MULT;   // stale copy
```

The defense is the rule in [[#Caching a struct correctly]]: a memory copy is a snapshot. Take it after the last write, or use a storage pointer.

### Dangling storage pointers

A storage pointer is a slot number. Nothing ties it to the array's length, so shrinking the array does not invalidate it. The full experiment is in the A-level question below. In short: after `Item storage it = items[1]; items.pop();`, reading `it.id` returns 0 (pop zeroed the slot), and writing `it.amount = 777` writes into a slot past the end. The length stays 1. A later `items.push()` makes index 1 live again, and `items[1]` reads `(0, 777)`. No compiler warning is printed for this pattern in 0.8.38.

### Partial `delete` of structs with mappings

`delete accounts[id]` zeroes every non-mapping field and silently keeps every mapping entry. Re-creating the account, or pushing a new element into an array of such structs, brings the old entries back. Foundry's linter flags this as `mapping-deletion` (medium severity). Covered in depth in the E-level question.

> [!warning] `delete` and `pop` on unbounded arrays
> Both cost gas per slot. A storage array that users can grow without limit makes `delete arr` a denial-of-service lever ([[5.7 Denial of service and griefing]]). A struct with a big nested array has the same problem on `delete s` or `s = S(...)`.

### Quick checklist for reviews

- Every `X memory x = storageThing;` is a full copy. Is it read enough to justify it? Is it used after storage changed?
- Every `X storage p = ...;` taken before a `pop`, `delete` or re-assignment of the parent: can it dangle?
- Every `external` function with `memory` parameters it never writes: switch to `calldata`.
- Every `delete` of a struct or struct array: does the type contain a mapping?
- Every memory array passed to an internal function: does the callee mutate it, and does the caller expect that?
- Every transient variable: is it cleared or used safely when the same contract is called twice in one transaction ([[5.11 New attack surfaces - transient storage, EIP-7702, account abstraction]])?

## Question ladder

> [!question]- **B** Name each data location and its lifetime.
> Solidity has five places for data. The first four are explicit keywords for reference types; the fifth is implicit.
>
> | Location | Lives until | Notes |
> |---|---|---|
> | `storage` | Overwritten or cleared; survives across transactions | Default for state variables. Per contract (per storage context under `DELEGATECALL`). Most expensive. |
> | `transient` | End of the current transaction | State variables only, value types only (0.8.28+). Shared by all calls to this contract in the transaction. Rolled back if the frame that wrote it reverts. |
> | `memory` | The current external call frame returns | Fresh, zeroed memory per frame. Solidity never frees it within a frame. Shared by all internal function calls in that frame. |
> | `calldata` | The current call frame returns | The input bytes of the call. Read-only. No copy unless you ask. |
> | stack | The variable goes out of scope | Value-type locals, parameters, return values, and the pointers of reference-type locals. Only the top 16 items are reachable. |
>
> An interviewer may push on "memory lives until the function returns". That is wrong for internal calls: an internal call is a `JUMP` within the same frame, so a memory array created in a helper and returned to the caller stays valid. Memory dies when the **external** frame ends.

> [!question]- **I** Which assignments copy and which alias: storage→memory, memory→memory, storage→local storage pointer, memory→storage?
> | Assignment | Behavior | Verified |
> |---|---|---|
> | storage → memory (`S memory m = s;`) | **copy**: one `SLOAD` per slot, including nested dynamic arrays | changing `m.a` left `s.a` = 1 |
> | memory → memory (`S memory b = a;`) | **alias**: copies one stack word (the offset) | changing `b.a` changed `a.a` |
> | storage → local storage pointer (`S storage p = s;`) | **alias**: `p` holds `s`'s slot number | changing `p.a` changed `s.a` |
> | memory → storage (`s = m;`) | **copy**: one `SSTORE` per slot | changing `m.a` after left `s.a` = 1 |
>
> The rest of the rule: anything **from calldata** copies (calldata cannot be aliased into another location, and you cannot write to it anyway). Any assignment to a **state variable** copies, even storage → storage (`t = s;`). Value types always copy.
>
> The memory model explains it. A reference-type local is one pointer on the stack. A pointer names a position inside one area. Assignments that stay inside one area can copy the pointer. Assignments that cross areas must copy the bytes.
>
> Two corollaries interviewers like:
> - **Passing a memory struct to an internal function passes a reference.** The callee can change the caller's data.
> - **`delete` on a memory variable is an assignment.** It rebinds that variable to a fresh zero value and leaves aliases alone (verified: after `m2 = m1; delete m2;`, `m1.a` was still 1). But `delete m.a` on a field writes in place, so aliases see 0 (verified).
>
> And the illegal ones: memory → local storage pointer is a compile error (*"... memory is not implicitly convertible to expected type ... storage pointer"*), and any copy of a type containing a mapping is a compile error (*"Types in storage containing (nested) mappings cannot be assigned to."*).

> [!question]- **I** Why prefer `calldata` for external function parameters?
> Because `memory` parameters force the ABI decoder to copy the whole argument into memory before the function body runs. `calldata` parameters are a pointer into the input. Nothing is copied, and each element is read with one `CALLDATALOAD` when you touch it.
>
> Measured on solc 0.8.38 (legacy, optimizer on), a function that returns `xs[0]`:
>
> | Elements | `calldata` | `memory` |
> |---|---|---|
> | 1 | 523 gas | 755 gas |
> | 100 | 523 gas | 8,795 gas |
> | 1,000 | 523 gas | 83,650 gas |
>
> The calldata version is flat. The memory version grows linearly (about 70–83 gas per element in my runs, legacy and via-IR) plus quadratic memory expansion. Summing all elements still favored calldata by about a third (177,542 vs 264,584 gas at 1,000 elements), because the memory version reads every word twice: once to copy, once to sum.
>
> Other reasons:
> - **Safety by type.** The compiler forbids writes (*"Calldata arrays are read-only."*), so a reviewer knows the input is unchanged.
> - **Slices.** Only calldata supports `x[a:b]` and `data[4:]`, which is how routers and multicall decoders split inputs for free.
> - **Pass-through.** Since 0.6.9, internal functions can take calldata too, so you can pass the input down a call chain without copying.
> - **Memory DoS.** An attacker controls array lengths in calldata. With `memory`, a huge length costs your function quadratic memory gas before your first line runs ([[1.4 Memory]]).
>
> When not to: if you must modify the input, or if internal callers need to pass memory arrays to a `public` function (a memory argument cannot convert to a calldata parameter).

> [!question]- **A** Why can't you `push` to a memory array, and how would you grow one in assembly?
> **Why not.** Solidity's memory allocator is a bump allocator. `new uint256[](n)` writes the length at the free memory pointer, reserves `n` words after it, and moves the pointer past the end. The next allocation is placed immediately after. There is no spare capacity, no header with a capacity field, and no `free`. Growing in place would overwrite whatever was allocated next. Solidity could implement `push` as "allocate a bigger array and copy", but that would silently change the pointer and break every alias, and would cost O(n) per push with no capacity doubling. So the language just forbids it: *"Member "push" is not available in uint256[] memory outside of storage."* and *"Member "length" is read-only and cannot be used to resize arrays."*
>
> **How in assembly.** Check whether the array is the last allocation: `add(add(a, 0x20), mul(mload(a), 0x20)) == mload(0x40)`.
> - If yes, write the new element at the end, increment the length word, and bump the free memory pointer by 32. The pointer does not change, so aliases see the new length too.
> - If no, allocate `32 · (len + 2)` bytes at the free memory pointer, write `len + 1`, `mcopy` the old elements, write the new one, and bump the pointer. Return the new pointer. Aliases still see the old array.
>
> The `MemArray.push` library above does exactly this. In py-evm, three pushes onto an empty array grew it in place at `0x80`. With a `bytes` allocated in between, the push copied the array to `0x100`.
>
> Things an interviewer listens for:
> - Never trust memory above the free memory pointer to be zero. Write every word you claim.
> - Update `0x40` so later Solidity code does not overwrite your data. That is what makes the block honestly `"memory-safe"`.
> - Always use the returned pointer, since the copy path moves the array.
> - For many pushes, reserve capacity up front (allocate `cap` words, set the length word lower, raise it as you fill). This is the pattern used by libraries such as Solady's `DynamicBufferLib`. The cost of pushing then stays O(1) per element.
> - `mcopy` needs the `cancun` EVM version or later (default in 0.8.38 is `osaka`). See [[3.5 Memory management in assembly]].

> [!question]- **A** What goes wrong with `Item storage it = items[i]; items.pop();`?
> `it` is a slot number, computed as `keccak256(slot of items) + i * 2` when the pointer was made. `pop()` decrements the length and zeroes the last element's slots, but it cannot reach your local variable. If `i` was the last index, `it` now points past the end of the array, and **no bounds check applies to accesses through a pointer**.
>
> Experiment (solc 0.8.38, legacy and via-IR identical). `items` is an `Item[]` at slot 0, `Item { uint256 id; uint256 amount; }`, seeded with `(1, 100), (2, 200)`. Data starts at `keccak256(abi.encode(0)) = 0x290d...e563`.
>
> ```solidity
> // SPDX-License-Identifier: MIT
> pragma solidity ^0.8.28;
>
> contract Dangle {
>     struct Item { uint256 id; uint256 amount; }
>     Item[] public items; // slot 0 holds the length
>
>     function seed() external {
>         items.push(Item(1, 100));
>         items.push(Item(2, 200));
>     }
>
>     function popThenUse() external returns (uint256 readId, uint256 readAmount, uint256 len) {
>         Item storage it = items[1];
>         items.pop();              // zeroes items[1], length = 1
>         readId = it.id;           // 0
>         it.amount = 777;          // writes past the end: no bounds check
>         readAmount = it.amount;   // 777
>         len = items.length;       // 1
>     }
>
>     function pushEmpty() external returns (uint256 id, uint256 amount) {
>         items.push();             // does not clear the new element's slots
>         Item storage e = items[items.length - 1];
>         return (e.id, e.amount);  // (0, 777)
>     }
> }
> ```
>
> | Step | length (slot 0) | data slots `base+0 .. base+3` | Return |
> |---|---|---|---|
> | after `seed()` | 2 | `1, 100, 2, 200` | |
> | after `popThenUse()` | 1 | `1, 100, 0, 777` | `(0, 777, 1)` |
> | after `items.push()` | 2 | `1, 100, 0, 777` | new element reads `(0, 777)` |
> | `items(1)` getter | | | `(0, 777)` |
>
> What goes wrong:
> 1. **Reads return zero**, which code may treat as "empty" or "no owner".
> 2. **Writes succeed** and pay normal `SSTORE` gas, but the data is invisible: the length says it does not exist. (Here the write cost only 100 gas because `pop` had already dirtied the slot in the same transaction. A write to a slot that was zero at the start of the transaction costs 20,000.)
> 3. **Resurrection.** `push()` with no argument does not clear the new slot. It assumes the slots past the end are zero, which is true only if nothing wrote there. Here the new element came back as `(0, 777)`. `push(Item(0, 0))` would overwrite it, but the no-argument form is very common.
> 4. If `i` was **not** the last index (for example a swap-and-pop removal where you moved the last element into `i` first), `it` still points at a live element, but now it is a different item than before. Code after the pop silently edits the wrong record.
>
> Fixes: finish all reads and writes through the pointer before shrinking the array; re-derive pointers after any `pop`, `delete` or reassignment of the parent; in swap-and-pop, take the pointer to the moved element after the move. The compiler gives no warning here, so this is a review and testing item ([[6.2 Unit, fuzz and invariant testing]]).

> [!question]- **E** What does `delete` do for each type, and why does deleting a struct leave its nested mapping untouched?
> `delete x` means `x = <zero value of its type>`. It is an assignment, which explains every case below. All rows were verified on solc 0.8.38 except where noted.
>
> | Target | Effect |
> |---|---|
> | Value types (`uint`, `int`, `address`, `bool`, `bytesN`, enum, UDVT) | Set to zero (`false`, `address(0)`, first enum member). |
> | Internal function type variable | Set to zero. Calling it afterwards reverts with `Panic(0x51)` (verified). |
> | Storage static array `T[3]` | Every element is reset. |
> | Storage dynamic array `T[]`, storage `bytes`/`string` | Length set to 0 and every element slot zeroed (a 54-byte string: length slot and both data slots became 0). Cost is linear: 10 elements → 55,893 gas with 11 × 4,800 refund. |
> | Array element `delete a[i]` | That element is reset. Length unchanged (`[1, 2, 3]` → `[1, 0, 3]`). |
> | Struct | Every member is reset recursively, **except mappings**, which are skipped at any depth. |
> | Mapping `delete m` | Compile error: *"Built-in unary operator delete cannot be applied to type mapping(uint256 => uint256)."* `delete m[k]` is fine and resets one value. |
> | Local storage pointer `delete p` | Compile error (no zero storage object to point to). |
> | Memory variable `delete m` | Rebinds `m` to a fresh zero value. Aliases keep the old data (verified `(len, aliasLen) = (0, 3)` for an array). |
> | Memory field / element `delete m.a`, `delete arr[i]` | Writes zero in place; aliases see it. |
> | `bytes memory` element `delete b[i]` | Clears that one byte. **Bug before 0.8.37:** on the legacy pipeline it cleared 32 bytes starting at `b[i]`, "corrupting up to 31 bytes after the element" (SOL-2026-5, low/medium, all versions up to 0.8.36; via-IR unaffected; `b[i] = 0` was always correct). I reproduced it with solc-js 0.8.36: deleting `b[1]` of a 37-byte array zeroed bytes 1–32; 0.8.38 cleared only byte 1. |
> | Transient variable | Set to zero with `TSTORE`. Via-IR 0.8.28–0.8.33 could emit `SSTORE` instead (fixed in 0.8.34). |
>
> **Why mappings survive.** A mapping has no storage of its own except an unused anchor slot. Its values live at `keccak256(key . slot)` for every possible key, and the contract keeps no list of which keys were written ([[2.3 Storage layout]]). To delete a mapping, the compiler would have to clear 2^256 possible slots. So `delete` skips mappings, and the type checker forbids `delete m` on a bare mapping. A struct is just its members at consecutive slots, so `delete s` walks the members, zeroes the value members and arrays, and skips the mapping member.
>
> I verified it: `Account { uint256 balance; mapping(address => uint256) allowance; }` with `balance = 50`, `allowance[0xBEEF] = 123`. After `delete accounts[1]`, reads returned `(0, 123)`. solc 0.8.38 printed **no error and no warning**, in either pipeline. (Assigning such a struct, `t = s`, is an error; deleting it is not.) The same happens with arrays of such structs: after `accts.pop()` then `accts.push()`, the new element's `allow[address(1)]` read back the old 77.
>
> What an interviewer listens for:
> - **The security consequence.** "Deleted" accounts keep allowances, votes, nonces or role flags. Re-registering the same id brings them back. Static analyzers flag it (Foundry lint `mapping-deletion`, medium).
> - **The fixes and their trade-offs.**
>   1. Track keys (an `EnumerableSet` next to the mapping) and delete each one. Correct, but costs a write per key and makes deletion O(n), a DoS risk for big sets.
>   2. **Versioning / epochs**: key the inner mapping by `(epoch, key)` or nest `mapping(uint256 epoch => mapping(address => uint256))` and bump the epoch on reset. O(1) reset, old data stays on chain but becomes unreachable. This is the standard answer.
>   3. Never reuse ids: allocate a fresh struct for every new account, so stale entries are never reachable by the same id.
> - **Gas facts.** Each cleared slot is a 2,900-gas reset (5,000 cold) with a 4,800 refund, and refunds are capped at one fifth of the transaction's gas ([[1.5 Storage and transient storage]]). So "delete to get gas back" helps little, and deleting large arrays can blow the gas limit.
> - **The memory/bytes nuance.** Mentioning that `delete b[i]` on `bytes memory` had a legacy-pipeline bug until 0.8.37, and that `b[i] = 0` is the portable form, shows you track compiler bugs, not just language rules ([[2.10 Version map of 0.8.x features]]).
