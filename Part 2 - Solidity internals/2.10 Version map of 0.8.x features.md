# 2.10 Version map of 0.8.x features

> [!abstract] In one minute
> - 0.8.0 (16 Dec 2020) brought **checked arithmetic**, **ABI coder v2 by default** and **`Panic(uint256)`** for failed asserts. Every later 0.8.y release is "non-breaking" for source code, but many of them **change bytecode**: a new default EVM target, new codegen, or a bug fix.
> - The language milestones to remember: custom errors **0.8.4**, user-defined value types **0.8.8**, via-IR stable and `memory-safe` assembly **0.8.13**, UDVT operators **0.8.19**, `require(cond, CustomError)` **0.8.26** (via-IR) / **0.8.27** (legacy), `transient` state variables **0.8.28**, `layout at` **0.8.29**, `erc7201()` **0.8.35**, `block.slotnum` **0.8.37** (Amsterdam only).
> - The default `evmVersion` moved: istanbul (0.8.0) → berlin 0.8.5 → london 0.8.7 → paris 0.8.18 → shanghai 0.8.20 (**PUSH0**) → cancun 0.8.25 (**MCOPY** in codegen) → prague 0.8.30 → **osaka 0.8.31** (still the default in 0.8.38). `amsterdam` exists since 0.8.36 but is **experimental**.
> - Targets older than `london` are **deprecated** (homestead to byzantium in 0.8.22, constantinople to berlin in 0.8.37). 0.8.38 still accepts them with a warning.
> - Recent serious compiler bugs: **TransientStorageClearingHelperCollision** (high, via-IR, 0.8.28–0.8.33), **InheritanceOrderReversalOnStorageEndWarning** and **UnsoundSpillInMutualRecursion** (medium, fixed 0.8.36), two via-IR/legacy memory bugs fixed in 0.8.37, and a Yul optimizer bug fixed in 0.8.38. **0.8.38 has no known bugs** in `bugs_by_version.json`.
> - Only the **latest release** gets security fixes. Upgrading an audited codebase is a bytecode change: check `bugs.json` for your version and pipeline, diff bytecode, gas and storage layout, re-run every test, and scope a partial re-audit.

**Prerequisites:** [[1.11 Hard forks that changed contract code]], [[2.1 Types]], [[2.8 Errors and reverts]] · **Leads to:** [[3.11 Compiler IR and the optimizer]], [[5.13 Toolchain, dependencies and operations]], [[6.7 Deployment and verification]], [[6.9 Audit process]]

Every date and version below comes from the compiler's own `Changelog.md`, `docs/bugs.json` and `docs/bugs_by_version.json` (downloaded from the `develop` branch of github.com/argotorg/solidity on 30 Oct 2026) or from the soliditylang.org release posts. Every "compiles / does not compile / warns" claim was checked with solc-js 0.8.38. The bug reproductions were run against solc-js 0.8.36 and 0.8.38 in py-evm.

## Why a version map matters

A Solidity compiler version is not just a syntax level. It decides four separate things:

1. **What source you can write.** `error`, `type T is uint256`, `transient`, `layout at` and `erc7201()` each need a minimum version.
2. **Which EVM the bytecode targets.** The default `evmVersion` decides whether the compiler emits `PUSH0`, `MCOPY` or `CLZ`, and which opcodes inline assembly may use. A chain that has not activated a fork rejects code that uses its opcodes.
3. **How the code is generated.** The same source gives different bytecode from release to release: new optimizer steps, cheaper checked arithmetic, unchecked loop counters, a new default Yul optimizer sequence.
4. **Which compiler bugs you inherit.** Each release ships with a set of known bugs. Some are only found years later and are recorded backwards in `bugs.json`.

Solidity still uses `0.x` versioning. Breaking changes to the language arrive only in `0.x.0` releases (0.8.0 was the last). A `0.8.y` release keeps old source compiling, but it is free to change defaults and bytecode. That is why "we only bumped the patch version" is not a safe argument in an audit. The changes to watch are mostly not in the language features column. They are in the EVM target and codegen columns.

> [!note] How to read the tables
> Tables are newest first, as everywhere in this vault. "Legacy" means the default evmasm pipeline. "Via-IR" means `--via-ir` / `settings.viaIR: true` (the Yul-based pipeline, see [[3.11 Compiler IR and the optimizer]]). Bug names are the `name` field in `bugs.json`, with the severity the Solidity team assigned. Purely tooling items (SMTChecker, LSP, build system) are left out unless they touch contract bytecode or audit workflow.

> [!warning] Two rows of the release history are easy to get wrong
> - **`string.concat` and 0.8.12.** The 0.8.12 changelog does not list `string.concat` as a new feature. It says it "now properly takes strings as arguments and returns `string memory`. It was accidentally introduced as a copy of `bytes.concat` before." I checked: solc-js **0.8.11** rejects `string.concat(a, b)` on two `string`s ("Invalid type for argument in the bytes.concat function call… string provided"). **0.8.12** compiles it. So 0.8.12 is the first version where `string.concat` works as documented.
> - **Release posts vs changelog dates.** The blog list dates the 0.8.24 post 26 Jan 2024 and the 0.8.14 post 18 May 2022. The changelog says 25 Jan 2024 and 17 May 2022. This note uses the changelog dates (the release tags).

### The four eras of 0.8.x

The table is long. It reads better as four phases.

**2020–2021: the safe-by-default reset (0.8.0–0.8.10).** 0.8.0 made overflow a revert instead of a silent wrap ([[2.9 Arithmetic and numeric pitfalls]]) and made ABI coder v2 the default ([[2.5 ABI encoding and decoding]]). The next releases added the tools that modern code takes for granted: `catch Panic` (0.8.1), custom errors (0.8.4, [[2.8 Errors and reverts]]) and user-defined value types (0.8.8, [[2.1 Types]]). The default target followed mainnet to `berlin` and then `london`.

**2022: via-IR goes production (0.8.11–0.8.17).** `abi.encodeCall` (0.8.11) gave type-checked calldata. 0.8.13 removed the "experimental" label from via-IR and added the `memory-safe` assembly annotation, which lets the via-IR pipeline move variables to memory around inline assembly. The new optimizer paths then produced a cluster of bugs: InlineAssemblyMemorySideEffects (0.8.13–0.8.14) and StorageWriteRemovalBeforeConditionalTermination (0.8.13–0.8.16), plus the calldata re-encoding bugs fixed in 0.8.14 and 0.8.16. Lesson: a pipeline that just lost its "experimental" tag deserves extra testing.

**2023–2024: following the forks (0.8.18–0.8.28).** Paris (0.8.18), Shanghai and `PUSH0` (0.8.20), Cancun opcodes in assembly (0.8.24), Cancun as default with `MCOPY` in codegen (0.8.25), Prague (0.8.27). Language work in this era was ergonomic: UDVT operators (0.8.19), relaxed immutables (0.8.21), file-level events and unchecked loop counters (0.8.22), `require` with custom errors (0.8.26/0.8.27) and finally `transient` state variables (0.8.28).

**2025–2026: storage control and clean-up (0.8.29–0.8.38).** `layout at` (0.8.29) and `erc7201()` (0.8.35) let a contract move its whole storage block, which matters for proxies and namespaced storage ([[2.3 Storage layout]]). Prague and then Osaka became the defaults. 0.8.31 started the deprecation warnings that point at 0.9.0. 0.8.35 put every experimental feature behind an explicit switch, 0.8.36 removed the EOF backend and added an experimental `amsterdam` target, and 0.8.37–0.8.38 prepared for Glamsterdam (`block.slotnum`, reserved `dupn`/`swapn`/`exchange`). This era also produced the most serious recent bug, TransientStorageClearingHelperCollision (high), in a feature only months old.

## Default `evmVersion` by compiler version

The `evmVersion` setting tells the compiler which hard fork's rules to assume. It controls three things: which opcodes the code generator may emit on its own (`PUSH0`, `MCOPY`), which builtins inline assembly may use (`tload`, `clz`, `slotnum`), and the gas costs the optimizer assumes. [[1.11 Hard forks that changed contract code]] covers what each fork changed in the EVM. This table covers when the compiler started assuming it **by default**.

| Compiler version (date) | New default `evmVersion` | What the default change does to your bytecode |
|---|---|---|
| 0.8.31 (3 Dec 2025) | **`osaka`** (still the default in 0.8.38) | Enables Yul `clz`. The code generator does not emit `CLZ` on its own, so ordinary bytecode is the same as for `prague` |
| 0.8.30 (7 May 2025) | `prague` | No new opcodes for Solidity codegen. Mostly a label change |
| 0.8.25 (14 Mar 2024) | `cancun` | Byte-array copies use **`MCOPY`** (0x5e). `transient` and `tload`/`tstore` become usable without setting a target |
| 0.8.20 (10 May 2023) | `shanghai` | **`PUSH0`** (0x5f) replaces `PUSH1 0x00` everywhere. Code shrinks, and fails on any chain without Shanghai |
| 0.8.18 (1 Feb 2023) | `paris` | `block.prevrandao`; `difficulty()` disallowed in assembly |
| 0.8.7 (11 Aug 2021) | `london` | `block.basefee` / `basefee()` available |
| 0.8.5 (10 Jun 2021) | `berlin` | Optimizer assumes cold-access costs (EIP-2929) |
| 0.8.0 (16 Dec 2020) | `istanbul` (default since 0.5.14) | — |

I confirmed the current default by compiling with no `evmVersion` and reading the metadata: solc-js 0.8.38 writes `"evmVersion": "osaka"`.

> [!tip] Always pin `evmVersion` explicitly
> The default follows Ethereum mainnet, not your deployment chain. A project that floats `pragma solidity ^0.8.0` and lets the toolchain pick the newest compiler silently picked up `PUSH0` in May 2023 and `MCOPY` in March 2024. Set `evm_version` in `foundry.toml` (or `settings.evmVersion`) to the oldest fork among all chains you deploy to. Part 1 has the measured size effect ([[1.11 Hard forks that changed contract code]]); the next section shows it again for one contract.

### What the target changes in one contract

I compiled the same contract (a `bytes.concat(a, b)` of two `bytes memory` arguments) for each target with solc-js 0.8.38 and counted opcodes in the runtime code (skipping push data and the CBOR metadata tail):

| Target | Legacy: runtime bytes / `PUSH0` / `MCOPY` | Via-IR: runtime bytes / `PUSH0` / `MCOPY` |
|---|---|---|
| `london`, `paris` | 591 / 0 / 0 | 470 / 0 / 0 |
| `shanghai` | 574 / 25 / 0 | 461 / 9 / 0 |
| `cancun`, `prague`, `osaka` | 548 / 26 / 2 | 419 / 10 / 3 |

So one compiler version produces three different bytecodes for one source file, depending only on the target. This is the first thing to check when bytecode "unexpectedly" changes after a toolchain upgrade.

Solidity removes features only in breaking releases. During 0.8.x it announces them with warnings. The 0.8.31 release post says these are scheduled for removal in 0.9.0 (no date given). Everything below was checked with solc-js 0.8.38, in both pipelines.

Four patterns stand out:

- **Via-IR carries most recent risk.** Of the seven 2026 bugs, five need via-IR or the Yul optimizer. Via-IR is the newer, more aggressive pipeline. Its stack-to-memory mover alone produced two bugs (SOL-2026-2 and SOL-2026-4), both latent since 0.7.2.
- **New features ship with bugs.** Transient variables arrived in 0.8.28; their high-severity clearing bug lived until 0.8.34. `layout at` arrived in 0.8.29; its inheritance-reversal bug lived until 0.8.36. UDVTs arrived in 0.8.8 with a storage-layout bug fixed two days later in 0.8.9.
- **Old code paths hide old bugs.** MemoryByteArrayElementDeleteClearsWholeWord and DirtyBytesArrayToStorage predate the first release. LostStorageArrayWriteOnSlotOverflow dates from 0.1.0. "Mature" does not mean "bug-free".
- **Severity is the team's estimate of real-world impact.** It combines how likely the trigger is, how easy it is to spot in tests and how bad the damage is. "Low" does not mean "harmless if you hit it". It usually means "hard to hit".

## How to read `bugs.json` and check your exposure

Every entry has the same shape. Here is the start of the newest one, as downloaded:

```text
{
  "uid": "SOL-2026-7",
  "name": "YulOptimizerKnowledgeBaseStaleBookkeeping",
  "summary": "The Yul optimizer could consider two memory or storage locations distinct ...",
  "description": "The Yul optimizer steps ``LoadResolver`` and ``EqualStoreEliminator`` ...",
  "link": "https://blog.soliditylang.org/2026/10/22/yul-optimizer-knowledge-base-stale-bookkeeping-bug/",
  "introduced": "0.8.19",
  "fixed": "0.8.38",
  "severity": "low",
  "conditions": {"yulOptimizer": true}
}
```

The fields, as the docs define them:

| Field | Meaning |
|---|---|
| `uid` | `SOL-<year>-<number>`. Several entries can share one uid when a bug hits several version ranges |
| `name` | Unique name. This is what `bugs_by_version.json` lists |
| `summary`, `description`, `link` | Short and long explanation, and usually a blog post with the trigger and examples |
| `introduced` | First published version with the bug. Optional: missing means "all versions before `fixed`" |
| `fixed` | First published version without the bug |
| `severity` | `very low`, `very low/low`, `low`, `low/medium`, `medium`, `medium/high` or `high` |
| `conditions` | Settings that must hold: `optimizer` (the evmasm optimizer), `yulOptimizer`, `ABIEncoderV2`, `viaIR` (`true` = only via-IR, `false` = only legacy), `evmVersion` (a comparison like `">=cancun"`). No conditions means "assume the bug is present" |
| `check` | Optional heuristics: a `source-regex` (no match → bug very likely absent) or an `ast-compact-json-path` (match → bug likely present) |

`bugs_by_version.json` maps each version to `{"bugs": [names…], "released": "YYYY-MM-DD"}`. It answers "which bugs exist in 0.8.x", but not "which apply to my settings". You need both files.

The exposure check, step by step:

1. **Find the exact compiler and settings of the deployed code.** Do not trust the pragma. Read the verified metadata (Etherscan/Sourcify) or decode the CBOR tail of the runtime code (shown below; more in [[6.7 Deployment and verification]]). The CBOR tail gives only the version; optimizer, via-IR and target come from the metadata JSON. You need: version, optimizer on/off, via-IR on/off, `evmVersion`, ABI coder.
2. **Look up the version in `bugs_by_version.json`.**
3. **Filter by `conditions`** against your settings.
4. **For each remaining bug, read `description`** and decide whether your code has the trigger pattern. The descriptions are precise about triggers (for example, SOL-2026-1 needs `delete` on a transient variable *and* persistent-storage clearing in the same bytecode).
5. **Search the code** for the trigger (the `check` regex if present, or `grep` / Semgrep / Slither for the construct), then confirm by compiling with the fixed version and diffing bytecode for the affected contracts.

A small script for steps 2 and 3:

```text
# exposure.py  (python3 -I exposure.py bugs.json bugs_by_version.json <version> <legacy|via-ir> <evmVersion>)
# Assumes optimizer on, ABI coder v2. Prints bugs whose conditions match.
```

The core of it:

```text
def exposure(bugs, by_version, version, s):
    names = set(by_version[version]["bugs"])
    for b in bugs:
        if b["name"] not in names:
            continue
        c = b.get("conditions", {})
        hit = True
        if "optimizer" in c:     hit &= c["optimizer"] == s["optimizer"]
        if "yulOptimizer" in c:  hit &= c["yulOptimizer"] == (s["optimizer"] and s.get("yul", True))
        if "viaIR" in c:         hit &= c["viaIR"] == s["viaIR"]
        if "ABIEncoderV2" in c:  hit &= c["ABIEncoderV2"] == s.get("abiV2", True)
        if "evmVersion" in c:    hit &= evm_ok(c["evmVersion"], s["evmVersion"])
        if hit:
            yield b["severity"], b["name"], b.get("introduced", "-"), b["fixed"]
```

Real output against the 30 Oct 2026 files:

```text

very low    MisorderedNamedParametersInRequireWithCustomErrors   introduced 0.8.26 fixed 0.8.37
```

> [!note] The Yul optimizer runs in the legacy pipeline too
> With `optimizer.enabled: true`, the Yul optimizer is on by default even without via-IR. It optimizes inline assembly and the compiler's own Yul helpers. So `yulOptimizer: true` bugs can apply to legacy builds, usually only to inline assembly (the descriptions say which).

## Solidity and Yul in practice

### One contract, annotated with the version each feature needs

This contract uses most of the 0.8.x language features in one place. Each comment gives the release that introduced the feature. It compiles without warnings on solc-js 0.8.38 in both pipelines (legacy 1,325 runtime bytes, via-IR 998). I deployed it in py-evm: `deposit(5)` then `withdraw(7)` reverts with `0xf92f8c23` (`Insufficient(uint128,uint128)`, since a UDVT is ABI-encoded as its underlying type) followed by 5 and 7.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;                                // pin exactly in production

type Amount is uint128;                                // 0.8.8  UDVT
using {add as +, lt as <} for Amount global;           // 0.8.19 operators (0.8.13 `global`)
function add(Amount a, Amount b) pure returns (Amount) {
    return Amount.wrap(Amount.unwrap(a) + Amount.unwrap(b));   // 0.8.0 checked
}
function lt(Amount a, Amount b) pure returns (bool) {
    return Amount.unwrap(a) < Amount.unwrap(b);
}

error Insufficient(Amount have, Amount need);           // 0.8.4  custom errors
error Reentered();
event Deposited(address indexed who, Amount amount);    // 0.8.22 file-level event

uint256 constant BASE = erc7201("example.vault");       // 0.8.35 erc7201 builtin

contract Vault layout at BASE {                         // 0.8.29 layout at (0.8.31 constants)
    mapping(address user => Amount) public balanceOf;   // 0.8.18 named mapping params
    bool transient locked;                              // 0.8.28 transient (needs cancun+)

    modifier nonReentrant() {
        require(!locked, Reentered());                  // 0.8.26 via-IR / 0.8.27 legacy
        locked = true;
        _;
        locked = false;
    }

    function deposit(Amount a) external nonReentrant {
        balanceOf[msg.sender] = balanceOf[msg.sender] + a;
        emit Deposited(msg.sender, a);
    }

    function withdraw(Amount a) external nonReentrant {
        Amount have = balanceOf[msg.sender];
        require(!(have < a), Insufficient(have, a));
        balanceOf[msg.sender] = Amount.wrap(Amount.unwrap(have) - Amount.unwrap(a));
    }

    function label(string memory name) external pure returns (string memory) {
        return string.concat("vault:", name);           // 0.8.12 string.concat
    }

    function freeMemoryPointer() external pure returns (uint256 p) {
        assembly ("memory-safe") { p := mload(0x40) }   // 0.8.13 annotation
    }
}
```

The `storageLayout` output puts `balanceOf` at slot `0xd1921ee58d28820c9487d4d5d3eec1942edd7f5897e909e18a400cd2422da100`, which is `erc7201("example.vault")`. The transient `locked` is not in that list: transient variables have their own layout, which `layout at` does not move ([[2.3 Storage layout]]). Compiling the same file with `evmVersion: shanghai` fails: `Transient storage is not supported by EVM versions older than cancun.`

The minimum compiler for this file is therefore 0.8.35 (the newest feature it uses). Each feature has its own note: UDVTs and operators in [[2.1 Types]], custom errors and `require(cond, Err)` in [[2.8 Errors and reverts]], `transient` in [[1.5 Storage and transient storage]] and [[3.6 Storage, transient storage and bit packing]], `layout at` and `erc7201` in [[2.3 Storage layout]], `memory-safe` assembly in [[3.4 Interop with Solidity]] and [[3.5 Memory management in assembly]].

### `erc7201()` matches the ERC-7201 formula

I compiled `bytes32(erc7201("example.main"))` with 0.8.38, ran it in py-evm (both pipelines) and compared it with the formula `keccak256(abi.encode(uint256(keccak256(id)) - 1)) & ~bytes32(uint256(0xff))` computed in Python:

```text
erc7201("example.main")   (legacy)  0x183a6125c38840424c4a85fa12bab2ab606c4b6d0e7cc73c0c06ba5300eab500
erc7201("example.main")   (via-IR)  0x183a6125c38840424c4a85fa12bab2ab606c4b6d0e7cc73c0c06ba5300eab500
Python formula                      0x183a6125c38840424c4a85fa12bab2ab606c4b6d0e7cc73c0c06ba5300eab500
```

So code that used OpenZeppelin-style hard-coded ERC-7201 constants before 0.8.35 can switch to the builtin without moving any slot.

### Reading the compiler version from deployed bytecode

The runtime code ends with CBOR metadata. Its last two bytes are the CBOR length. The `solc` key holds three bytes: major, minor, patch. The tail of a 0.8.38 build:

```text
a2 64 69706673 58 22 1220f089…852c   64 736f6c63 43 000826   0033
   "ipfs"      bytes(34) multihash   "solc"     bytes(3)    length = 0x33 = 51
                                                 0.8.38
```

`0x26` is 38. This tells you the version, not the settings. Builds with `--no-cbor-metadata` (0.8.18+) have no tail at all; then you need the verified source and settings.

### Differential testing: old compiler vs new compiler

The most convincing way to see a compiler bug is to compile the same source with the buggy and the fixed compiler and run both. I installed solc-js 0.8.36 next to 0.8.38 and ran each build in py-evm.

**MemoryByteArrayElementDeleteClearsWholeWord** (fixed in 0.8.37, legacy only):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract DelBytes {
    function f() external pure returns (bytes memory) {
        bytes memory b = hex"0102030405";
        delete b[1];          // should clear only b[1]
        return b;
    }
}
```

```text
0.8.36 legacy -> 0100000000      <- bytes 2..4 wiped by a 32-byte MSTORE
0.8.36 via-IR -> 0100030405
0.8.38 legacy -> 0100030405
0.8.38 via-IR -> 0100030405
```

**MisorderedNamedParametersInRequireWithCustomErrors** (fixed in 0.8.37, via-IR only):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.26;

error TooSmall(uint256 have, uint256 need);

contract Named {
    function check(uint256 a) external pure {
        require(a >= 10, TooSmall({need: 10, have: a}));
    }
}
```

Calling `check(3)` and decoding the revert data `(have, need)`:

```text
0.8.36 legacy -> e94fe3af  have=3   need=10
0.8.36 via-IR -> e94fe3af  have=10  need=3     <- arguments swapped
0.8.38 legacy -> e94fe3af  have=3   need=10
0.8.38 via-IR -> e94fe3af  have=3   need=10
```

Both bugs give different results across compilers and across pipelines for the same source. That is exactly what a differential test catches and a unit test written against the buggy build would not (the test would encode the wrong expectation, or not test the field at all).

### Codegen changes you get for free: unchecked loop counters

Since 0.8.22, a `for` loop whose counter is compared with `<` and incremented by `++i` skips the overflow check on the increment. The setting is `optimizer.details.simpleCounterForLoopUncheckedIncrement` (default `true`, and it runs even with the optimizer off). I measured `sum(100)` on this loop with the setting on and off (execution gas only, no intrinsic cost):

```solidity
function sum(uint256 n) external pure returns (uint256 s) {
    for (uint256 i = 0; i < n; ++i) {
        s += i;
    }
}
```

| Pipeline | Unchecked increment (default) | Checked increment | Saved per iteration |
|---|---|---|---|
| Legacy | 12,584 gas | 18,784 gas | 62 gas |
| Via-IR | 8,880 gas | 10,379 gas | about 15 gas |

This is why the old `unchecked { ++i; }` idiom is now mostly noise. It also shows why a compiler upgrade changes your gas snapshot even when you change nothing.

## Pitfalls and incidents

> [!warning] A floating pragma is not a version
> `pragma solidity ^0.8.0;` accepts 39 compilers with different bug lists and eight different default targets. The bytecode you audited and the bytecode you deploy can come from different compilers if CI, a teammate and the deploy script resolve the pragma differently. For deployable contracts, pin the exact version (`pragma solidity 0.8.38;` or `solc_version` in `foundry.toml`) and pin `evm_version`. Libraries meant for reuse may keep a range, but the range should start at the oldest version whose bugs you accept.

> [!warning] The default target follows mainnet, not your chain
> Code compiled with 0.8.20+ defaults contains `PUSH0`. Code compiled with 0.8.25+ defaults contains `MCOPY`. A chain or rollup that has not activated Shanghai or Cancun treats those bytes as invalid opcodes: deployment or the first call fails. Part 1 notes that `PUSH0` caused most of the "invalid opcode" deployment failures on lagging L2s in 2023 and 2024 ([[1.11 Hard forks that changed contract code]], [[4.8 L2s and cross-chain]]). The same risk now applies to `osaka` (only if you write `clz` in assembly; codegen does not emit it) and, once it ships, `amsterdam`.

> [!warning] A compiler fix can change storage layout
> UserDefinedValueTypesBug (0.8.8 only): UDVTs over types shorter than 32 bytes were laid out with a full slot each. 0.8.9 packs them correctly. A proxy implementation compiled with 0.8.8 and upgraded with code compiled by 0.8.9 would read its UDVT state from the wrong slots. It was rated "very low", and it shipped in a single release that was replaced two days later, but the mechanism is the point. Always diff `storageLayout` across a compiler upgrade, not only across source changes ([[5.9 Proxies, delegatecall and storage]]).

> [!warning] New features are where the new bugs are
> `transient` (0.8.28) had a high-severity via-IR clearing bug until 0.8.34. `layout at` (0.8.29) had a medium inheritance-reversal bug until 0.8.36. `require(cond, Err({...}))` (0.8.26) encoded named arguments in the wrong order via IR until 0.8.37. Adopting a feature in the release that introduced it means you are the test suite. Wait for at least one bug-fix release, or add differential tests (old pattern vs new feature) around it.

> [!warning] Mixed-version systems
> A protocol usually has contracts compiled with several versions: an old vault, a newer router, a library built elsewhere. The bug exposure is per contract, per build. Keep a table of every deployed address with its compiler version, optimizer, via-IR and `evmVersion` setting, and re-run the `bugs.json` check against it whenever a new bug is published. The list is updated backwards: SOL-2026-4 was published in Sep 2026 against code compiled since 0.7.2.

**Compiler bugs and real money.** The Solidity bugs above were all found by the team, researchers or bounty hunters, and the bug posts do not report known exploits. The best-known compiler incident in the EVM world is in a different compiler: Vyper versions 0.2.15, 0.2.16 and 0.3.0 had a broken `@nonreentrant` lock, and several Curve pools compiled with them were drained on 30 Jul 2023 (tens of millions of dollars). The pattern applies to Solidity too: the source looked correct, the audit read the source, and the bug lived in the bytecode. See [[5.13 Toolchain, dependencies and operations]] and [[5.14 Case studies]].

**Pipeline switching is a compiler upgrade too.** Moving a codebase from legacy to via-IR with the *same* version changes almost every byte, changes gas, changes which bugs apply (compare the two 0.8.28 exposure lists above), and can change behaviour where the code relied on unspecified evaluation order or on the legacy memory layout of inline assembly. Treat it with the same process as a version bump ([[3.11 Compiler IR and the optimizer]]).

> [!info]- Deep dive: changes in 0.8.37 that are not in `bugs.json`
> Some fixes appear only in the changelog's ordinary "Bugfixes" list, not as known bugs. Two in 0.8.37 can still change behaviour:
> - "Fix constants read in both checked and `unchecked` contexts within one contract getting the checked/unchecked semantics of whichever read was generated first via IR, which could remove a required overflow panic or introduce a spurious one."
> - "Fix uninitialized internal function pointers being read from a packed storage slot with the wrong value when a subsequent variable in the slot holds a non-zero value."
>
> And in 0.8.37 the Yul optimizer stopped wrongly removing a `returndatacopy()` that refers to a stale `returndatasize()`. When you review an upgrade, read the whole changelog section for every version you skip, not only the "Important Bugfixes" heading and `bugs.json`.

## Question ladder

> [!question]- **I** Which of these features would you adopt in a new codebase today, and which carry risk?
> Start from 0.8.38 (the only 0.8.x release with no known bugs), pin it, and pin `evmVersion` to the oldest fork on any target chain. Then sort features into three groups.
>
> **Adopt freely (old, widely used, no open bugs):**
> - Checked arithmetic (0.8.0), with `unchecked` only where you can prove the bound ([[2.9 Arithmetic and numeric pitfalls]]).
> - Custom errors (0.8.4) instead of revert strings: smaller code, cheaper reverts, typed data ([[2.8 Errors and reverts]]).
> - `abi.encodeCall` (0.8.11) instead of `abi.encodeWithSelector`: the compiler checks the argument types.
> - User-defined value types (0.8.8) for units like `Price`, `Shares`, `Timestamp`, and their operators (0.8.19) ([[2.1 Types]]). Zero runtime cost, real type safety.
> - `string.concat`/`bytes.concat`, file-level events and errors, named mapping parameters, relaxed immutables (0.8.21). All ergonomic, no codegen risk.
> - `require(cond, CustomError(...))` (0.8.26/0.8.27), with positional arguments. The named-argument form was miscompiled via IR until 0.8.37; fixed now, but positional arguments avoid the whole class.
>
> **Adopt with care (powerful, newer, had bugs):**
> - **`transient` state variables (0.8.28).** Great for reentrancy locks and per-transaction context. But: a high-severity via-IR clearing bug until 0.8.34; transient slots are numbered from 0 and do not move with `layout at`, so a proxy and its implementation share them; and the SIR.trading exploit (Mar 2025, about $355K) came from one transient slot reused for two meanings. Keep transient state minimal, one meaning per slot, and test `delete` on it ([[5.11 New attack surfaces - transient storage, EIP-7702, account abstraction]]).
> - **`layout at` and `erc7201()` (0.8.29, 0.8.35).** Good for namespaced or relocated storage in upgradeable systems. But the feature is young: a medium inheritance-order bug until 0.8.36, the base must be a compile-time constant, only the most-derived contract can carry it, and tooling (storage-layout diff tools, upgrade plugins) must understand it. Verify the layout output yourself ([[2.3 Storage layout]], [[4.2 Upgradeability and proxies]]).
> - **Via-IR.** Often smaller and cheaper code and fewer "stack too deep" errors. But most 2026 compiler bugs were via-IR-only, compilation is slower, and it changes behaviour in edge cases. If you adopt it, adopt it from the start, run the full test suite on the via-IR build you deploy, and consider differential tests against a legacy build.
> - **`assembly ("memory-safe")`.** Required for via-IR to move variables around your assembly. It is a promise to the compiler. A wrong promise is a silent memory corruption, not a compile error ([[3.5 Memory management in assembly]]).
>
> **Avoid or plan to remove (deprecated in 0.8.x):** `send`/`transfer`, ABI coder v1, virtual modifiers, comparing contract-type variables directly, the `memory-safe-assembly` comment, `selfdestruct`, `block.difficulty`, and identifiers that will become keywords (`layout`, `at`, `transient`, `error`, …). Also avoid anything that needs `settings.experimental` (the `amsterdam` target, `block.slotnum`, SSA CFG codegen) in production: Glamsterdam has no mainnet date and experimental features have no stability promise.
>
> What an interviewer listens for: you tie each feature to a version, you know that "new" correlates with "recent bugs", and you separate the *language* risk (semantics you might misuse) from the *compiler* risk (bytecode that does not match the source).

> [!question]- **A** How do you decide whether to upgrade the compiler for an audited codebase?
> Frame it as a trade-off. The audited bytecode is a known quantity. A new compiler gives new bytecode that nobody has audited, in exchange for bug fixes, gas savings or features. The answer depends on whether the code is already deployed and immutable, upgradeable, or not yet deployed.
>
> **1. Is the current build exposed to a known bug?** Read the exact settings of every contract (version, optimizer, runs, via-IR, `evmVersion`, coder) from the build metadata, not the pragma. Run the `bugs.json` / `bugs_by_version.json` check per contract and per pipeline, then read each matching `description` and search the code for the trigger. Example: a via-IR 0.8.30 build that `delete`s a transient variable and also pops a storage array matches TransientStorageClearingHelperCollision (high). A legacy 0.8.30 build of the same code does not match that bug, but matches the legacy `bytes` delete bug if it uses `delete` on `bytes memory` elements. If nothing applies, "no upgrade" is a valid answer for code that is already deployed and immutable.
>
> **2. Remember the support policy.** The security policy says: "As a general rule, only the latest release gets security updates." There are no 0.8.30.1 patch releases. If a bug in your version matters, the fix is "move to the latest", which pulls in every other change since your version. That is why the decision is about the whole jump, not one fix.
>
> **3. Measure the jump.** For the candidate version, compile with the same settings and produce:
> - **Changelog diff.** Read every section between the two versions, including ordinary bug fixes (some, like the 0.8.37 checked/unchecked constant fix, can change behaviour without a `bugs.json` entry). Note default changes: if you did not pin `evmVersion`, a jump across 0.8.20/0.8.25/0.8.30/0.8.31 silently changes the target.
> - **Bytecode diff** per contract (runtime and creation, metadata stripped). Expect differences. The point is to know *which* contracts and functions changed, and why (target, optimizer sequence, codegen change). A contract whose bytecode is identical after stripping metadata needs no further review.
> - **Storage layout diff** (`storageLayout` and `transientStorageLayout`) for every upgradeable contract. Layout should not change with a compiler upgrade; UserDefinedValueTypesBug (0.8.8 → 0.8.9) is the precedent that it can.
> - **Gas snapshot diff** (`forge snapshot --diff`). Big changes point at codegen changes worth reading. Small uniform drops are usually `PUSH0`, loop increments or optimizer sequence changes. Check that nothing relies on exact gas (hard-coded gas stipends, `gasleft()` thresholds).
> - **Code size** against the 24,576-byte limit; via-IR and new optimizer sequences can move a contract over or under it.
>
> **4. Re-run everything on the new bytecode.** Unit, fuzz and invariant suites, fork tests against mainnet state, and any formal specs ([[6.2 Unit, fuzz and invariant testing]], [[6.5 Formal verification]]). A suite that passes on both compilers is necessary but not sufficient, because tests encode expectations you wrote against the old build.
>
> **5. Differential testing old vs new.** Deploy both builds side by side (or on two forks) and drive them with the same random call sequences, comparing return data, revert data, events and storage after each call. Any difference is either an intended codegen change or a bug in one compiler. I reproduced two 2026 bugs this way above: the same source returned `0100000000` vs `0100030405`, and `(have=10, need=3)` vs `(3, 10)`. Differential fuzzing is the only routine technique that catches "the source is right but the bytecode is wrong".
>
> **6. Scope a partial re-audit.** Auditors reviewed source plus a compiler. With a new compiler, re-review: functions whose bytecode changed in non-trivial ways; inline assembly (especially `memory-safe` blocks, since optimizer bugs often live there); code touching features with recent bugs (transient, `layout at`, recursion under via-IR, `bytes` memory manipulation); anything relying on evaluation order or exact gas. Pure target-driven differences (`PUSH0`, `MCOPY`) usually need only a test-backed sign-off. Give the auditors the bytecode diff, the gas diff, the layout diff and the bug-exposure table; it turns a full re-audit into a scoped one.
>
> **7. Deployment and verification.** New bytecode means new verification. Publish the exact compiler version and settings to Sourcify/Etherscan; verify that the deployed runtime code matches your build (CBOR tail shows the version). For proxies, upgrade the implementation through the normal timelock or governance path, and re-check storage layout against the live proxy's storage, not only against the previous source. For immutable deployed code, a compiler bug that applies is not fixed by recompiling: it means a migration, or a mitigation (pausing the affected path, an external guard). That is a governance decision, not a build decision.
>
> **Decision rule.** Upgrade when (a) a known bug applies to your build and settings, (b) you need a feature or target (for example `transient`, `cancun` opcodes, a chain's new fork), or (c) you are about to deploy new code anyway and the bump is cheap to review. Do not upgrade an immutable, audited, unaffected system just to be on the latest version. When you upgrade, jump to the latest release (that is the only one that gets fixes) and pin it.
>
> What separates an expert answer: per-contract, per-pipeline bug matching; knowing that only the latest release is patched; bytecode, layout and gas diffs as the inputs to scoping; differential testing; and the distinction between "recompile" (upgradeable or undeployed code) and "migrate" (immutable code).
