# 2.1 Types

> [!abstract] In one minute
> - **Value types** (integers, `address`, `bool`, `bytesN`, enums, user-defined value types, function types) are copied on every assignment and fit in one 32-byte word (an external function takes two stack slots). **Reference types** (arrays, `bytes`, `string`, structs, mappings) carry a data location and can alias. See [[2.2 Data locations]].
> - Narrow types still live in a full 256-bit word. The compiler keeps the unused high bits "clean" (mask with `AND`, sign-extend with `SIGNEXTEND`). The legacy pipeline cleans **lazily**, just before an operation the bits could affect; via-IR cleans **eagerly** after each operation. Inline assembly sees whatever is on the stack.
> - `address payable` exists so that you must say on purpose that an address may receive Ether. Since 0.8.0 `msg.sender`, `tx.origin` and `address(x)` are plain `address`; use `payable(x)`.
> - Enums are always one byte (more than 256 members is a compile error since 0.8.0). A bad integer→enum conversion, a bad enum in storage, or a bad enum being ABI-encoded raises **`Panic(0x21)`**. A bad enum in **calldata** is rejected by the ABI decoder with an **empty revert**.
> - **User-defined value types** (`type Price is uint128;`, 0.8.8) are zero-cost wrappers with no operators. Since 0.8.19 you can bind pure free functions as operators: `using {add as +} for Price global;`.
> - Number literals are **arbitrary-precision rationals** (up to 4,096 bits) until they meet a non-literal type, so `2**800 / 2**799` is the constant 2. There is no usable fixed-point type: `fixed`/`ufixed` parse but cannot be assigned.

**Prerequisites:** [[1.3 Execution model]], [[1.5 Storage and transient storage]] · **Leads to:** [[2.2 Data locations]], [[2.3 Storage layout]], [[2.5 ABI encoding and decoding]], [[2.9 Arithmetic and numeric pitfalls]], [[3.9 Cleanup, dirty bits and safety]]

Everything in this note was checked with solc-js 0.8.38 (default EVM version `osaka`, optimizer on, 200 runs, both pipelines where it matters) and by running the bytecode in py-evm 0.12.1b1 with Prague rules. Gas figures are execution gas only: they leave out the 21,000 intrinsic cost and calldata.

## The type system at a glance

The EVM has one data type: the 256-bit word ([[1.3 Execution model]]). Every Solidity type is a rule for how to interpret a word, or a group of words, and which operations are allowed on it. That is the whole idea of this note. A `uint8` is a word whose top 248 bits must be zero. An `int8` is a word whose top 248 bits must copy bit 7. An `address` is a word whose top 96 bits must be zero. A `bytes4` is a word whose **low** 224 bits must be zero, because fixed bytes are left-aligned.

Solidity splits types into two families.

| Family | Members | Assignment | Where it can live |
|---|---|---|---|
| Value types | `bool`, `intN`/`uintN`, `address`, `address payable`, `bytes1`…`bytes32`, enums, user-defined value types, function types, (unusable) `fixedMxN`/`ufixedMxN` | Always copies the value | Stack, memory, storage, transient storage, calldata |
| Reference types | `T[]`, `T[k]`, `bytes`, `string`, structs, `mapping` | Copies or creates a reference, depending on data location | Must state `memory`, `storage` or `calldata` (except state variables) |

Two consequences matter in practice:

- **A value type has no identity.** Passing a `uint256` to a function can never let the callee change the caller's copy. A `storage` struct reference can. The rules for when references alias and when they copy are in [[2.2 Data locations]].
- **Value types are the only types that fit in transient storage, in immutables and in user-defined value types.** Transient state variables only support value types today (since 0.8.28, [[1.5 Storage and transient storage]]). An immutable must be a value type. A UDVT's underlying type must be an elementary value type; `type Ref is bytes;` fails with "The underlying type of the user defined value type "Ref" is not a value type."

Sizes and defaults for the value types, as reported by the compiler's `storageLayout` output:

| Type | Bytes in storage | Default | ABI type | Valid word |
|---|---|---|---|---|
| `uintN` (N = 8…256, step 8) | N/8 | 0 | `uintN` | top 256−N bits zero |
| `intN` | N/8 | 0 | `intN` | top bits equal bit N−1 (sign-extended) |
| `address`, `address payable` | 20 | `address(0)` | `address` | top 96 bits zero |
| `bool` | 1 | `false` | `bool` | 0 or 1 |
| `bytesN` (N = 1…32) | N | all zero | `bytesN` | low 256−8N bits zero |
| `enum E` | 1 | first member (0) | `uint8` | 0 … (members − 1) |
| `type T is U` | same as `U` | `U`'s default | `U` | same as `U` |
| external function | 24 | zero (calls revert with empty data: address 0 has no code) | `function` (24 bytes) | address ‖ selector, then 8 zero bytes |
| internal function | 8 | zero (calls `Panic(0x51)`) | not allowed in ABI | pipeline-specific |

## Integers

`uint8` through `uint256` and `int8` through `int256` come in steps of 8 bits. `uint` and `int` are aliases for the 256-bit versions. Signed integers are two's complement, so `int8(-1)` is the byte `0xff`, and in a full word it is `0xff…ff` after sign extension.

Since 0.8.0 the arithmetic operators `+ - * / % **` and unary `-` are checked. Overflow raises `Panic(0x11)`, division or modulo by zero raises `Panic(0x12)`. Shifts, bitwise operators and explicit conversions are **never** checked. An `unchecked { }` block turns the arithmetic checks off. The full catalogue of numeric traps (rounding direction, `type(int256).min / -1`, shift semantics, exponent edge cases) belongs to [[2.9 Arithmetic and numeric pitfalls]].

`type(T).min` and `type(T).max` give the range of any integer type (since 0.6.8). Measured return values:

| Expression | Word returned |
|---|---|
| `type(int8).min` | `0xff…ff80` (−128, sign-extended) |
| `type(int8).max` | `0x…7f` (127) |
| `type(uint64).max` | `0x…ffffffffffffffff` |
| `type(int256).min` | `0x8000…0000` |

> [!tip] Narrow types do not save gas on the stack
> A local `uint8` costs the same stack slot as a `uint256` and may add masking instructions. Narrow types pay off only when they are **packed** next to each other in storage, in transient storage, or in a struct ([[2.3 Storage layout]]). For loop counters, function parameters and locals, use `uint256`.

## Addresses: `address` and `address payable`

An `address` holds a 20-byte account address. It has the members `balance`, `code`, `codehash`, and the low-level calls `call`, `delegatecall` and `staticcall` ([[1.7 Message calls and precompiles]]). `address payable` is the same 20 bytes plus two more members: `transfer` and `send`.

The documentation states the purpose in one sentence: "The idea behind this distinction is that `address payable` is an address you can send Ether to". A plain address might be a contract that was never built to receive Ether. Making the programmer write `payable(...)` turns "I want to pay this address" into an explicit decision that a reviewer can see.

Conversion rules, all checked against 0.8.38:

| From → To | Rule | Measured |
|---|---|---|
| `address payable` → `address` | Implicit | `return p;` compiles |
| `address` → `address payable` | Explicit `payable(a)` only | `p = a;` fails: "Type address is not implicitly convertible to expected type address payable." |
| `uint160` → `address payable` | Not allowed | "Explicit type conversion not allowed from "uint160" to "address payable"." Go through `payable(address(x))` |
| `uint160`, `bytes20`, integer literal → `address` | Explicit | `address(uint160(x))` |
| `address` → `uint256` | Not allowed in one step | "Explicit type conversion not allowed from "address" to "uint256"." Use `uint256(uint160(a))` |
| contract `C` → `address payable` | `payable(c)` only if `C` has `receive` or a payable `fallback` | Without one: "Explicit type conversion not allowed from "contract NoRecv" to "address payable"." |
| `payable(0)` | Allowed | The documented exception |

`a.transfer(1)` on a plain address fails with ""send" and "transfer" are only available for objects of type "address payable", not "address"."

How the rule evolved:

| Version | Change |
|---|---|
| 0.8.0 | `msg.sender` and `tx.origin` become `address` (no longer payable). `address(x)` always returns a non-payable `address`, including `address(this)` |
| 0.6.0 | `payable(x)` conversion added ("Allow explicit conversions from `address` to `address payable` via `payable(...)`") |
| 0.5.0 | `address payable` introduced. Only it has `transfer`. Conversion from `address` went through `uint160`. `msg.sender` was `address payable` |

**Address literals.** A 40-hex-digit literal must pass the EIP-55 mixed-case checksum to be typed as `address`. Writing it in lower case is a compile error that even gives you the fix:

```text
SyntaxError: This looks like an address but has an invalid checksum. Correct checksummed
address: "0x5B38Da6a701c568545dCfcB03FcB875f56beddC4". If this is not used as an address,
please prepend '00'.
```

> [!warning] `payable` is a type annotation, not a capability check
> `payable(x)` compiles to nothing. It does not check that `x` can receive Ether. `transfer` and `send` still forward only the 2,300-gas stipend, which smart wallets and EIP-7702 delegated accounts may not fit in ([[1.7 Message calls and precompiles]]). Prefer `(bool ok, ) = x.call{value: v}("")` plus reentrancy discipline ([[5.2 Reentrancy]]).

## Fixed-size bytes, `bytes` and `string`

`bytes1` … `bytes32` are value types holding 1 to 32 bytes. They are **left-aligned**: a `bytes2` holding `0x1234` is the word `0x1234000…0`. That is the opposite of integers, which are right-aligned. The alignment explains every conversion rule below: converting between `bytesN` sizes keeps the **left** bytes, and converting between integer sizes keeps the **right** (low-order) bits.

`bytesN` supports comparison, bitwise operators, shifts, index access `b[i]` (read-only, returns `bytes1`) and `.length` (a constant). The old alias `byte` for `bytes1` was removed in 0.8.0.

`bytes` and `string` are **dynamic reference types**. They are covered in [[2.2 Data locations]] and their storage encoding in [[2.3 Storage layout]]. The difference between them is only what the compiler lets you do:

| | `bytes32` | `bytes` | `string` |
|---|---|---|---|
| Kind | Value type, one word | Dynamic byte array | Dynamic byte array, intended for UTF-8 |
| `.length` | Constant 32 | Yes | No: "Member "length" not found…" Use `bytes(s).length` |
| Index `x[i]` | Yes (read) | Yes (read/write) | No: "Index access for string is not possible." |
| `==` | Yes | No | No: "Built-in binary operator == cannot be applied to types string memory and string memory." Compare `keccak256` hashes |
| Concatenation | Via `bytes.concat` | `bytes.concat` (0.8.4) | `string.concat` (0.8.12) |
| ABI encoding | Static, 32 bytes in the head | Offset + length + padded data | Same as `bytes` |
| Storage, short value | One slot | One slot if ≤ 31 bytes | One slot if ≤ 31 bytes |

Measured storage writes into fresh zero slots (execution gas only): `bytes32` "hello": 22,376. `string` "hello": 22,938. The short string fits in one slot as `68656c6c6f00…000a` (data in the high bytes, `length × 2` = 10 in the lowest byte). A 40-byte `bytes` took 67,344 gas: one length slot (`0x51` = 40 × 2 + 1) plus two data slots. The extra cost of the dynamic types is the copy loop and the length handling, not the slot count, until you pass 31 bytes.

## Booleans and enums

`bool` is one byte with values 0 and 1. `&&` and `||` short-circuit. A dirty bool (any nonzero word) is treated as `true` and normalized to 1 when it is stored or encoded: an assembly `x := 2` came back from the function as `1` in both pipelines.

An **enum** is a named set of constants numbered from 0. It is stored and ABI-encoded as `uint8`. The compiler output for a three-member enum:

```text
storageLayout:  s  slot 0  offset 0  t_enum(Status)  numberOfBytes 1
ABI:            echo(uint8)   internalType "enum Enums.Status"
```

An enum with exactly 256 members also takes 1 byte. An enum with 257 members does not compile: "DeclarationError: Enum with more than 256 members is not allowed." (0.8.0 changelog: "Type System: Disallow enums with more than 256 members.") So in current Solidity **an enum is always `uint8`**. Before 0.8.0 the integer type was "just large enough to hold all enum values" (0.7 docs), so a 257-member enum was a `uint16`; you will only meet that in old code.

`type(E).min` and `type(E).max` (since 0.8.8) return the first and last member. Enums convert explicitly to and from any unsigned integer type, never implicitly.

### Where invalid enum values are caught

An enum value outside the range 0 … members − 1 is the only case where the compiler **rejects** a bad narrow value instead of masking it. I tested every path with `enum Status { Pending, Active, Closed }`:

| Path | Code | Result (legacy and via-IR) |
|---|---|---|
| Integer → enum conversion | `Status(v)` with `v = 3`, `255`, `256` | Revert with `Panic(0x21)`: `4e487b71…21` |
| Integer → enum, in range | `Status(2)` | Returns 2 |
| Calldata parameter | `echo(Status st)` called with 3 or `2**256 − 1` | **Empty revert** (ABI decoder validation) |
| `abi.decode(data, (Status))` with 5 | memory decode | **Empty revert** |
| Storage load | slot holds 7, then `s()` getter, `s == Status.Closed` or `uint256(s)` | `Panic(0x21)` |
| ABI encoding of a return value | `assembly { st := 7 }`, then `return st` | `Panic(0x21)` |
| Literal → enum | `Status(3)` with a literal | Compile error if the literal is out of range (0.8.0 rule) |

So the answer to "conversion or decoding?" is: both, with **different** failure signals. Explicit conversion and every internal use raise `Panic(0x21)`. The ABI decoder, like all its validation failures, reverts with no data. A test that expects a `Panic(0x21)` from bad calldata will fail.

## User-defined value types

A **user-defined value type** (UDVT, since 0.8.8) gives an existing elementary value type a new name that the type checker treats as distinct:

```solidity
type Price is uint128;
```

The docs call it "a zero cost abstraction over an elementary value type". A `Price` has exactly the bits of a `uint128`, the same storage size (16 bytes, so two UDVTs pack into one slot), and the same ABI type (`uint128`, with `internalType` "Price"). What changes is what the compiler allows:

- `Price.wrap(uint128) → Price` and `Price.unwrap(Price) → uint128` are the **only** conversions. `Price(x)` fails with "Explicit type conversion not allowed from "uint128" to "Price"."
- There are **no operators** by default. `p + p` fails with "Built-in binary operator + cannot be applied to types Price and Price. No matching user-defined operator found."
- Two UDVTs over the same type do not mix. With `type Qty is uint128`, `p == q` fails with "…cannot be applied to types Price and Qty".

That last property is the point. Prices, quantities, token ids, timestamps and basis points are all `uint256` in raw Solidity, and mixing them up is a real bug class. A UDVT turns the bug into a compile error at no runtime cost. The external interface does not change, because the ABI only sees the underlying type. (Bug note: 0.8.8 gave every UDVT shorter than 32 bytes its own full storage slot; fixed in 0.8.9, `UserDefinedValueTypesBug`.)

### Attaching operators with `using … for … global` (0.8.19)

Since 0.8.19 you can bind operators to a UDVT with a file-level directive such as `using {add as +, sub as -, lt as <, eq as ==} for Price global;`, where `add`, `sub`, `lt` and `eq` are pure free functions in scope. A complete, compiling example is in [[#A typed price with operators]].

The rules, each checked by trying to break it:

| Rule | Error when broken |
|---|---|
| The function must be a **pure free function** (file-level). A `view` free function or a library function is rejected | "Only pure free functions can be used to define operators." |
| The directive must be `global` | "Operators can only be defined in a global 'using for' directive." |
| `global` needs a UDVT defined at file level in the same source unit | "Can only use "global" with types defined in the same source unit at file level." |
| Only these operators: `\| & ^ ~ + - * / % == != < > <= >=` | `++`: "Not a user-definable operator: ++. Only the following operators can be user-defined: …" |
| Compound assignment is not derived | `p += p`: "Operator += not compatible with types Price and Price." |
| Parameters and return use the UDVT; comparisons return `bool` | (type errors) |

`~` is unary, `-` can be unary and binary (separate definitions; a unary `neg as -` compiled and worked), the rest are binary. Functions in the same `using` list without an operator name become attached member functions, so `p.unwrapLib()` works. The operator function's own body decides checked or unchecked arithmetic. An `unchecked { r = a - b; }` around a user-defined `-` does **not** reach into the operator function: with `a = 1`, `b = 2` it still reverted with `Panic(0x11)`. Conversely, the Solidity blog notes that an operator body written with `unchecked` silently bypasses checks for every caller.

## Function types

A function type is a value that refers to a function. There are two kinds.

**Internal function types** refer to functions in the current contract's code (including inherited, library-internal and free functions). Calling one is a jump within the same code, with no new call frame. Internal is the default: `function(uint256) pure returns (uint256) f` is internal. They cannot cross a contract boundary, so they cannot appear in the ABI or in external function parameters.

**External function types** refer to a function on some contract by `(address, selector)`. Calling one is a real message call ([[1.7 Message calls and precompiles]]). They have the members `.address` and `.selector`, and you get one with `this.f` or `otherContract.g`. They are the way to pass a callback across contracts.

Conversions between function types require identical parameter and return types. State mutability may only get weaker: `pure` → `view` → non-payable, and `payable` → non-payable.

### Runtime representation of external function types

On the stack an external function value takes **two slots**: the address and the selector. In the via-IR output you can see the pair being combined only at the boundaries:

```yul
function combine_external_function_id(addr, selector) -> combined {
    combined := shift_left_64(or(shift_left_32(addr), and(selector, 0xffffffff)))
}
```

So the 24-byte value is `address (20 bytes) ‖ selector (4 bytes)`, and in a 32-byte word it is left-aligned like a `bytes24`, followed by 8 zero bytes. Measured with the contract at `0xdd…dd01` and `target(uint256)` (selector `0x9811c7c1`):

```text
abi.encode(this.target):     dddddddddddddddddddddddddddddddddddddd01 9811c7c1 0000000000000000
storage, slot 0 (24 bytes):  0000000000000000 dddddddddddddddddddddddddddddddddddddd01 9811c7c1
                             (8 bytes free)    address (high 20 of the 24)             selector
ABI signature:               callIt(function,uint256)   -> selector 0x331e29f0
storageLayout:               cb  slot 0 offset 0  numberOfBytes 24
```

In storage the value is right-aligned in its 24 bytes like any packed value, so an 8-byte variable can share the slot (the internal function pointer in the same test landed at offset 24). The ABI decoder validates the padding: passing the 24 bytes followed by `00…01` instead of eight zero bytes reverted with empty data in both pipelines.

### Runtime representation of internal function types

Here the two pipelines differ completely. The compiler docs ("Solidity IR-based Codegen Changes"):

- Legacy: "The old code generator uses code offsets or tags for values of internal function pointers." Calling the pointer is `JUMP` to that offset.
- via-IR: "In the new code generator, function pointers use internal IDs that are allocated in sequence. Since calls via jumps are not possible, calls through function pointers always have to use an internal dispatch function". "The ID `0` is reserved for uninitialized function pointers which then cause a panic in the dispatch function when called."

I confirmed both by pulling the raw pointer value out with assembly and by writing bad values into storage:

| Observation | Legacy | via-IR |
|---|---|---|
| Raw value of `double` / `triple` | `0x315` / `0x309` (code offsets; byte there is `0x5b` JUMPDEST) | `1` / `2` |
| Pointer assigned in the **constructor**, as stored | `0x00000034_000000c5`: creation-code tag in the upper 32 bits, runtime tag in the lower 32 | `1` |
| Pointer assigned at runtime, as stored | `0x000000d1` | `2` |
| Storage size | 8 bytes | 8 bytes |
| Stored value 0, then call | `Panic(0x51)` | `Panic(0x51)` |
| Stored value 3 (not a JUMPDEST), then call | Invalid jump, **all 100,000 gas consumed** | `Panic(0x51)` |
| Stored value 99 (`0x63`, happens to be a JUMPDEST), then call | **Returns success** with empty output after 630 gas: execution jumped into the middle of unrelated code | `Panic(0x51)` |

The constructor row is why legacy needs two tags. Constructor code and runtime code are different byte strings ([[1.8 Contract creation]]), so a function's offset differs between them. A pointer stored during construction must work both in the rest of the constructor and later at runtime, so the compiler packs both offsets into one value.

The via-IR dispatch function, from the unoptimized IR of the test contract:

```yul
function dispatch_internal_in_1_out_1(fun, in_0) -> out_0 {
    switch fun
    case 1 { out_0 := fun_double_29(in_0) }
    case 2 { out_0 := fun_triple_41(in_0) }
    default { panic_error_0x51() }
}
```

There is one such function per signature shape (number of inputs and outputs), listing every function whose address is taken with that shape.

> [!warning] Internal function pointers in storage are tied to the bytecode
> The docs warn that an internal function value "is an identifier that is strongly tied to contract's bytecode". Recompile, add a function, change the optimizer settings, switch pipelines, or upgrade a proxy implementation, and every stored pointer may now name a different function. Under legacy it may jump to a random JUMPDEST, as the 99 row shows. Never store internal function pointers in upgradeable contracts. Store an enum and `if`/`else` on it instead.

## Literals and constant expressions

Number literals are not `uint256`. Each has its own **rational constant type**, written `int_const 291` or `rational_const 5 / 2` in error messages. The docs: "Number literal expressions retain arbitrary precision until they are converted to a non-literal type", so "computations do not overflow and divisions do not truncate in number literal expressions."

The compiler evaluates the whole literal expression exactly, then converts the **final** value to a real type. Only that final value must fit. Measured in 0.8.38:

| Expression | Result |
|---|---|
| `uint256 constant C = 2**800 / 2**799;` | 2 |
| `(2**256 - 1) * 2 / 2` | `2**256 − 1` (the intermediate `2**257 − 2` is fine) |
| `1e18 * 3.5` | `3500000000000000000` (`0x30927f74c9de0000`) |
| `-3 >> 1` | −2 (literal shift rounds toward −∞) |
| `return 2**800;` into `uint256` | "Return argument type int_const 6668...(233 digits omitted)...7376 is not implicitly convertible to expected type … uint256. Literal is too large to fit in uint256." |
| `return 7 / 2;` into `uint256` | "Return argument type rational_const 7 / 2 is not implicitly convertible to expected type … uint256." |
| `uint256 x = 2.5;` | "…rational_const 5 / 2 is not implicitly convertible to expected type uint256. Try converting to type ufixed8x1 or use an explicit conversion." |
| `1 / 0` | "Built-in binary operator / cannot be applied to types int_const 1 and int_const 0." |
| `2**2048` | Accepted. `2**2049` is rejected ("Built-in binary operator ** cannot be applied…") |
| a product reaching 4,097 bits | "Precision of rational constants is limited to 4096 bits." |

As soon as one operand is a typed value, the literal is converted to a real type first, and normal fixed-width, checked arithmetic applies:

- `x + 300` with `x` a `uint8` has type `uint16` (the smallest type holding 300), so returning it as `uint8` fails to compile.
- `a * 5 / 2` with a `uint256` compiles: it multiplies, then divides with truncation. The same literal `7 / 2` that is a compile error above returns 3 once the 7 sits in a `uint256` variable.
- `a * 2.5` fails: "Built-in binary operator * cannot be applied to types uint256 and rational_const 5 / 2."
- `~uint8(0) + 1` is typed, so it is a runtime `Panic(0x11)`, not a compile-time constant.

**Other literal forms.** Underscores separate digits (`1_000_000`). Scientific notation (`2e10`, `2.5e-1`) is allowed if the result is an integer by the time it is typed. Hex literals `0x…` are integers, and convert to `bytesN` only when they have exactly the right number of hex digits (or are zero): `bytes2 b = 0x123;` fails with "int_const 291 is not implicitly convertible to expected type … bytes2". Decimal literals never convert to `bytesN`. String literals (`"abc"`, `hex"0011"`, `unicode"…"`) convert implicitly to `bytesN`, `bytes` and `string`. Ether units (`1 ether`) and time units (`1 days`) are literal multipliers.

## Fixed-point numbers: declared but unusable

`fixedMxN` and `ufixedMxN` (M bits from 8 to 256, N decimals from 0 to 80; `fixed` = `fixed128x18`) are in the grammar. The docs: "Fixed point numbers are not fully supported by Solidity yet. They can be declared, but cannot be assigned to or from." In 0.8.38:

| Code | Result |
|---|---|
| `fixed x; x;` (local, never assigned) | Compiles (useless) |
| `fixed128x18 x = 1.5;` | "UnimplementedFeatureError: Not yet implemented - FixedPointType." |
| `fixed128x18 public x;` (state variable) | "UnimplementedFeatureError: Fixed point types not implemented." |

So all decimal math in Solidity is integer math with a scale you choose: 18-decimal "WAD", 27-decimal "RAY", Q64.96 in Uniswap v3, or a UDVT that wraps one of them (PRBMath's `UD60x18` is exactly this pattern). Rounding direction becomes your responsibility. See [[2.9 Arithmetic and numeric pitfalls]] and [[4.9 DeFi math and primitives]].

## Implicit and explicit conversions

**Implicit** conversion happens when it cannot lose information. Between integers that means the same signedness and a wider or equal width: `uint8 → uint16`, `int8 → int16`. A sign change is never implicit, even when the value would fit: `uint8 → int16` fails with "Type uint8 is not implicitly convertible to expected type int16." and `uint8 → int8` fails the same way. `bytesN → bytesM` is implicit for M ≥ N and pads on the right. `address payable → address` is implicit, and any contract converts implicitly to the contracts it inherits from.

**Explicit** conversion `T(x)` reinterprets or truncates. Since 0.8.0 one conversion may change **at most one** of sign, width or type category: "The conversion is only allowed when there is at most one change in sign, width or type-category". For an `int8 x`, `uint16(x)` must be written `uint16(uint8(x))` or `uint16(int16(x))`, and the order you choose changes the result: for `x = -1` the first gave 255 and the second 65,535. `int8 → uint16` directly fails with "Explicit type conversion not allowed from "int8" to "uint16"." Integers and `bytesN` convert only at the same size: `uint128(bytes32)` fails, `uint16(bytes2)` works.

Measured results (all compile with 0.8.38):

| Expression | Result | Rule |
|---|---|---|
| `uint8(uint16(0x1234))` | `0x34` | Integer narrowing keeps the **low-order** bits |
| `uint256(uint16(0x1234))` (implicit) | `0x1234` | Zero-extends |
| `uint8(int8(-1))` | 255 | Same width, sign change: same bits |
| `int16(int8(-1))` (implicit) | −1 (`0xff…ff`) | Sign-extends |
| `int8(int16(-129))` | 127 (`0x7f`) | Narrowing a signed value can flip its sign |
| `bytes1(bytes2(0x1234))` | `0x12` | Bytes narrowing keeps the **left** (high-order) bytes |
| `bytes4(bytes2(0x1234))` (implicit) | `0x12340000` | Pads on the right |
| `uint16(bytes2(0x1234))` | `0x1234` | Same size only |
| `uint32(uint16(bytes2(0x1234)))` | `0x00001234` | Integer first, then widen |
| `uint32(bytes4(bytes2(0x1234)))` | `0x12340000` | Bytes first, then reinterpret |
| `bytes20(a)` for an address | address in the 20 high bytes | Bytes view is left-aligned |
| `uint160(a)` for an address | address in the 20 low bytes | Integer view is right-aligned |

The two `uint32` rows are the classic trap: the same input and the same target type give different answers depending on the path. Explicit narrowing never reverts. If you want a checked downcast, use OpenZeppelin's `SafeCast` (`toUint128` reverts when the value does not fit) and see [[2.9 Arithmetic and numeric pitfalls]].

## Cleanup of narrow types

This is the bridge to [[3.9 Cleanup, dirty bits and safety]], which covers the topic in full. The short version follows.

A narrow value is **dirty** when its unused high bits are not what the type requires. Arithmetic can create dirty bits: `uint8(255) + 1` in `unchecked` computes 256 on the 256-bit EVM, `~a` sets all 248 high bits, `a << 1` can push a bit past position 7. Inline assembly can write any word into a narrow variable.

The compiler docs give the type table:

| Type | Valid values | Invalid values mean |
|---|---|---|
| enum of n members | 0 … n − 1 | Exception (`Panic(0x21)`) |
| `bool` | 0 or 1 | Treated as 1 |
| signed integers | Sign-extended word | Silently sign-extended ("may throw in future") |
| unsigned integers | High bits zero | Silently masked ("may throw in future") |

And the timing rule:

- **Legacy:** "The old code generator only performs cleanup before an operation whose result could be affected". Comparisons, division, storing to memory or storage, hashing and ABI encoding all clean first. Addition does not need to, because the low bits of a sum do not depend on dirty high bits.
- **via-IR:** "The new code generator performs cleanup after any operation that can result in dirty bits", and relies on the optimizer to remove the redundant cleanups.
- **Both:** reading a narrow Solidity variable inside inline assembly is not a cleanup point. The docs: the compiler does not guarantee such values are clean.
- **External input** is validated, not cleaned, under ABI coder v2 (the default since 0.8.0): a `uint8` parameter of `0x1ff` reverted with empty data in both pipelines.

Measured, with `uint8 x` set to `0x1ff` in assembly and then used in Solidity (identical in both pipelines, optimizer on or off):

| Use | Result | Why |
|---|---|---|
| `return x` | `0xff` | ABI encoding cleans |
| `x == 255` | `true` | Comparison cleans |
| `x + 1` (checked) | `Panic(0x11)` | Clean value is 255, so 256 overflows |
| `uint256(x)` | `0xff` | Widening cleans |
| `x / 2` | `0x7f` | Division cleans |
| `keccak256(abi.encodePacked(x))` | `keccak256(0xff)` = `0x8b1a944c…8db9` | Memory write cleans |
| `stored = x` (packed next to a `uint8` holding 7) | slot = `0x07ff` | Storage write masks; the neighbour survives |
| `assembly { r := x }` | `0x1ff` | **No cleanup: dirty bits visible** |

And with dirty bits created by Solidity arithmetic, read back in assembly:

| Code | Legacy | via-IR |
|---|---|---|
| `uint8 a = 255; unchecked { c = a + 1; }` then `assembly { r := c }` | `0x100` | `0x0` |
| same, `c == 0` in Solidity | `true` | `true` |
| `uint8 a = 0x81; c = a << 1;` then `assembly { r := c }` | `0x102` | `0x2` |
| docs example: `a = ~a` for `a = 1` | `0xff…fe` | `0xfe` |

The pattern is consistent. Solidity code never observes dirty bits. Assembly that reads Solidity variables can, but only under the legacy pipeline when the value came from an operation that left bits dirty, or under any pipeline when earlier assembly put them there.

## Solidity and Yul in practice

### A typed price with operators

This compiles with 0.8.38. Two UDVTs share one storage slot (`best` at offset 0, `size` at offset 16) exactly as two `uint128` would, and the ABI shows `improve(uint128)`.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

type Price is uint128;
type Qty is uint128;

using {add as +, sub as -, lt as <, eq as ==, unwrapLib} for Price global;

function add(Price a, Price b) pure returns (Price) { return Price.wrap(Price.unwrap(a) + Price.unwrap(b)); }
function sub(Price a, Price b) pure returns (Price) { return Price.wrap(Price.unwrap(a) - Price.unwrap(b)); }
function lt(Price a, Price b) pure returns (bool) { return Price.unwrap(a) < Price.unwrap(b); }
function eq(Price a, Price b) pure returns (bool) { return Price.unwrap(a) == Price.unwrap(b); }
function unwrapLib(Price a) pure returns (uint128) { return Price.unwrap(a); }

contract Book {
    Price public best;            // storage: same layout as uint128
    Qty public size;

    function improve(Price p) external returns (Price) {
        if (p < best || best == Price.wrap(0)) best = p;
        return best + Price.wrap(1);
    }

    function spread(Price ask, Price bid) external pure returns (uint128) {
        return (ask - bid).unwrapLib();       // checked: reverts if bid > ask
    }
}
```

Running it: `improve(100)`, `improve(150)`, `improve(90)` returned 101, 101 and 91. `spread(105, 100)` returned 5. `spread(100, 105)` reverted with `Panic(0x11)` because `sub` uses checked arithmetic. `improve(2**128)` reverted with empty data: the decoder validates the underlying `uint128` range.

### An external callback

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

contract Caller {
    // ABI type "function": 20-byte address + 4-byte selector, left-aligned in one word.
    function callIt(function(uint256) external returns (uint256) f, uint256 x) external returns (uint256) {
        return f(x);
    }
}

contract Target {
    function target(uint256 x) external pure returns (uint256) { return x + 1; }

    function viaCaller(Caller c) external returns (uint256) {
        return c.callIt(this.target, 41);   // passes (address(this), 0x9811c7c1)
    }

    function parts() external view returns (address, bytes4) {
        return (this.target.address, this.target.selector);
    }
}
```

`Target.viaCaller(caller)` returned 42. Calling `callIt` directly with calldata `0x331e29f0 ‖ <address ‖ 9811c7c1 ‖ 00×8> ‖ 41` also returned 42.

### A dirty mapping key in assembly

This is the shape of real dirty-bit bugs: hand-computed storage slots. It compiles in both pipelines, and its behavior differs between them.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

contract DirtyKey {
    mapping(uint8 => uint256) public credit;   // slot 0

    function seed() external { credit[0xfe] = 100; }

    // Reads credit[~a] by computing the mapping slot by hand.
    function readByHand(uint8 a) external view returns (uint256 v, uint256 rawKey) {
        uint8 k = ~a;                          // for a = 1, Solidity's value is 0xfe
        assembly {
            rawKey := k
            mstore(0x00, k)                    // BUG: k may carry dirty high bits
            mstore(0x20, credit.slot)
            v := sload(keccak256(0x00, 0x40))
        }
    }

    function readByHandSafe(uint8 a) external view returns (uint256 v) {
        uint8 k = ~a;
        assembly {
            mstore(0x00, and(k, 0xff))         // clean explicitly
            mstore(0x20, credit.slot)
            v := sload(keccak256(0x00, 0x40))
        }
    }
}
```

| Call, after `seed()` | Legacy | via-IR |
|---|---|---|
| `readByHand(1)` | `v = 0`, `rawKey = 0xff…fe` | `v = 100`, `rawKey = 0xfe` |
| `readByHandSafe(1)` | 100 | 100 |
| `credit(0xfe)` getter | 100 | 100 |

Under legacy the hash covers the dirty word, so the code reads an unrelated, empty slot. A write through the same path would credit a slot no getter can see. The fix is to mask (`and(k, 0xff)`) or sign-extend (`signextend(0, k)` for `int8`) every narrow value before it is hashed, compared or stored in assembly. Never rely on the pipeline to have done it.

### Enum conversion with a clear error

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

contract Orders {
    enum Status { Pending, Active, Closed }
    error BadStatus(uint256 raw);

    // Status(raw) alone would revert with Panic(0x21); a custom error is easier to debug.
    function toStatus(uint256 raw) public pure returns (Status) {
        if (raw > uint256(type(Status).max)) revert BadStatus(raw);
        return Status(raw);
    }
}
```

`toStatus(2)` returned 2. `toStatus(3)` reverted with `BadStatus(3)`: `0x4a5d4550` followed by the word 3.

## Pitfalls and incidents

- **Explicit narrowing is silent.** `uint128(x)` drops the high bits with no revert. Downcasts of amounts, timestamps and prices belong behind `SafeCast` or an explicit `require`. Many audit findings are a `uint96(amount)` or `uint32(block.timestamp)` that wraps.
- **Sign and width in two steps.** `uint32(uint16(b))` and `uint32(bytes4(b))` differ by a factor of 65,536 for the same `bytes2 b`. Write the intended path out and test it.
- **`payable()` is not a check.** It costs nothing and proves nothing. `transfer`/`send` keep the 2,300 stipend.
- **Enum errors are two different signals.** Calldata gives an empty revert, internal conversions give `Panic(0x21)`. Off-chain decoders and tests must expect the right one.
- **Enum ranges are part of storage.** Removing or reordering enum members in an upgrade makes stored values mean something else. Only append new members at the end, and remember a stored value above the new `max` would panic on read ([[5.9 Proxies, delegatecall and storage]]).
- **Internal function pointers in storage.** They are code offsets (legacy) or IDs (via-IR) and change with the bytecode. A bad legacy value can jump to an arbitrary JUMPDEST and return success.
- **`interfaceId` is not inherited.** `type(I).interfaceId` XORs only functions declared in `I`. An ERC-165 `supportsInterface` that should report a parent interface must list it separately ([[4.4 Token standards]]).
- **UDVT operators can hide unchecked math.** An operator body inside `unchecked` disables overflow checks for every user of the operator. Read the operator definitions when you audit a codebase that uses them.
- **Dirty bits in assembly.** Hashing, comparing or storing a narrow Solidity variable in assembly without masking it. Worst under the legacy pipeline after `~`, `<<` or `unchecked` arithmetic.

Compiler bugs in this area, from the official list of known bugs (newest fix first):

| Bug | Fixed in | Severity | What went wrong |
|---|---|---|---|
| AbiReencodingHeadOverflowWithStaticArrayCleanup | 0.8.16 | medium | Padding cleanup of a static calldata array in the last head slot overwrote up to 32 bytes of the tail |
| DirtyBytesArrayToStorage | 0.8.15 | low | Copying `bytes` to storage left dirty bytes after the end; a later `push()` did not yield zero |
| UserDefinedValueTypesBug | 0.8.9 | very low | UDVTs shorter than 32 bytes took a full storage slot each (introduced 0.8.8) |
| SignedImmutables | 0.8.9 | very low | Signed immutables shorter than 256 bits were zero-extended instead of sign-extended; visible only from assembly |
| DynamicArrayCleanup | 0.7.3 | medium | Shrinking a packed small-type storage array left stale bits that reappeared on regrowth |
| TupleAssignmentMultiStackSlotComponents | 0.6.6 | very low | Tuple assignments with two-slot components such as external function pointers produced invalid values |
| UninitializedFunctionPointerInConstructor | 0.5.8 | very low | Uninitialized internal function pointers created in the constructor did not always revert |
| ExpExponentCleanup | 0.4.25 | medium/high | A narrow exponent was not cleaned before `EXP` |
| HighOrderByteCleanStorage | 0.4.4 | high | High-order bytes of short types were not cleaned on storage writes, corrupting neighbouring variables |
| CleanBytesHigherOrderBits | 0.3.3 | medium/high | Short `bytesNN` were not cleaned before comparison |

## Question ladder

> [!question]- **B** Why is conversion from `address` to `address payable` explicit?
> Because receiving Ether is not something every address can safely do, and Solidity wants the decision to send Ether to be visible in the code. The docs: "The idea behind this distinction is that `address payable` is an address you can send Ether to". A plain `address` might be a contract with no `receive` or payable `fallback`. Sending to it reverts, and Ether forced in by other means (a `selfdestruct` beneficiary, a block's fee recipient) may be stuck there for good.
>
> Only `address payable` has `transfer` and `send`. So `a.transfer(1)` on a plain address fails to compile with ""send" and "transfer" are only available for objects of type "address payable"". Implicit `p = a` also fails ("Type address is not implicitly convertible to expected type address payable."). You must write `payable(a)`.
>
> Three details interviewers like:
> - Since 0.8.0, `msg.sender`, `tx.origin` and `address(x)` (including `address(this)`) are plain `address`. Withdraw functions need `payable(msg.sender).transfer(...)` or, better, a `call`.
> - `payable(c)` on a contract value compiles only if the contract has `receive` or a payable `fallback`. `uint160 → address payable` is not allowed in one step.
> - `payable(...)` is purely a compile-time annotation. It emits no code and does not check anything at runtime. The 2,300-gas stipend of `transfer`/`send` is the real compatibility risk, especially for smart wallets and EIP-7702 delegated EOAs.

> [!question]- **B** When do you use `bytes32`, `bytes` and `string`?
> - **`bytes32`** for fixed 32-byte data: hashes, Merkle roots, storage keys, short identifiers, packed flags, `keccak256` outputs, EIP-712 type hashes. It is a value type: one word on the stack, one slot in storage, static in the ABI (no offset or length). It supports `==`, bitwise operators and index reads. Use smaller `bytesN` (`bytes4` selectors, `bytes20` raw addresses) when the width is fixed and smaller.
> - **`bytes`** for arbitrary binary data of variable length: calldata payloads, signatures, encoded messages, bytecode. It has `.length`, read/write indexing and `bytes.concat`. Prefer it over `bytes1[]`, which pads each element to 32 bytes in memory.
> - **`string`** for human-readable UTF-8 text: names, symbols, URIs. It is the same bytes as `bytes`, minus features: no `.length`, no indexing, no `==` (all three are compile errors in 0.8.38). Use `bytes(s).length` (which counts bytes, not characters), `keccak256(bytes(a)) == keccak256(bytes(b))` for comparison, and `string.concat` to join.
>
> Cost: a 5-byte value costs about the same either way in storage, because short `bytes`/`string` (≤ 31 bytes) are stored in one slot with the length in the lowest byte. Measured: 22,376 gas for a fresh `bytes32` write, 22,938 for `string "hello"`. Above 31 bytes the dynamic types need a length slot plus `ceil(len / 32)` data slots (40 bytes took 67,344 gas). In the ABI, `bytes32` is one head word, while `bytes`/`string` cost an offset, a length and padded data ([[2.5 ABI encoding and decoding]]). Rule of thumb: if the length is fixed and at most 32, use `bytesN`.

> [!question]- **I** Why does `2**800 / 2**799` compile as a constant but fail with variables?
> Because number literals are not machine integers. Every literal and every expression made only of literals has a **rational constant type** that the compiler evaluates exactly, with arbitrary precision. `2**800` is a 241-digit integer; `2**800 / 2**799` is the exact rational 2. Only when the expression is finally converted to a real type (here the `uint256` constant) does the compiler check that the value fits. 2 fits, so `uint256 constant C = 2**800 / 2**799;` compiles and the bytecode just contains `2`.
>
> With variables, the expression is no longer a literal. `uint256 a = 2; a**800 / a**799` is compiled to runtime `EXP` and `DIV` on 256-bit words with 0.8 overflow checks. `a**800` overflows long before the division, so the call reverts with `Panic(0x11)` (measured: `4e487b71…11`).
>
> Consequences:
> - Intermediate literal results may be huge or fractional. `(2**256 - 1) * 2 / 2` is fine, `1e18 * 3.5` is an exact integer, `7 / 2` is the rational 3.5 and cannot become a `uint256` ("rational_const 7 / 2 is not implicitly convertible…").
> - Limits exist. Precision of rational constants is capped at 4,096 bits ("Precision of rational constants is limited to 4096 bits."), and in 0.8.38 `2**2048` is accepted while `2**2049` is rejected.
> - The boundary is the first typed operand. `x + 300` with a `uint8 x` converts 300 to `uint16` first, then does checked 16-bit math. Writing `uint256(1) * 7 / 2` gives 3, while `7 / 2 * 2` (all literals) is exactly 7.
> - A `constant` is not a literal once declared: `uint256 constant C` has type `uint256` wherever it is used, but the right-hand side that defines it is folded exactly. (`2**800 / 2**799` also works as an `immutable` initializer.)

> [!question]- **I** What do user-defined value types buy you, and how do you attach operators with `using ... for ... global`?
> **What they buy.** Type safety at zero runtime cost. `type Price is uint128;` creates a new type with the same bits, storage size, packing and ABI type as `uint128`, but the type checker keeps it separate. You cannot pass a `Qty` where a `Price` is expected, compare a `Price` with a `Qty`, or do arithmetic on a `Price` by accident. The only conversions are `Price.wrap(uint128)` and `Price.unwrap(Price)`, which compile to nothing. The ABI is unchanged (`improve(uint128)`), so integrators see no difference. Real uses: Uniswap v4's `Currency`, `PoolId` and `BalanceDelta`, PRBMath's `UD60x18`/`SD59x18` fixed-point types, and order books where price and size must never mix.
>
> **Attaching operators (0.8.19).** Write pure free functions at file level, then bind them in a global directive in the same file as the type:
>
> ```solidity
> // SPDX-License-Identifier: MIT
> pragma solidity 0.8.38;
>
> type Price is uint128;
> using {add as +, lt as <} for Price global;
>
> function add(Price a, Price b) pure returns (Price) { return Price.wrap(Price.unwrap(a) + Price.unwrap(b)); }
> function lt(Price a, Price b) pure returns (bool) { return Price.unwrap(a) < Price.unwrap(b); }
> ```
>
> Rules (each confirmed by its compile error): only pure free functions ("Only pure free functions can be used to define operators." also rejects library functions and `view` functions); only in a `global` directive; `global` only for a file-level UDVT in the same source unit; only the operators `| & ^ ~ + - * / % == != < > <= >=`; `-` may be defined unary and binary; comparison operators return `bool`; `+=` and `++` are not derived. `global` means the binding follows the type into every file that imports it, so users cannot forget the `using`.
>
> What to watch: the operator body decides checked vs unchecked arithmetic, not the call site. An `unchecked { a - b }` around a user-defined `-` still reverted with `Panic(0x11)` when the body was checked, and a body written in `unchecked` removes the checks for everyone. Each operator use compiles to an internal function call, which the optimizer may inline.

> [!question]- **A** How are internal and external function types represented at runtime?
> **External** function types are a pair `(address, selector)`. On the stack they take two slots. When encoded or stored they become 24 bytes: address followed by selector. In the ABI the type is `function`, encoded left-aligned like `bytes24` with 8 zero bytes of padding. Measured: `abi.encode(this.target)` gave `dd…dd01 9811c7c1 0000000000000000`. In storage the 24 bytes are right-aligned in the slot like any packed value (`0000000000000000 dd…dd01 9811c7c1`), so an 8-byte value can share the slot. The decoder rejects nonzero padding with an empty revert. Calling one is a normal external `CALL` to `.address` with `.selector`.
>
> **Internal** function types depend on the pipeline:
>
> | | Legacy | via-IR |
> |---|---|---|
> | Value | Code offset of the function's JUMPDEST (`0x315`, `0x309` in my test) | Sequential ID (`1`, `2`) |
> | Call | `JUMP` to the value | `dispatch_internal_in_N_out_M(fun, …)`: a `switch` over IDs |
> | Assigned in constructor | Two offsets packed: creation tag in bits 32–63, runtime tag in bits 0–31 (`0x00000034_000000c5`) | Same ID as at runtime |
> | Uninitialized (0) | Points to a special panic function: `Panic(0x51)` | `default` branch: `Panic(0x51)` |
> | Garbage value | Jumps there: invalid JUMPDEST burns all gas; a valid one (99) **returned success** | `Panic(0x51)` |
> | Storage | 8 bytes | 8 bytes |
>
> The constructor packing exists because initcode and runtime code are different byte strings, so the same function has different offsets in each. The via-IR design exists because Yul has no dynamic jumps; the dispatch switch is also what lets the optimizer see every possible target.
>
> What an interviewer listens for: that internal pointers are bytecode-specific, so storing them is unsafe across upgrades or recompiles (the docs say the value "is an identifier that is strongly tied to contract's bytecode"), that only external function types can cross contract boundaries or appear in the ABI, and that under legacy a corrupted pointer is a control-flow hijack primitive rather than a clean revert.

> [!question]- **A** What happens when an out-of-range integer is converted to an enum?
> An explicit conversion `Status(v)` checks the range at runtime. With `enum Status { Pending, Active, Closed }`, `Status(3)`, `Status(255)` and `Status(256)` all reverted with `Panic(0x21)` (`0x4e487b71` followed by the word `0x21`), in both pipelines. The panic used about 371 gas; a valid conversion returned normally. A literal out of range, `Status(3)` written as a constant, is a compile error since 0.8.0.
>
> The same `Panic(0x21)` appears whenever the compiler meets an invalid enum value internally: loading one from storage (I wrote 7 into the slot with assembly; the getter, a comparison and `uint256(s)` all panicked) and ABI-encoding one (an assembly-assigned 7 returned from a function panicked).
>
> ABI **decoding** is different. A calldata parameter of enum type with value 3 or `2**256 − 1`, and `abi.decode(data, (Status))` with 5, both reverted with **empty returndata**, because the ABI decoder's validation failures revert with no data. So the answer to "on conversion or on decoding?" is: both are checked, but conversion gives `Panic(0x21)` and decoding gives a plain empty revert.
>
> History: before 0.8.0 the range check was a "failing assert" (0.7 docs), which compiled to `INVALID` and consumed all gas. 0.8.0 turned assert-style failures into `Panic` codes and capped enums at 256 members, so the type is always `uint8`; the 257th member is a compile error. (The 0.7 docs used `uint16` for enums with more than 256 values.)
>
> Practical advice: when converting user-supplied numbers, check against `type(Status).max` first and revert with a custom error that carries the bad value. When upgrading, only append enum members, since stored values are raw numbers.

> [!question]- **E** When can dirty higher-order bits in a narrow type leak into results, and where does the compiler clean them?
> **What dirty means.** A `uint8` is a 256-bit word that should have its top 248 bits zero; an `int8` should have them copy bit 7; an `address` should have its top 96 bits zero; a `bytes4` should have its low 28 bytes zero. The EVM does not know any of this, so any 256-bit operation can produce a word that violates it.
>
> **Sources of dirty bits.**
> 1. Wrapping arithmetic: `unchecked { uint8 c = a + 1; }` with `a = 255` leaves 256 on the stack.
> 2. Operators that are never checked: `~a` sets all high bits; `a << 1` can push bit 7 into bit 8.
> 3. Inline assembly assigning to a narrow variable: `x := 0x1ff`, or `calldataload`/`mload`/`sload` results assigned without masking.
> 4. Historically, compiler bugs (HighOrderByteCleanStorage, CleanBytesHigherOrderBits, ExpExponentCleanup, DynamicArrayCleanup, DirtyBytesArrayToStorage, SignedImmutables; see the table above).
>
> **Where the compiler cleans.** It cleans before every operation whose result depends on the high bits: comparisons, division and modulo, right shifts, widening conversions, writes to memory, writes to storage (masking so that packed neighbours survive), hashing and ABI encoding, `EXP` exponents, and conditionals that would branch differently. It skips cleanup where the low bits are unaffected (addition, multiplication, left shift) and where any nonzero works (`JUMPI` conditions). External input is validated, not cleaned: under ABI coder v2 a `uint8` argument of `0x1ff` reverts with empty data. Invalid enums panic; dirty bools become 1; dirty integers are masked or sign-extended. The legacy pipeline does all of this lazily, at the point of use. Via-IR cleans right after each operation that can dirty, and leaves it to the optimizer to drop redundant masks.
>
> **Where it leaks.** Pure Solidity never observes dirty bits; I could not produce a wrong result from Solidity code alone in 0.8.38. Every leak goes through inline assembly:
> - Reading a Solidity variable in assembly is **not** a cleanup point. Under legacy, `unchecked { c = 255 + 1 }` then `r := c` gave `0x100`, `c = 0x81 << 1` gave `0x102`, and the docs' `~1` example gives `0xff…fe`. Under via-IR the same code gave `0`, `2` and `0xfe`. So assembly is pipeline-dependent unless it masks.
> - Values written by assembly are cleaned once Solidity uses them (`return x`, `x == 255`, `x / 2`, `stored = x` all saw `0xff`), but **not** when other assembly reads them (`r := x` returned `0x1ff`).
> - The dangerous combinations are assembly that hashes (`keccak256` for mapping slots, signatures, Merkle leaves), compares (`eq`, `lt`, `gt`, `iszero`), divides, or writes full words to memory or storage. In my `DirtyKey` test, a hand-computed mapping slot from `~a` read slot `keccak256(0xff…fe ‖ 0)` under legacy (value 0) instead of `keccak256(0xfe ‖ 0)` (value 100). A write through that path would create a balance no getter can see.
> - Hand-written `mstore` of a narrow value into a Solidity memory array, then `abi.encode` of the array, is cleaned on encode, but `keccak256` over that memory in assembly is not.
>
> **Defenses an interviewer listens for.**
> - In assembly, treat every narrow input as dirty: `and(x, 0xff)` for `uint8`, `and(a, 0xffffffffffffffffffffffffffffffffffffffff)` for `address`, `signextend(0, x)` for `int8`, `and(b, shl(224, 0xffffffff))` for `bytes4`. Clean narrow outputs before assigning them back.
> - Prefer `uint256`/`bytes32` at the Solidity–assembly boundary so there is nothing to clean.
> - Do not depend on the pipeline: code that is correct under via-IR may be wrong under legacy, and the docs warn the cleanup points are not guaranteed.
> - Test with dirty inputs on purpose, under both pipelines and optimizer settings, and fuzz the assembly against a pure-Solidity reference ([[6.2 Unit, fuzz and invariant testing]]).
> - Know the gas trade-off: via-IR's eager cleanup adds `AND`/`SIGNEXTEND` instructions that the optimizer must remove; legacy saves them but makes assembly fragile. A mask costs 3 gas (`AND`) or 5 gas (`SIGNEXTEND`), so correctness wins.
>
> The full treatment, including calldata and memory cases and the opcode-level patterns, is in [[3.9 Cleanup, dirty bits and safety]].
