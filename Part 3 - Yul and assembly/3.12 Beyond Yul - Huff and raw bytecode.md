# 3.12 Beyond Yul - Huff and raw bytecode

> [!abstract] In one minute
> - **Huff** is a macro assembler for the EVM. You write opcodes and manage the stack yourself. It adds named constants, macros, jump labels, jump tables, code tables and `__FUNC_SIG`. Yul hides the stack behind variables and only allows structured control flow; Huff gives you both back. The maintained compiler in Nov 2026 is **huff-neo (`hnc`) 1.7.1** (24 Oct 2026). The original `huff-rs` is deprecated, and its planned successor `huff2` was discontinued.
> - The **EIP-1167 minimal proxy** is 45 bytes: `363d3d373d3d3d363d73 <impl> 5af43d82803e903d91602b57fd5bf3`. It copies calldata, `DELEGATECALL`s a fixed address with all gas, copies returndata, and returns or reverts. It uses `RETURNDATASIZE` as a 2-gas "push zero", which is valid only before the first call. The 10-byte deployer `3d602d80600a3d3981f3` returns it. In my py-evm runs a clone cost **9,035 gas** to create (plus the 32,000 base), against 147,436 for the full implementation, and added **2,666 gas** per call (2,600 of it is the cold `DELEGATECALL` target).
> - **PUSH0 variants** save a few gas per call. ERC-7511 (still **Draft**) is 44 bytes and saved 5 gas per call; Solady's `clone_PUSH0` is 45 bytes and saved 8. Solady's default `clone` is the 44-byte "0age" variant without PUSH0 (4 gas). Different bytes mean different code hashes, so explorers and on-chain checks must know each variant.
> - Hand-written bytecode pays only where **exact bytes matter** (proxies, deployers, factories that other tools recognise by hash) or the hot path is tiny and called millions of times (MEV, precompile-like math). For normal contracts the saving is small: my Huff `SimpleStore` saved 152 gas on a 22,309-gas write against Solidity, and standalone Yul matched Huff exactly.
> - **Verification**: Sourcify verifies Solidity, Vyper, Yul (since Jan 2026) and Fe (since Mar 2026); Etherscan and `forge verify-contract` take Solidity and Vyper. **No explorer compiles Huff.** Trust in custom bytecode comes from reproducible builds (pinned compiler, exact command, expected hash), on-chain `codehash` checks, Etherscan's 1167 clone detection and "Similar Match", and audits.
> - Glamsterdam's **EIP-8024** (`DUPN` `0xe6`, `SWAPN` `0xe7`, `EXCHANGE` `0xe8`, each with a one-byte immediate) is **scheduled**. It lifts the 16-deep stack limit for hand-written code. `hnc -e amsterdam` already emits it.

**Prerequisites:** [[1.8 Contract creation]], [[1.7 Message calls and precompiles]], [[3.3 Opcodes by family]], [[3.10 Yul objects and standalone contracts]] · **Leads to:** [[4.2 Upgradeability and proxies]], [[4.3 Deterministic and cross-chain deployment]], [[4.10 Gas optimization]], [[6.7 Deployment and verification]]

All measurements in this note: solc-js 0.8.38 (optimizer on, runs 200, `evmVersion` prague), huff-neo `hnc` 1.7.1 (prebuilt Linux release, `rev 2fe1d0c9`), run in py-evm with **Prague** rules. Gas is **execution gas** only. It excludes the 21,000 intrinsic gas and calldata cost, and for deployments the 32,000 creation charge and the initcode word cost. Every call is its own transaction, so accounts and slots start cold.

## Intuition: three ways to say the same thing

Yul already took away Solidity's dispatcher, ABI decoder, checked arithmetic and free memory pointer ([[3.10 Yul objects and standalone contracts]]). What is left between you and the bytes?

Two things. First, **variables**. In Yul you write `let x := add(a, b)` and the compiler decides where `x` lives on the stack and which `DUP`/`SWAP` fetches it. Second, **structured control flow**. Yul has `if`, `switch`, `for` and functions, but no labels and no `JUMP` ([[3.2 Syntax and control flow]]). The compiler places every jump destination.

Huff removes both. There are no variables: the stack *is* your state, and you write `dup2` yourself. There are no `if` blocks: you write `label jumpi` and put `label:` where you want. Raw bytecode removes the last layer, the assembler. You count byte offsets by hand.

Think of it like a camera:

| Level | You decide | The tool decides |
|---|---|---|
| Solidity | Logic and types | Everything else: dispatch, ABI, memory, stack, layout, checks |
| Yul (standalone) | Every opcode's arguments, memory layout, calldata parsing | Stack slots for variables, jump placement, `PUSH` widths, constant folding and inlining (optimizer) |
| Huff | Stack order, every `DUP`/`SWAP`, jump labels, jump tables, byte placement of tables | Label offsets, `PUSH` widths, macro expansion, constructor bootstrap |
| Raw hex | Every byte | Nothing |

The lower you go, the fewer tools can help. No type checker, no stack checker, no optimizer, no source verification. That is the price. This note shows where paying it makes sense, and how to get the result trusted afterwards.

## Huff: a macro assembler for the stack machine

### State of the compiler in November 2026

Huff was written by the Aztec team for Weierstrudel, an elliptic-curve library that neither Solidity nor Yul could make cheap enough. The community Rust compiler `huff-rs` (`huffc`) became the standard. Its story since then:

| Project | Binary | State on 1 Nov 2026 | Evidence |
|---|---|---|---|
| **huff-neo** (`cakevm/huff-neo`) | `hnc` | **Maintained.** 1.7.1 released 24 Oct 2026; 1.6.0–1.7.1 all in Oct 2026. Supports Osaka (`CLZ`) and `-e amsterdam` (`SLOTNUM`, `DUPN`/`SWAPN`/`EXCHANGE`, EIP-7954 size limits). Test runner on Foundry's executor. | Repo tags and CHANGELOG; I ran the 1.7.1 binary |
| huff2 (`huff-language/huff2`) | `huff2` | **Discontinued** (huff-neo's README and docs say so). Last commit 15 Mar 2026; its own README still lists jump tables as missing. | Repo history |
| huff-rs (`huff-language/huff-rs`) | `huffc` | **Deprecated, unmaintained.** The README banner says so; the last commit (30 Sep 2026) only removed links to the old `huff.sh` domain. | Repo README |

`hnc` is a drop-in replacement for `huffc` with real fixes. The one that matters most for safety is in 1.3.0 (12 Aug 2025): before it, **labels were not scoped per macro invocation**, so if a macro containing a label was invoked twice, "all jumps [would] target the last label definition". Code compiled with old `huffc` that invokes a labelled macro twice deserves a second look.

> [!note] How I installed it
> Huff compilers are not on crates.io (`cargo search huff` finds only Huffman-coding crates), and building huff-neo from source pulls Foundry as a git dependency. The prebuilt release worked: `hnc-v1.7.1-x86_64-unknown-linux-gnu.tar.gz` from the GitHub release, as the `hnc-up` installer does. `hnc --version` printed `hnc 1.7.1 (rev: 2fe1d0c9)`. Every Huff snippet in this note was compiled with it.

### The language in six ideas

1. **Opcodes are words.** `0x04 calldataload` pushes 4 and then runs `CALLDATALOAD`. A hex literal becomes the smallest `PUSHn`. `0x00` becomes `PUSH0` when the target is Shanghai or later (the default target is `osaka`); with `-e paris` it becomes `PUSH1 0x00`.
2. **Macros are inlined.** `#define macro NAME(args) = takes (n) returns (m) { … }` pastes its body wherever you write `NAME()`. `takes`/`returns` are **documentation only**: `hnc` does not check them (see the pitfall below). `#define fn` makes a jump-in, jump-out subroutine instead; it saves size and costs gas.
3. **`MAIN` and `CONSTRUCTOR`.** `MAIN` is the runtime entry point. If `CONSTRUCTOR` does not `RETURN` itself, `hnc` adds a 9-byte bootstrap that copies `MAIN` out of the initcode and returns it.
4. **Labels and jumps.** `name:` emits a `JUMPDEST`. Writing `name` pushes its offset, so `name jumpi` is a conditional jump. Offsets are `PUSH2` by default; `--relax-jumps` shrinks them to `PUSH1` where they fit.
5. **Constants and builtins.** `#define constant X = 0x…` is used as `[X]`. `FREE_STORAGE_POINTER()` hands out slot numbers 0, 1, 2… at compile time. `__FUNC_SIG(setValue)` or `__FUNC_SIG("transfer(address,uint256)")` is a 4-byte selector, `__EVENT_HASH` a topic, `__ERROR` a custom-error selector. huff-neo adds compile-time `for` and `if`, arithmetic in constants and `__ASSERT_PC`.
6. **Tables.** `#define jumptable` stores label offsets as 32-byte words (`jumptable__packed`: 2 bytes each); `#define table` stores raw bytes. `__tablestart(T)` and `__tablesize(T)` let you `codecopy` them. A jump table turns a selector switch into one `MLOAD` and one `JUMP`.

### A complete Huff contract

A store with `setValue(uint256)` and `getValue()`. Comments in square brackets show the stack, top first, which is the Huff convention.

```huff
/* Interface */
#define function setValue(uint256) nonpayable returns ()
#define function getValue() view returns (uint256)

/* Storage slots */
#define constant VALUE_SLOT = FREE_STORAGE_POINTER()

/* Methods */
#define macro SET_VALUE() = takes (0) returns (0) {
    0x04 calldataload       // [value]
    [VALUE_SLOT]            // [slot, value]
    sstore                  // []
    stop
}

#define macro GET_VALUE() = takes (0) returns (0) {
    [VALUE_SLOT] sload      // [value]
    0x00 mstore             // []          memory[0x00..0x20) = value
    0x20 0x00 return
}

#define macro MAIN() = takes (0) returns (0) {
    callvalue reverts jumpi            // non-payable: revert if msg.value != 0

    0x00 calldataload 0xe0 shr         // [selector]
    dup1 __FUNC_SIG(setValue) eq set jumpi
    dup1 __FUNC_SIG(getValue) eq get jumpi

    reverts:                           // unknown selector or value sent
        0x00 dup1 revert

    set:
        SET_VALUE()
    get:
        GET_VALUE()
}
```

`hnc SimpleStore.huff -b --relax-jumps` printed the initcode:

```text
6031 80 6009 3d 39 3d f3 | 34601d575f3560e01c80635524107714602157806320965255146028575b5f80fd5b6004355f55005b5f545f5260205ff3
^ bootstrap (9 bytes)      ^ MAIN = runtime (49 bytes)
```

The bootstrap is `PUSH1 0x31, DUP1, PUSH1 0x09, RETURNDATASIZE, CODECOPY, RETURNDATASIZE, RETURN`. It copies 0x31 = 49 bytes from code offset 9 to memory 0 and returns them, using `RETURNDATASIZE` for zero (still 2 gas and 1 byte, the same as `PUSH0`). Compare solc's version of the same idea in [[1.8 Contract creation]]: `600180600a5f395ff3fe00`.

The runtime, disassembled:

Three things to notice. The selector is left on the stack when a branch is taken; nobody cleans it up, and nobody needs to, because the call ends. `set` ends in `STOP`, so it cannot fall through into `get`. And `hnc -l` prints the label table (`reverts 0x20`, `set 0x24`, `get 0x2b` without `--relax-jumps`, where each label push is a 3-byte `PUSH2`), which is how you check offsets when debugging.

I deployed it next to the same contract in Solidity (both pipelines) and in standalone Yul (a `switch` on the selector, same logic), and called each:

| Version | Runtime bytes | `setValue` 0→42 | `setValue` 42→43 | `getValue` | Value sent | Unknown selector | `setValue` with no argument |
|---|---|---|---|---|---|---|---|
| Huff (`hnc` 1.7.1, `--relax-jumps`) | 49 | 22,157 | 5,057 | 2,186 | reverts | reverts | **succeeds, stores 0** |
| Standalone Yul (optimized) | 51 | 22,157 | 5,057 | 2,183 | reverts | reverts | **succeeds, stores 0** |
| Solidity 0.8.38 via-IR | 149 | 22,254 | 5,154 | 2,244 | reverts | reverts | reverts |
| Solidity 0.8.38 legacy | 165 | 22,309 | 5,209 | 2,244 | reverts | reverts | reverts |

The Solidity sizes include 53 bytes of CBOR metadata (`a264697066735822…0033`). The gas gap is 97–152 gas on a write, 58 on a read. That is what Solidity's calldata-length check, free-pointer setup and dispatcher cost here. The Yul version matched Huff on writes and beat it by 3 gas on reads: for the last `case` it compares the selector without duplicating it, one `DUP1` fewer than my Huff. That is the honest lesson of this table: **for straight-line code, standalone Yul already gets you Huff's bytecode**. Huff earns its keep when the stack layout across branches, a jump table, or an exact byte layout matters.

The last column is the cost of "no compiler help". Solidity rejects calldata shorter than the ABI requires. Neither the Huff nor the Yul version checks, so a call with only the selector stores zero ([[3.8 ABI, errors and events by hand]] covers the checks you would add).

### Seeing what Huff controls: one factory, three tools

Here is a small production-style job: a CREATE2 factory that deploys EIP-1167 clones of a fixed implementation (the clone bytes are explained in the next section). Calldata is a 32-byte salt; the function returns the clone address.

```huff
// CREATE2 factory for EIP-1167 clones of a fixed implementation.
// Calldata: a 32-byte salt. Returns the clone address as one ABI word.

#define constant IMPL = 0x0000000000000000000000000000000000000000   // set with -c IMPL=0x...
#define constant HEAD = 0x3d602d80600a3d3981f3363d3d373d3d3d363d73   // 1167 initcode + runtime head
#define constant TAIL = 0x5af43d82803e903d91602b57fd5bf3             // runtime tail

// Build the 55-byte clone initcode at memory [0x0c, 0x43).
#define macro BUILD_INITCODE() = takes (0) returns (0) {
    [TAIL] 0x23 mstore      // mem[0x34..0x43) = tail   (written first: later stores overlap its zero bytes)
    [IMPL] 0x14 mstore      // mem[0x20..0x34) = implementation
    [HEAD] 0x00 mstore      // mem[0x0c..0x20) = head
}

#define macro BUBBLE() = takes (0) returns (0) {
    returndatasize 0x00 0x00 returndatacopy
    returndatasize 0x00 revert
}

#define macro MAIN() = takes (0) returns (0) {
    BUILD_INITCODE()
    0x00 calldataload       // [salt]
    0x37 0x0c callvalue     // [value, offset, size, salt]
    create2                 // [clone]
    dup1 iszero fail jumpi  // [clone]
    0x00 mstore
    0x20 0x00 return
    fail:
        BUBBLE()
}
```

`hnc CloneFactory.huff -r --relax-jumps -c IMPL=0x2bda…2feb` produced 93 bytes. They were **byte-for-byte identical** to the version I assembled by hand below. Without `--relax-jumps` it was 94 bytes (a `PUSH2` for `fail`). The same logic as a standalone Yul object (`mstore`, `create2`, `if iszero(clone) { … }`) also compiled to 93 bytes, differing only in `PUSH0 DUP1` instead of `PUSH0 PUSH0` before `RETURNDATACOPY`.

So for this job all three tools converge. The differences show up elsewhere:

- **Yul cannot emit the clone's own runtime.** Those 45 bytes rely on `RETURNDATASIZE` as zero, on values left on the stack across the `DELEGATECALL`, and on a `JUMPI` whose fall-through is `REVERT`. Yul has no way to say "keep this zero on the stack for later" or "use `RETURNDATASIZE` here"; its code generator chooses. You would have to paste the bytes as data or `verbatim` ([[3.3 Opcodes by family]]).
- **Huff's `-c` flag sets a constant at build time.** That is a clean way to bake addresses into code without immutables. The Solidity equivalent needs an immutable patched by the constructor ([[1.8 Contract creation]]).
- **Huff never adds anything.** No metadata, no `0xfe` separator, no `memoryguard`. What you write is what ships.

## Raw bytecode: the EIP-1167 minimal proxy

[[1.8 Contract creation]] hand-wrote an initcode for a one-byte runtime. The classic real-world case of hand-written bytecode is the **minimal proxy**: a 45-byte contract that forwards every call to a fixed implementation with `DELEGATECALL`. EIP-1167 (Final, 2018) fixed the exact bytes so tools can recognise clones by pattern:

```text
363d3d373d3d3d363d73 bebebebebebebebebebebebebebebebebebebebe 5af43d82803e903d91602b57fd5bf3
|---- 10 bytes ----| |------------ implementation (20) -------| |---------- 15 bytes ---------|
```

Why so short? It has no dispatcher, no storage, no admin. It cannot be upgraded. Its only job is "run the implementation's code on my storage, give back whatever it returns". Factories deploy thousands of these (wallets, vaults, pools, NFT drops) at a fraction of a full deployment's cost. Upgradeable proxies are a different family ([[4.2 Upgradeability and proxies]]).

### Walking the runtime

The opcode-by-opcode walk-through is the intermediate question of the ladder below, with the full stack trace. In short:

1. `CALLDATACOPY(0, 0, CALLDATASIZE)` copies the whole calldata to memory 0. The two zeros come from `RETURNDATASIZE`, which is 0 because nothing has been called yet in this frame (EIP-211).
2. Push three more zeros and the calldata size, then the implementation address and `GAS`. Then `DELEGATECALL(gas, impl, 0, cds, 0, 0)`: forward all available gas (minus the 1/64 the EVM keeps back), input = memory `[0, cds)`, output size 0 (the proxy copies returndata later, because it does not know its size yet).
3. `RETURNDATACOPY(0, 0, rds)` copies the result over the calldata in memory.
4. Rearrange the stack to `[success, 0, rds]`, push `0x2b`, `JUMPI`. Success jumps to `JUMPDEST; RETURN(0, rds)`. Failure falls through to `REVERT(0, rds)`, so revert data bubbles up unchanged.

### The deployer: 10 bytes of initcode

A clone's initcode must return those 45 bytes. The common deployer (used by the 1167 reference implementation and OpenZeppelin's `Clones`) is `3d602d80600a3d3981f3`:

```text
pc  bytes  opcode           stack after (top first)        note
00  3d     RETURNDATASIZE   [0]                            0: no call yet in this frame
01  602d   PUSH1 0x2d       [45, 0]                        runtime length
03  80     DUP1             [45, 45, 0]
04  600a   PUSH1 0x0a       [10, 45, 45, 0]                runtime starts at code offset 10
06  3d     RETURNDATASIZE   [0, 10, 45, 45, 0]             destination 0
07  39     CODECOPY         [45, 0]                        memory[0..45) = code[10..55)
08  81     DUP2             [0, 45, 0]
09  f3     RETURN           (halts)                        return memory[0..45)
```

The leftover `0` on the stack does not matter: `RETURN` ends the frame. The whole initcode is 10 + 45 = 55 bytes. The deployer works for any runtime under 256 bytes if you change `0x2d` (length) and keep the offset `0x0a` equal to the deployer's own length. The PUSH0-era generic form is one byte shorter, `60LL 80 6009 5f 39 5f f3` (offset 9), which is what ERC-7511, Solady and my factory deployer below use. For a runtime of 256 bytes or more, the length needs `PUSH2`, the deployer grows by one byte, and the offset must grow with it. Getting that offset wrong is silent: `CODECOPY` zero-pads past the end of code, as [[1.8 Contract creation]] demonstrated.

### Deployed and tested in py-evm

I compiled an implementation in Solidity (`count`, `owner`, `init(address)` guarded by `require(owner == address(0), "initialized")`, `inc()`, `boom()` that reverts with `NotOwner(msg.sender)`, `echo(bytes)`, `whoami()`), deployed it at `0x2bda…2feb`, then deployed `3d602d80600a3d3981f3 ‖ 363d3d373d3d3d363d73 ‖ impl ‖ 5af43d82803e903d91602b57fd5bf3` as a separate contract. Results:

```text
create exec gas (incl. 200/byte deposit)   9,035      vs 147,436 for the 736-byte implementation itself
deployed code == expected 45 bytes         True
init(0x2222…) via clone                    success, 25,264 gas
init(0x3333…) again                        revert Error("initialized")
owner slot 1:  clone 0x2222…2222           implementation 0x0      (storage is the clone's)
inc() via clone -> 1 (25,091 gas), -> 2 (7,991 gas)
count slot 0:  clone 2                     implementation 0
whoami() -> (address(this) = clone address, msg.sender = original caller 0x1010…10)
```

`DELEGATECALL` keeps `msg.sender`, `msg.value` and `address(this)`, and all storage writes land in the clone ([[1.7 Message calls and precompiles]]).

### What a clone costs per call

| Call (execution gas, each its own tx) | Direct instance | Through EIP-1167 clone | Overhead |
|---|---|---|---|
| `count()` (view) | 2,283 | 4,949 | +2,666 |
| `inc()` (nonzero → nonzero) | 5,325 | 7,991 | +2,666 |

I counted the overhead opcode by opcode for `count()` (4 bytes of calldata, 32 bytes of returndata). It is exactly 2,666:

```text
CALLDATASIZE, 2x RETURNDATASIZE                    6
CALLDATACOPY 1 word (3 + 3) + memory 1 word (3)    9
3x RETURNDATASIZE, CALLDATASIZE, RETURNDATASIZE   10
PUSH20 3, GAS 2                                    5
DELEGATECALL to a cold address                  2,600
RETURNDATASIZE 2, DUP3 3, DUP1 3                   8
RETURNDATACOPY 1 word (3 + 3)                      6
SWAP1 3, RETURNDATASIZE 2, SWAP2 3, PUSH1 3       11
JUMPI 10, JUMPDEST 1, RETURN 0                    11
total                                           2,666
```

So 97.5 % of the overhead is the **cold account access** to the implementation (EIP-2929). The proxy's own instructions cost 66 gas plus memory. If the implementation is already warm in the transaction (for example, the user calls two clones of it), the access costs 100 instead. Hand-tuning the other 66 gas is what the PUSH0 variants below fight over.

## PUSH0 and the other minimal proxies

### Why 1167 uses `RETURNDATASIZE` at all

In 2018 the cheapest way to push zero was `RETURNDATASIZE` (1 byte, 2 gas), against `PUSH1 0` (2 bytes, 3 gas). It returns 0 only until the first call in the frame. The 1167 runtime pushes all its zeros **before** `DELEGATECALL` and then has to keep them on the stack and fetch them with `DUP3`, `DUP1`, `SWAP1`, `SWAP2` (3 gas each).

Shanghai's `PUSH0` (EIP-3855, 12 Apr 2023) is also 1 byte and 2 gas, but it gives zero **at any time**. A PUSH0 proxy can create zeros after the call instead of juggling old ones. The saving is small, a few gas, because the 2,600-gas cold access dominates.

### The variants side by side

I deployed all four in front of the same implementation and called `count()` and `inc()` through each:

| Variant | Status | Runtime (impl shown as `<a>`) | Bytes | Create gas | Per call vs 1167 |
|---|---|---|---|---|---|
| **EIP-1167** | Final (2018) | `363d3d373d3d3d363d73<a>5af43d82803e903d91602b57fd5bf3` | 45 | 9,035 | — |
| "0age" (Solady `clone`) | Library pattern | `3d3d3d3d363d3d37363d73<a>5af43d3d93803e602a57fd5bf3` | 44 | 8,832 | −4 |
| **ERC-7511** "Minimal Proxy Contract with PUSH0" | **Draft** since 4 Sep 2023 | `365f5f375f5f365f73<a>5af43d5f5f3e5f3d91602a57fd5bf3` | 44 | 8,832 | −5 |
| Solady `clone_PUSH0` | Library pattern | `5f5f365f5f37365f73<a>5af43d5f5f3e6029573d5ffd5b3d5ff3` | 45 | 9,032 | −8 |

Create gas is execution plus the 200-gas-per-byte deposit, so each byte saved at deploy time is about 200 gas. The 0age variant pushes four zeros up front, and after the call uses `RETURNDATASIZE RETURNDATASIZE SWAP4 DUP1` where 1167 uses `RETURNDATASIZE DUP3 DUP1 … SWAP1 RETURNDATASIZE SWAP2`. ERC-7511 replaces `DUP3` and `DUP1` after the call with two `PUSH0`s, replaces `SWAP1` with `PUSH0`, and pre-pushes only two zeros: −1, −1, −1, −2 = −5 gas, matching its own claim of "about 5 gas". Solady's PUSH0 variant optimises for runtime first: it rebuilds `(0, rds)` separately on the revert and the return paths, so it needs no swaps at all, at the cost of one extra byte.

> [!warning] Same idea, four code hashes
> A tool that recognises "a minimal proxy" by exact bytes recognises **one** of these. Solady exposes `CLONE_CODE_HASH` = `0x48db2cfd…eb1f` and `PUSH0_CLONE_CODE_HASH` = `0x67bc6bde…89dc` (hash of the runtime with a zero implementation address). I recomputed both and they match. EIP-1167 was standardised precisely so explorers could detect clones; a nonstandard variant may show up as unverified bytecode on an explorer that only knows 1167. Solady's source comments say its 0age and PUSH0 clones are "automatically verified on Etherscan"; I could not check that claim from here.

> [!warning] PUSH0 needs Shanghai on the target chain
> `0x5f` is an invalid opcode before Shanghai. With a PUSH0 deployer (ERC-7511's and Solady's both use `PUSH0`), creation itself fails there. With a pre-Shanghai deployer such as `3d602d80600a3d3981f3`, the PUSH0 runtime deploys fine (the deposit does not check opcodes) and then **fails every call**, consuming all forwarded gas. Solady names these functions with a "jarring" `_PUSH0` suffix for this reason. Check the chain before using them. The same applies to code compiled with solc ≥ 0.8.20 for the default target ([[1.11 Hard forks that changed contract code]]).

Solady 0.1.26's `LibClone` ships hand-written bytecode for several proxy shapes. Each one is a constant byte string in the library, with its stack trace in a comment block:

## A CREATE2 clone factory in raw bytecode

The Huff factory above, assembled by hand. The trick is to build the 55-byte clone initcode in memory with three `MSTORE`s, written **back to front** so that each store's leading zeros land on bytes that the next store overwrites:

```text
memory after the three stores (offsets in hex)
0x00 .. 0x0c   zeros (never read)
0x0c .. 0x20   3d602d80600a3d3981f3 363d3d373d3d3d363d73   head: deployer (10) + runtime head (10)
0x20 .. 0x34   <implementation, 20 bytes>
0x34 .. 0x43   5af43d82803e903d91602b57fd5bf3             runtime tail (15)
initcode = memory[0x0c .. 0x43), length 0x37 = 55
```

`MSTORE(0x23, tail)` writes the word `0x23..0x43`; the 15-byte tail is right-aligned, so it lands at `0x34..0x43`, and `0x23..0x34` become zero. `MSTORE(0x14, impl)` then writes `0x14..0x34` with the address at `0x20..0x34`. `MSTORE(0x00, head)` writes `0x00..0x20` with the head at `0x0c..0x20`. This is exactly the layout Solady and OpenZeppelin build in their Solidity assembly.

```text

0013  73 <impl 20 bytes>                             PUSH20 impl          [impl]
0028  6014                                           PUSH1 0x14           [0x14, impl]

002b  73 3d602d80600a3d3981f3363d3d373d3d3d363d73    PUSH20 head          [head]
```

The compiled Solidity equivalent, which also offers address prediction and an on-chain "is this one of my clones?" check, is in [[#Solidity and Yul in practice]]. > The keyless "Arachnid" deterministic deployment proxy at `0x4e59b44847b379578588920cA78FbF26c0B4956C` is hand-written bytecode that takes `salt ‖ initcode` and runs `CREATE2`. EIP-7997, which would make it a predeploy, is **scheduled** for Glamsterdam. ## EIP-8024: deeper stack access (scheduled)

Hand-written code lives on the stack, and the stack has a reach of 16: `DUP1`–`DUP16` and `SWAP1`–`SWAP16` are the only ways to touch items. Anything deeper must first be spilled to memory. Solidity hits the same wall as "stack too deep"; via-IR works around it by moving variables to memory ([[3.11 Compiler IR and the optimizer]]). Huff has no such mover: you redesign the macro.

EIP-8024 "Backward Compatible SWAPN, DUPN, EXCHANGE" is **scheduled** for Glamsterdam (EIP-7773 lists it; it is in Last Call with a deadline of 1 Nov 2026). Each instruction is 2 bytes, an opcode plus a one-byte immediate, and costs 3 gas:

| Instruction | Opcode | Operands | Effect | Immediate encoding |
|---|---|---|---|---|
| `DUPN n` | `0xe6` | 17 ≤ n ≤ 235 | Push a copy of the n-th item | `(n + 111) mod 256` |
| `SWAPN n` | `0xe7` | 17 ≤ n ≤ 235 | Swap top with the (n+1)-th item | `(n + 111) mod 256` |
| `EXCHANGE n m` | `0xe8` | 1 ≤ n < m, n + m ≤ 30 | Swap the (n+1)-th and (m+1)-th items | `(16q + r) xor 143`, with (q, r) from the EIP |

The odd encoding has a reason. The EVM decides which bytes are valid `JUMPDEST`s by scanning code and skipping `PUSH` immediates. If the new opcodes' immediates were skipped too, existing contracts that contain `0xe6 0x5b` would lose a jump target. So the EIP leaves **jumpdest analysis unchanged** and simply forbids immediates that look like `JUMPDEST` (`0x5b`) or `PUSH1`–`PUSH32` (`0x60`–`0x7f`): `DUPN`/`SWAPN` immediates 91–127 and `EXCHANGE` immediates 82–127 halt.

`hnc 1.7.1` already supports it with `-e amsterdam`:

```huff
#define macro MAIN() = takes (0) returns (0) {
    for(i in 0..17) { <i> }   // push 0..16: 17 items
    dupn 17                   // copy the 17th item (the first value pushed, 0) to the top
    swapn 17
    exchange 1 2
    dupn 235
}
```

```text
hnc Deep.huff -r -e amsterdam
5f 6001 6002 … 6010   e680   e780   e88e   e65a
                      dupn17 swapn17 exch1,2 dupn235
hnc Deep.huff -r -e osaka
Error: Opcode 'dupn' requires EVM version 'amsterdam' or later (current version: 'osaka')
```

I checked the immediates against the EIP's `encode_single`/`encode_pair`: 17 → `0x80`, 235 → `0x5a`, (1, 2) → `0x8e`. py-evm (Prague rules) cannot execute these opcodes, so the run above is a compile check only. Solidity 0.8.38 warns that `dupn`, `swapn` and `exchange` become reserved identifiers from the Amsterdam EVM version ([[3.3 Opcodes by family]]).

Why it matters for hand-written code: a Huff macro that needs 20 live values today must park some in memory (`MSTORE` 3 gas + `MLOAD` 3 gas + `PUSH`es, plus expansion). With `DUPN` the same access is one 3-gas instruction. It also changes **disassembly**: a tool that does not know EIP-8024 shows `e6 80` as `INVALID, DUP1`. Upgrade your disassemblers and debuggers before reading Amsterdam-era bytecode.

## Getting custom bytecode verified and trusted

### What verification actually checks

Source verification answers one question: **does compiling this source with these settings give the bytes at this address?** The verifier recompiles and compares the runtime (and, if it has the creation transaction, the creation code). It masks the parts that legitimately differ: immutable values, linked library addresses, constructor arguments appended to the initcode, and (for a weaker match) the metadata hash.

Verification says nothing about whether the code is *correct*. It only removes the "is the source I am reading the code that runs?" question. For hand-written bytecode, that question is the whole problem, because there is often no source a verifier understands.

### Who supports what (checked Nov 2026)

| Verifier | Languages | Notes |
|---|---|---|
| **Sourcify** (server 4.2.0, 21 Oct 2026) | Solidity, Vyper, **Yul** (since server 3.9.0, 7 Jan 2026), **Fe** (since 3.12.0, 30 Mar 2026) | Two levels: **exact_match** (bytecode and metadata hash identical, so the sources are byte-identical) and **match** (identical except the metadata hash), formerly "perfect" and "partial". A similarity endpoint (`/v2/verify/similarity`, since 3.8.0, 19 Nov 2025) tries previously verified compilations whose bytecode matches. Its lookup API reports `proxyResolution`. |
| **Etherscan** | Solidity (single file, multi-part, standard JSON), Vyper | **EIP-1167 clones** inherit the implementation's source and ABI if they use the standard bytes (announced Aug 2019). **"Similar Match Source Code"** labels an unverified contract whose bytecode matches a verified one. Etherscan itself warns the heuristic "is not foolproof" and that different constructor arguments can change behaviour. |
| **Blockscout** | Solidity, Vyper; can import Sourcify results | Same model |
| **`forge verify-contract`** | `--language solidity` or `vyper` | Verifiers: etherscan, sourcify, blockscout, oklink, custom (Etherscan-compatible API) |
| Huff, ETK, raw hex | **None** | No verifier ships a Huff compiler |

### The playbook for Huff and raw bytecode

1. **Use a standard pattern when one exists.** The exact EIP-1167 bytes get automatic treatment on Etherscan and are recognised by every proxy-detection library. A 3-gas-cheaper custom proxy loses that. This is the strongest argument for boring bytes.
2. **Verify everything that can be verified.** The implementation behind a clone, the factory if it is written in Solidity or Yul, and any Yul helper. Users then only have to trust the small unverified part.
3. **Make the build reproducible.** Publish the source at a tagged commit, the exact compiler (`hnc 1.7.1`, with the release binary's SHA-256), the exact command and flags (`--relax-jumps`, `-e`, every `-c` constant), and the expected `keccak256` of runtime and initcode. Add a CI job that rebuilds and compares against `cast code <address>` on every chain. Anyone can then reproduce the hash in a minute.
4. **Pin the code hash on-chain.** A factory can expose `isClone(a)` by comparing `a.codehash` with the expected hash (the Solidity below does this), and integrators can check `codehash` before trusting an address. EIP-1167's motivation is exactly this: "tooling can interrogate the bytecode at a redirecting address".
5. **Publish an ABI.** `hnc -g` generates a Solidity interface from the `#define function` lines. Without an ABI, explorers and wallets cannot decode calls even when users trust the code.
6. **Prove equivalence.** Write a Solidity reference, then differential-fuzz the Huff against it (same outputs, reverts, logs, storage for random inputs: [[6.2 Unit, fuzz and invariant testing]]) or prove it with symbolic execution ([[6.5 Formal verification]]). huff-neo's test runner runs on Foundry's executor, so `forge`-style fuzzing is available.
7. **Get it audited by hash.** The audit report should name the commit, the compiler and the runtime hash, so "audited" can be checked against what is deployed.

> [!warning] A "verified" wrapper around opaque bytes proves nothing
> Since Sourcify accepts Yul, you can wrap any bytecode in a Yul object: `object "X" { code { datacopy(0, dataoffset("runtime"), datasize("runtime")) return(0, datasize("runtime")) } data "runtime" hex"34601d57…" }`. I compiled exactly that around the Huff `SimpleStore` runtime with solc 0.8.38; it deployed `603180600a5f395ff3fe` followed by the 49 Huff bytes, and the deployed code equalled the Huff runtime. A verifier would accept a runtime match. But the "source" a reader sees is the same hex string. Treat such a badge as "the bytes are published", not as "the logic is reviewed".

## Solidity and Yul in practice

### A CREATE2 clone factory with on-chain recognition

The Solidity counterpart of the raw factory. It adds address prediction and an `isClone` check by code hash, which is what integrators should call before trusting an instance.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

/// Deploys EIP-1167 clones with CREATE2 and recognises them on-chain.
contract CloneFactory1167 {
    address public immutable implementation;

    error DeploymentFailed();

    constructor(address impl) {
        implementation = impl;
    }

    /// The 55-byte initcode: 10-byte deployer + 45-byte runtime.
    function initCode() public view returns (bytes memory) {
        return abi.encodePacked(
            hex"3d602d80600a3d3981f3363d3d373d3d3d363d73",
            implementation,
            hex"5af43d82803e903d91602b57fd5bf3"
        );
    }

    function clone(bytes32 salt) external payable returns (address instance) {
        bytes memory code = initCode();
        assembly ("memory-safe") {
            instance := create2(callvalue(), add(code, 0x20), mload(code), salt)
        }
        if (instance == address(0)) revert DeploymentFailed();
    }

    function predict(bytes32 salt) external view returns (address) {
        bytes32 h = keccak256(abi.encodePacked(bytes1(0xff), address(this), salt, keccak256(initCode())));
        return address(uint160(uint256(h)));
    }

    /// True if `a` runs exactly the 45-byte EIP-1167 runtime pointing at `implementation`.
    function isClone(address a) external view returns (bool) {
        bytes memory expected = abi.encodePacked(
            hex"363d3d373d3d3d363d73", implementation, hex"5af43d82803e903d91602b57fd5bf3"
        );
        return a.codehash == keccak256(expected);
    }
}
```

Tested in both pipelines against the same implementation:

```text
                     legacy                                 via-IR
predict(7)           0x384eb5ff…1aba                        0x51975fe8…0564   (different factory addresses)
clone(7)             same address, 41,620 gas               same address, 41,538 gas
clone(7) again       revert 0x30116425 DeploymentFailed()   same; 984,967 / 984,925 of a 1,000,000 gas limit
isClone(clone)       true                                    true
isClone(impl)        false                                   false
inc() via the clone  1                                       1
```

Two details. The collision case reverts with the custom error, but it still burned almost the whole gas limit inside `CREATE2` first. And the `abi.encodePacked` of a `bytes` literal plus an `address` plus another literal is exactly the 55 bytes the raw factory built with three `MSTORE`s; it just costs about 500 more gas to build.

### Reading the implementation out of a clone

Sometimes you only have an address and want to know whether it is a standard clone, and of what. `EXTCODECOPY` the 45 bytes and check the fixed parts:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

/// Reads the implementation out of an EIP-1167 clone, or returns address(0).
library CloneInspector {
    function implementationOf(address a) internal view returns (address impl) {
        assembly ("memory-safe") {
            if eq(extcodesize(a), 45) {
                // Copy the 45 bytes to free memory (temporary use, not allocated).
                let m := mload(0x40)
                extcodecopy(a, m, 0, 45)
                let head := shr(176, mload(m))              // first 10 bytes
                let tail := shr(136, mload(add(m, 30)))     // last 15 bytes
                if and(eq(head, 0x363d3d373d3d3d363d73), eq(tail, 0x5af43d82803e903d91602b57fd5bf3)) {
                    impl := shr(96, mload(add(m, 10)))     // bytes 10..29
                }
            }
        }
    }
}

contract Probe {
    function implementationOf(address a) external view returns (address) {
        return CloneInspector.implementationOf(a);
    }
}
```

Results: a 1167 clone returned its implementation `0x2bda…2feb` (3,204 gas legacy, 3,076 via-IR). An ERC-7511 clone of the same implementation, the implementation itself and an EOA all returned `address(0)`. That second result is the point of the earlier warning: the PUSH0 variant is a different pattern, and a 1167 detector does not see it. The shifts are the usual "left-aligned bytes in a word" arithmetic: 10 bytes = 80 bits, so `shr(256 − 80 = 176, …)`; 15 bytes → `shr(136, …)`; an address at byte 10 → `shr(96, mload(m + 10))` ([[3.5 Memory management in assembly]]). Writing above the free pointer without bumping it is allowed under `memory-safe` for temporary data.

## Pitfalls and incidents

**Huff does not check `takes`/`returns`.** This compiles without a warning:

```huff
#define macro LIAR() = takes (0) returns (5) {
    0x01                    // pushes one item, claims five
}
#define macro MAIN() = takes (0) returns (0) {
    LIAR() pop pop          // second pop underflows at runtime
    stop
}
```

`hnc` emitted `6001505000`. Run in py-evm with 100,000 gas: `InsufficientStack('Wanted 1 stack item, had none')`, all 100,000 gas consumed. A stack underflow is an exceptional halt. The only defences are stack comments on every line, tests that reach every path, and review.

**Old `huffc` label scoping.** Before huff-neo 1.3.0 (12 Aug 2025), invoking the same labelled macro twice made every jump go to the last copy's label. Recompile old Huff with `hnc` and diff the bytecode; if it changes, find out why.

**No safety nets by default.** Measured above: the Huff and Yul `SimpleStore` accepted a call with no argument and stored 0. Nothing checks `msg.value`, calldata length, dirty address bits or overflow unless you write it ([[3.9 Cleanup, dirty bits and safety]] has the checklist).

**`RETURNDATASIZE` is zero only until the first call.** Copying the 1167 trick into code that runs after a `CALL` pushes the previous call's returndata size, not zero. Use `PUSH0` on Shanghai+ chains.

**`CODECOPY` and jump offsets are silent.** A wrong `CODECOPY` offset zero-pads ([[1.8 Contract creation]]). A jump to an address that is not a `JUMPDEST`, or to a `0x5b` byte inside `PUSH` data, halts. Recount offsets after every edit, or let an assembler do it.

**A clone of nothing.** I deployed a 1167 clone pointing at an address with no code and called `inc()`: success, **zero bytes returned**, 2,663 gas. `DELEGATECALL` to an empty account succeeds. A Solidity caller using the interface reverted (it tried to decode a `uint256` from empty returndata), but a low-level caller, or a function with no return value, would think it worked. OpenZeppelin's `Clones` says so in a WARNING: it "does not check if `implementation` has code".

**Uninitialised implementations and clones.** A clone has no constructor; it is set up by an `initialize` call. If the factory deploys and initialises in separate transactions, anyone can initialise first. The implementation contract itself must also be locked (OpenZeppelin's `_disableInitializers()` in its constructor). [[5.3 Access control and initialization]] covers this in depth.

**CREATE2 collisions burn gas.** A raw factory without a pre-check spent 29,531,784 gas on a collision in my test.

**PUSH0 and new opcodes per chain.** PUSH0 code fails before Shanghai, `CLZ` before Osaka, `DUPN` before Amsterdam. Hand-written bytecode has no compiler target setting to remind you; record the minimum fork in the README.

| Date | Incident | Lesson for hand-written proxies |
|---|---|---|
| 12 Aug 2025 | huff-neo 1.3.0 fixes label scoping across macro invocations (compiler fix, no known exploit) | Assemblers have bugs too; pin and diff |
| 6 Nov 2017 | **Parity multisig library** (`devops199`): the shared library behind many wallets had never been initialised. The attacker called `initWallet`, became owner, and called `kill`. 513,774.16 ETH in 587 wallets froze, because every wallet `DELEGATECALL`ed into a contract that no longer had code. | The same shape as clones: thousands of thin proxies, one implementation. Lock the implementation; never give it a destructive path. EIP-6780 (Cancun) now prevents code removal outside the creating transaction ([[1.8 Contract creation]]), but an implementation that can be taken over is still fatal. |

## Question ladder

> [!question]- **B** What does Huff let you control that Yul does not?
> Yul controls **which opcodes run with which arguments**. Huff also controls **where every value sits on the stack and where every jump goes**. Concretely:
>
> | Aspect | Yul | Huff |
> |---|---|---|
> | Stack | Hidden behind `let` variables; the code generator picks `DUP`/`SWAP`/`POP` | You write every `dupN`/`swapN`/`pop`. Values can stay on the stack across branches, calls and "functions" |
> | Control flow | `if`, `switch`, `for`, functions only; no labels, no `JUMP` | Labels, `jump`, `jumpi`, fall-through, computed jumps (`mload` a destination, then `jump`) |
> | Jump tables | Impossible (no computed jumps) | `#define jumptable` / `jumptable__packed` + `__tablestart`, so dispatch is one `MLOAD` + one `JUMP` |
> | Byte layout | The assembler orders blocks and adds a `0xfe` separator, metadata (via solc) and `memoryguard` | Exactly what you wrote, in the order you wrote it. `__ASSERT_PC` can pin positions |
> | Specific opcodes | Builtins only; no `PUSH`, `DUP`, `SWAP`, `JUMP`, `PC`; `RETURNDATASIZE`-as-zero tricks are impossible | Any opcode, including `pc` and `returndatasize` used as cheap zero |
> | Constants | Literals, `datasize`/`dataoffset`, immutables | `#define constant`, overridable at build time with `-c` |
> | Code reuse | Functions (the optimizer may inline) | Macros (always inlined) or `fn` (always jumped to): your choice per use |
> | Optimizer | Yes, can rewrite your code | None; nothing is rewritten |
>
> What you give up: variables, scoping, any checking of stack depth (`takes`/`returns` are not enforced: my `LIAR` macro compiled and underflowed at runtime), and source verification on every explorer.
>
> What an interviewer wants to hear is the trade-off, not a list. For straight-line code Yul and Huff produce the same bytes: my clone factory was 93 bytes from both, and my `SimpleStore` was 49 bytes in Huff and 51 in Yul with identical write gas. Huff wins when the stack layout across branches matters (a value kept on the stack through a call, as 1167 does), when dispatch can be a jump table, or when the exact bytes are the product (proxies, deployers). Also mention that Yul's `verbatim` can inject raw bytes in standalone Yul, but the optimizer treats them as an opaque block ([[3.3 Opcodes by family]]).

> [!question]- **I** Walk through EIP-1167 minimal proxy bytecode opcode by opcode.
> Runtime: `363d3d373d3d3d363d73 <20-byte impl> 5af43d82803e903d91602b57fd5bf3`, 45 bytes. Stack shown top first; `cds` = calldata size, `rds` = returndata size, `ok` = success flag. Memory changes are noted on the right.
>
> ```text
> pc  bytes      opcode           stack after                         note
> 00  36         CALLDATASIZE     [cds]
> 01  3d         RETURNDATASIZE   [0, cds]                            0: no call has happened yet (EIP-211)
> 02  3d         RETURNDATASIZE   [0, 0, cds]
> 03  37         CALLDATACOPY     []                                  mem[0..cds) = calldata  (dest 0, offset 0, size cds)
> 04  3d         RETURNDATASIZE   [0]                                 kept for later (becomes the RETURN/REVERT offset)
> 05  3d         RETURNDATASIZE   [0, 0]                              retSize = 0
> 06  3d         RETURNDATASIZE   [0, 0, 0]                           retOffset = 0
> 07  36         CALLDATASIZE     [cds, 0, 0, 0]                      argsSize
> 08  3d         RETURNDATASIZE   [0, cds, 0, 0, 0]                   argsOffset
> 09  73 <impl>  PUSH20 impl      [impl, 0, cds, 0, 0, 0]
> 1e  5a         GAS              [gas, impl, 0, cds, 0, 0, 0]
> 1f  f4         DELEGATECALL     [ok, 0]                             delegatecall(gas, impl, 0, cds, 0, 0)
> 20  3d         RETURNDATASIZE   [rds, ok, 0]                        now really the returndata size
> 21  82         DUP3             [0, rds, ok, 0]
> 22  80         DUP1             [0, 0, rds, ok, 0]
> 23  3e         RETURNDATACOPY   [ok, 0]                             mem[0..rds) = returndata (dest 0, offset 0, size rds)
> 24  90         SWAP1            [0, ok]
> 25  3d         RETURNDATASIZE   [rds, 0, ok]
> 26  91         SWAP2            [ok, 0, rds]
> 27  602b       PUSH1 0x2b       [0x2b, ok, 0, rds]
> 29  57         JUMPI            [0, rds]                            jump to 0x2b if ok != 0
> 2a  fd         REVERT           —                                   revert(0, rds): failure, bubble data
> 2b  5b         JUMPDEST         [0, rds]
> 2c  f3         RETURN           —                                   return(0, rds)
> ```
>
> Points to make while walking it:
>
> - **Why `RETURNDATASIZE`?** It pushes 0 for 2 gas in 1 byte, cheaper than `PUSH1 0` (3 gas, 2 bytes) before Shanghai. It is 0 only before the first call, so every zero the proxy needs after the call is pushed **before** it (the one at pc 04) or copied with `DUP3`/`DUP1`.
> - **Gas forwarding.** `GAS` pushes everything left; the EVM caps the forward at all but 1/64 (EIP-150). The implementation gets almost all gas, and an out-of-gas inside it becomes a failed `DELEGATECALL`, which the proxy turns into `REVERT` with empty data.
> - **Context.** `DELEGATECALL` runs the implementation's code with the clone's storage, balance, `address(this)`, `msg.sender` and `msg.value`. My test confirmed storage landed in the clone (`count` 2 in the clone, 0 in the implementation) and `whoami()` returned the clone and the original caller.
> - **Memory reuse.** Returndata overwrites calldata at offset 0. That is safe because calldata is no longer needed. Memory expansion is paid for `max(cds, rds)`.
> - **Revert bubbling.** On failure, the revert payload is returned unchanged. My `boom()` returned `0x245aecd3 ‖ caller` through the clone, byte for byte.
> - **Cost.** Deploying it is 45 × 200 = 9,000 gas of deposit (9,035 measured with the deployer) plus the 32,000 creation base. Each call adds 2,666 gas when the implementation is cold, of which 2,600 is the account access and 66 is the proxy's own instructions plus memory; I counted every opcode and it matched the measurement exactly.
> - **Deployer.** `3d602d80600a3d3981f3`: `RETURNDATASIZE` (0), `PUSH1 0x2d`, `DUP1`, `PUSH1 0x0a`, `RETURNDATASIZE`, `CODECOPY` (copy 45 bytes from code offset 10 to memory 0), `DUP2`, `RETURN(0, 45)`.
>
> Bonus point: name the PUSH0 variants and why they save gas (zeros on demand after the call instead of `DUP`/`SWAP` juggling): ERC-7511 (Draft, −5 gas measured), Solady `clone_PUSH0` (−8), and that they break 1167 pattern detection.

> [!question]- **A** When is hand-written bytecode worth its review cost?
> Start from what it costs. Hand-written bytecode has no type checker, no stack checker, no optimizer, no source verification, few reviewers who can read it, and a toolchain (Huff) with one active compiler maintained by a small team. Every audit hour is more expensive, and every future change repeats it. So it must buy something large or something only it can buy.
>
> **Worth it:**
>
> 1. **When the bytes are the product.** Minimal proxies, deployers, CREATE2/CREATE3 helpers, the keyless deterministic deployer. Here the code is tiny (9–100 bytes), fixed forever, deployed thousands of times, and must be byte-exact so tools recognise it. A 1167 clone cost 9,035 gas to create against 147,436 for the 736-byte implementation, a 16× saving on every deployment. Review cost is low because the whole program fits on one screen and the patterns are standard and already reviewed (EIP-1167, Solady, OpenZeppelin). Usually you should *reuse* such bytes, not write new ones.
> 2. **When a tiny hot path runs millions of times and gas is the business.** MEV searchers, on-chain order matching inner loops, cryptographic primitives (Huff was born for Weierstrudel's elliptic-curve maths). Even then, measure: on `SimpleStore`, Huff saved 152 gas of 22,309 (0.7 %) against legacy Solidity and nothing against standalone Yul. Storage, hashing and calls dominate real transactions ([[3.10 Yul objects and standalone contracts]] found the same for an ERC-20: everything assembly can win is 1–2 %).
> 3. **When you need something the compiler cannot express.** Jump-table dispatch, a value kept on the stack across a call, an opcode solc does not support yet (`DUPN` today with `hnc -e amsterdam`), or code that must fit a hard size limit.
>
> **Not worth it:**
>
> - Business logic that changes, holds user funds in complex ways, or needs many reviewers. Write Solidity, then put targeted `assembly` in measured hot spots ([[3.1 What Yul is and when to use it]]).
> - "It is a few hundred gas cheaper" when users pay 2,600 gas for one cold account and 20,000 for one new storage slot.
> - Anything where Yul gives the same bytes: my factory was 93 bytes in Yul, Huff and raw hex. Yul is verifiable on Sourcify; Huff is not.
>
> A good answer ends with the process that makes it acceptable: a reference implementation in Solidity, differential fuzzing between them, formal equivalence where possible, pinned compiler and published hashes, and an audit that names the code hash. And a rule of thumb: if the bytes are not small enough to print and annotate in full in the audit report, they are probably too big to hand-write.

> [!question]- **E** How would you get custom bytecode verified and trusted by users and explorers?
> Separate the two words. **Verified** means "this source compiles to these bytes"; **trusted** means "these bytes do what users think". Explorers can only help with the first, and only for compilers they run.
>
> **1. Know what the verifiers support (Nov 2026).**
>
> | Verifier | Accepts | Useful features |
> |---|---|---|
> | Sourcify 4.2.0 | Solidity, Vyper, Yul (since 7 Jan 2026), Fe (since 30 Mar 2026) | exact_match vs match (metadata hash), similarity verification, `proxyResolution` |
> | Etherscan | Solidity, Vyper | Automatic EIP-1167 clone source inheritance; "Similar Match" for identical bytecode |
> | `forge verify-contract` | `--language solidity` or `vyper` | Etherscan, Sourcify, Blockscout, OKLink, custom |
> | Anything | **not Huff, ETK or raw hex** | — |
>
> **2. Shrink the unverifiable part.** Write everything you can in Solidity or Yul and verify it. Keep the hand-written part to standard, tiny pieces. If you need a clone, use the **exact** EIP-1167 bytes: Etherscan then shows the implementation's verified source and ABI on every clone with no action, and every proxy-detection library understands it. A custom PUSH0 proxy saves 5–8 gas a call and loses all of that. My `implementationOf` detector found the 1167 clone and returned zero for an ERC-7511 clone of the same implementation: that is what "nonstandard" means for every integrator's tooling.
>
> **3. If the code must be Huff or raw, make it reproducible.**
> - Source at a tagged commit; the exact compiler (`hnc 1.7.1`, plus the release archive's SHA-256); the exact command line including every flag that changes bytes (`--relax-jumps` changed my factory from 94 to 93 bytes; `-e paris` turns every `PUSH0` into `PUSH1 0`; `-c IMPL=…` changes the address bytes).
> - The expected `keccak256` of runtime and creation code, per chain, in the README and the audit report.
> - A CI job that rebuilds and compares with `cast code` / `eth_getCode` on every deployment. Deterministic deployment (same factory, same salt) gives the same address and code hash on every chain, which makes the published hash a single fact to check ([[4.3 Deterministic and cross-chain deployment]]).
> - An ABI: `hnc -g` writes a Solidity interface from the `#define function` lines.
>
> **4. Let contracts check code, not just people.** Integrators and factories can check `extcodehash(a) == EXPECTED` before trusting an address. My `CloneFactory1167.isClone` does exactly that. Registries (allowlists of code hashes) work the same way. This is stronger than any explorer badge, because it is enforced at runtime.
>
> **5. Build trust in behaviour, not just identity.** A Solidity reference implementation plus differential fuzzing (same return data, revert data, logs and storage on random inputs; huff-neo's test runner runs on Foundry's executor), symbolic equivalence checking where feasible ([[6.5 Formal verification]]), and an audit that names the commit, compiler and code hash. Small, immutable code helps: users can read 45 annotated bytes.
>
> **6. Know the traps.**
> - Etherscan's "Similar Match" is a heuristic. Etherscan itself says it "is not foolproof" and that different constructor arguments can change behaviour. Two contracts with the same runtime and different immutables or storage are not the same contract.
> - A Yul wrapper with a `data "runtime" hex"…"` section will verify on Sourcify (I compiled one around the Huff runtime and the deployed code matched), but the "source" is the same hex. It proves publication, not review.
> - Sourcify's **match** (not exact_match) means the metadata differs: functionally the same bytecode, but the sources you read might not be byte-identical to what was compiled.
> - Verification of a proxy says nothing about its implementation, and vice versa. Check both, and check who can change the implementation ([[4.2 Upgradeability and proxies]]).
>
> What an interviewer listens for: that verification is reproducibility, not correctness; that the cheapest trust is using standard bytes; that hashes must be pinned and checked on-chain; and that you know the current tool support instead of assuming Etherscan can verify anything.
