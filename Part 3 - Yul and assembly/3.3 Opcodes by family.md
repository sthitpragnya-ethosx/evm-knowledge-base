# 3.3 Opcodes by family

> [!abstract] In one minute
> - A Yul builtin is an EVM opcode written as a function call. Arguments are listed **top of stack first**: `sub(a, b)` is `a − b`, and `shl(shift, value)` takes the **shift amount first**. Getting the order wrong compiles silently.
> - Nothing is checked. `add`, `sub`, `mul` and `exp` wrap modulo 2^256. `div`, `sdiv`, `mod`, `smod`, `addmod` and `mulmod` return **0** when the divisor or modulus is 0. `sdiv(−2^255, −1)` returns −2^255. Solidity's `x / 0` reverts with `Panic(0x12)`; Yul's `div(x, 0)` is 0.
> - Every word is unsigned. Signed numbers are a way of reading the same bits. Use `slt`, `sgt`, `sdiv`, `smod`, `sar` and `signextend` when the bits are two's complement; `lt`/`gt` treat −1 as 2^256 − 1.
> - Shifts by 256 or more give 0 (`sar` gives 0 or −1). `byte(i, x)` counts from the **most significant** byte, and `i ≥ 32` gives 0. `signextend(b, x)` reads the low `b + 1` bytes as signed; `b ≥ 31` leaves `x` alone.
> - Most opcodes cost 2, 3, 5 or 8 gas. `exp` costs 10 + 50 per byte of the exponent; `keccak256` costs 30 + 6 per word plus memory expansion. `clz` (Osaka, EIP-7939, `0x1e`, 5 gas, `clz(0) = 256`) turns "most significant bit" into 11 gas instead of about 200.
> - Some builtins are not opcodes (`datasize`, `memoryguard`, `verbatim`, `linkersymbol`, `setimmutable`), and some opcodes are not builtins (jumps, `DUP`, `SWAP`, `PUSH`, `PC`). Amsterdam adds `SLOTNUM` and `DUPN`/`SWAPN`/`EXCHANGE` (scheduled); solc 0.8.38 already warns when you use those names as identifiers.

**Prerequisites:** [[1.3 Execution model]], [[1.9 Gas accounting]], [[3.2 Syntax and control flow]] · **Leads to:** [[3.5 Memory management in assembly]], [[3.6 Storage, transient storage and bit packing]], [[3.7 External calls in assembly]], [[3.8 ABI, errors and events by hand]], [[3.9 Cleanup, dirty bits and safety]]

## How to read a builtin

[[3.2 Syntax and control flow]] showed that in Yul, an opcode is called like a function: `add(x, 1)`. This note is about what each of those calls *does*: the result on ordinary inputs, the result on edge inputs, and the gas.

Three rules explain almost every surprise in this note.

**1. Argument order is stack order.** The EVM pops its operands from the top of the stack. Yul lists them in the order they are popped: the first argument is the top of the stack. So `sub(a, b)` computes `a − b`, `div(a, b)` computes `a / b`, and `lt(a, b)` asks "is `a < b`". This reads naturally for arithmetic. It reads badly for shifts: the EVM's `SHL` pops the **shift amount** first, so Yul writes `shl(shift, value)`. Most languages write `value << shift`. This is the most common silent bug in hand-written assembly.

**2. Every value is a 256-bit unsigned word.** Yul (in the EVM dialect) has one type, `u256`. There are no negative literals: `let x := -1` is a parse error (`ParserError: Literal or identifier expected.`). You write −1 as `not(0)` and −x as `sub(0, x)`. "Signed" is not a type. It is a choice of opcode: `slt` reads both words as two's complement; `lt` reads them as unsigned. The bits are the same.

**3. No checks, ever.** Solidity 0.8 adds overflow checks, division-by-zero checks and type cleanup around its operators ([[2.9 Arithmetic and numeric pitfalls]]). Builtins are the raw opcodes. Every check you want, you write.

> [!note] How the numbers in this note were produced
> All behaviour and gas figures were measured in py-evm with **Prague** rules, by running small hand-built runtime bytecodes (for single opcodes) or contracts compiled with **solc 0.8.38** (optimizer on, 200 runs). Gas is **execution gas only**, excluding the 21,000 intrinsic gas and calldata. Per-opcode costs were isolated by subtracting a run of the same code without the opcode. `clz` cannot run in py-evm (it is an Osaka opcode); [[#Count leading zeros (Osaka)]] explains the opcode, and the last question of the [[#Question ladder]] explains how I tested it anyway.

The gas tiers come from [[1.9 Gas accounting]]: base 2, very low 3, low 5, mid 8. I re-measured every fixed-cost opcode in the arithmetic, comparison, bitwise and environment tables below (except `clz`), and all matched.

## Arithmetic

| Builtin | Byte | Stack in → out | Gas | Edge cases (all verified) |
|---|---|---|---|---|
| `add(a, b)` | `0x01` | a, b → a + b | 3 | Wraps: `add(2^256−1, 1) = 0` |
| `sub(a, b)` | `0x03` | a, b → a − b | 3 | Wraps: `sub(0, 1) = 2^256−1` |
| `mul(a, b)` | `0x02` | a, b → a · b | 5 | Wraps: `mul(2^255, 2) = 0` |
| `div(a, b)` | `0x04` | a, b → ⌊a / b⌋ | 5 | `div(a, 0) = 0` |
| `sdiv(a, b)` | `0x05` | a, b → a / b, signed, truncated toward 0 | 5 | `sdiv(a, 0) = 0`; `sdiv(−2^255, −1) = −2^255`; `sdiv(−7, 2) = −3` |
| `mod(a, b)` | `0x06` | a, b → a mod b | 5 | `mod(a, 0) = 0` |
| `smod(a, b)` | `0x07` | a, b → signed remainder | 5 | Sign of the result = sign of `a`; `smod(a, 0) = 0`; `smod(−2^255, −1) = 0` |
| `addmod(a, b, n)` | `0x08` | a, b, n → (a + b) mod n | 8 | Exact (257-bit) sum, no wrap; `n = 0` gives 0 |
| `mulmod(a, b, n)` | `0x09` | a, b, n → (a · b) mod n | 8 | Exact (512-bit) product, no wrap; `n = 0` gives 0 |
| `exp(a, e)` | `0x0a` | a, e → a^e mod 2^256 | 10 + 50 per exponent byte | `exp(0, 0) = 1`; `exp(2, 256) = 0` |
| `signextend(b, x)` | `0x0b` | b, x → x sign-extended from byte `b` | 5 | `b ≥ 31` returns `x` unchanged |

### Wrapping and division by zero

Here is the whole table's "no checks" rule, run in py-evm:

```text
add(0xff…ff, 1)        = 0x0
sub(0, 1)              = 0xff…ff            (= −1 read as signed)
mul(0x80…00, 2)        = 0x0
div(7, 0)              = 0x0
sdiv(−7, 0)            = 0x0
mod(7, 0)              = 0x0
smod(−7, 0)            = 0x0
addmod(0xff…ff, 1, 0)  = 0x0
mulmod(0xff…ff, 0xff…ff, 0) = 0x0
```

The EVM never faults on arithmetic. Division by zero is defined to be zero because an exception would need a new failure mode, and the designers preferred a total function. That is a reasonable machine design and a bad default for money: a share price of zero, a fee of zero, or an exchange rate of zero will flow onwards without any error. Solidity adds `Panic(0x12)` around `/` and `%`, even inside `unchecked`. In assembly you must test the divisor yourself (see [[#Question ladder]], first question).

### Signed division: `sdiv` and `smod`

`sdiv` reads both words as two's complement and **truncates toward zero**, like C and like Solidity's `/` on `int256`:

```text
sdiv(−7, 2)  = −3     (0xff…fd)
sdiv(7, −2)  = −3
smod(−7, 2)  = −1     sign follows the dividend
smod(7, −2)  = 1
smod(−7, −2) = −1
mod(−7, 2)   = 1      (−7 read as 2^256 − 7, which is odd)
```

The sign rule for `smod` is: the result has the sign of the **first** argument (the dividend), and its magnitude is `|a| mod |b|`. Python's `%` follows the sign of the divisor instead, so `-7 % 2 == 1` in Python. Do not test Yul against Python's `//` and `%` without converting.

The one input pair that overflows signed division is `−2^255 / −1`. The true answer, +2^255, does not fit in `int256`. The EVM returns the input unchanged:

```text
sdiv(0x8000…0000, 0xffff…ffff) = 0x8000…0000   (−2^255)
smod(0x8000…0000, 0xffff…ffff) = 0x0
```

Solidity's checked `int256` division tests exactly this pair and panics with `0x11` ([[2.9 Arithmetic and numeric pitfalls]]). Assembly does not.

### `exp` and its gas

`exp(a, e)` computes a^e modulo 2^256. It is the only arithmetic opcode whose cost depends on the input: 10 gas plus 50 gas for every byte of the exponent, counting from its most significant non-zero byte. Measured in py-evm:

| Exponent | Exponent bytes | Gas |
|---|---|---|
| 0 | 0 | 10 |
| 1 | 1 | 60 |
| 255 (`0xff`) | 1 | 60 |
| 256 (`0x100`) | 2 | 110 |
| 65,536 (`0x10000`) | 3 | 160 |
| 2^248 | 32 | 1,610 |
| 2^256 − 1 | 32 | 1,610 |

Only the size of the exponent matters, not the base. `exp(0, 0)` is 1, like most mathematics libraries. `exp(2, 256)` is 0 because 2^256 wraps.

> [!tip] Powers of two are shifts
> `exp(2, n)` costs 60 gas for any `n` from 1 to 255. `shl(n, 1)` costs 3 gas and gives the same answer (both give 0 for `n ≥ 256`). The Yul optimizer knows the rule: in a standalone Yul object and under via-IR, 0.8.38 compiled `exp(2, x)` to `PUSH1 0x01 … SHL`. Inline assembly in the **legacy** pipeline kept the `EXP`. Write `shl` yourself and the question goes away.

### `addmod` and `mulmod`

These two do modular arithmetic with an **exact** intermediate. `addmod` adds two 256-bit numbers into a 257-bit sum and only then reduces modulo `n`. `mulmod` multiplies into a 512-bit product and then reduces. Nothing wraps before the reduction. Compare them with the wrapping version:

```text
mulmod(2^255, 4, 7)          = 4      (2^257 mod 7 = 4, correct)
mod(mul(2^255, 4), 7)        = 0      (mul wrapped to 0 first: wrong)
addmod(2^256−1, 2^256−1, 7)  = 2      (correct)
mod(add(2^256−1, 2^256−1), 7) = 0     (add wrapped first: wrong)
mulmod(x, y, 0)              = 0
```

They are for any arithmetic in a finite field or ring whose modulus is close to 2^256: elliptic-curve and pairing code over the BN254 field, Poseidon or MiMC hashes, and, above all, the **512-bit product trick** inside `mulDiv`: `mulmod(x, y, not(0))` gives the product modulo 2^256 − 1, and combined with `mul(x, y)` (the product modulo 2^256) it recovers the high word. [[2.9 Arithmetic and numeric pitfalls]] builds `mulDiv` from that, so I do not repeat it here.

### `signextend`

`signextend(b, x)` treats the low **b + 1 bytes** of `x` as a two's complement number, and returns that number as a full 256-bit word. Mechanically: it looks at bit `8b + 7` (the top bit of byte `b`, counting bytes from the least significant end), and copies that bit into every bit above it. Bits below are kept.

So `b = 0` means "this is an `int8`", `b = 1` means `int16`, and `b = 15` means `int128`. In general `b = bytes − 1`. Measured:

```text
signextend(0, 0xff)      = 0xff…ff        −1      (top bit of the byte is 1)
signextend(0, 0x7f)      = 0x7f           127     (top bit is 0)
signextend(0, 0x1280)    = 0xff…ff80      −128    (the 0x12 above byte 0 is ignored)
signextend(1, 0x8000)    = 0xff…ff8000    −32768
signextend(1, 0xab7fff)  = 0x7fff         32767   (garbage above byte 1 is cleared)
signextend(30, 0x80 << 240) = 0xff80…00           (byte 30's top bit copied into byte 31)
signextend(31, 0xdead)   = 0xdead                 (b ≥ 31: unchanged)
signextend(32, 0x80)     = 0x80
signextend(1000, 0x80)   = 0x80
```

Two details matter. First, `signextend` **overwrites** the high bits; it does not OR into them. That makes it a cleanup operation: whatever garbage sits above the value, the result is the canonical `intN` word. Second, the first argument is a **byte index**, not a bit count and not a byte count. `signextend(8, x)` is sign extension from 72 bits (`int72`), not from 8 bits.

Solidity uses `signextend` exactly this way. The via-IR ABI decoder for an `int8` parameter, from `irOptimized` with 0.8.38:

```text
let value := calldataload(4)
let _2 := signextend(0, value)
if iszero(eq(value, _2)) { revert(0, 0) }
```

A calldata word of `0x80` (128, which is not a valid `int8` encoding) reverted with empty data; the proper encoding of −128 (`0xff…ff80`) was accepted on both pipelines. Cleanup of narrow types is the topic of [[3.9 Cleanup, dirty bits and safety]].

## Comparison

| Builtin | Byte | Stack in → out | Gas | Edge cases |
|---|---|---|---|---|
| `lt(a, b)` | `0x10` | a, b → 1 if a < b (unsigned) else 0 | 3 | `lt(−1, 1) = 0`: −1 is 2^256−1 unsigned |
| `gt(a, b)` | `0x11` | a, b → 1 if a > b (unsigned) | 3 | `gt(−1, 1) = 1` |
| `slt(a, b)` | `0x12` | a, b → 1 if a < b (signed) | 3 | `slt(−1, 1) = 1` |
| `sgt(a, b)` | `0x13` | a, b → 1 if a > b (signed) | 3 | `sgt(−1, 1) = 0` |
| `eq(a, b)` | `0x14` | a, b → 1 if a == b | 3 | Compares all 256 bits, including dirty high bits |
| `iszero(a)` | `0x15` | a → 1 if a == 0 else 0 | 3 | `iszero(5) = 0`, `iszero(2^256−1) = 0` |

Every comparison returns exactly 0 or 1. There is no `le`, `ge` or `ne`. You build them:

| You want | Write | Opcodes |
|---|---|---|
| `a <= b` | `iszero(gt(a, b))` | 2 |
| `a >= b` | `iszero(lt(a, b))` | 2 |
| `a != b` | `iszero(eq(a, b))` | 2 |
| "x is non-zero", as 0 or 1 | `iszero(iszero(x))` | 2 |
| "x is non-zero", for an `if` | just `x` | 0 |

`if` in Yul treats any non-zero word as true, so `if x { … }` needs no comparison. You only need `iszero(iszero(x))` when the value must be **exactly** 1, for example before you store it as a `bool`, return it, OR it into a bitmap, or multiply by it.

### `iszero` as a boolean normaliser

A `bool` in Solidity must be 0 or 1. If assembly hands Solidity a 2, what comes out depends on what touches it next. I wrote `assembly { b := 2 }` in a function returning `bool`. Both pipelines returned `0x…01`: the ABI encoder cleans `bool` with `iszero(iszero(·))` before writing it. In 0.8.38 Solidity also cleans it in comparisons, `if`, `&&`, `!` and storage packing, but other assembly code that reads the raw word sees the 2, and [[3.9 Cleanup, dirty bits and safety]] shows where dirty bools leak. Normalise in assembly: `b := iszero(iszero(x))`. In py-evm, `iszero(iszero(12345))` returned 1.

### Signed comparisons in compiler output

The via-IR decoder above starts with this check:

```text
if slt(add(calldatasize(), not(3)), 32) { revert(0, 0) }
```

`not(3)` is −4, so this is "calldata size minus 4 is less than 32", **signed**. If calldata were shorter than 4 bytes, `calldatasize() − 4` would wrap to a huge unsigned number, and `lt` would say "plenty of data". `slt` sees a negative number and reverts. The compiler deliberately uses a signed comparison on a value that is normally unsigned, because the subtraction might have underflowed. That is a useful trick to remember.

## Bitwise

| Builtin | Byte | Stack in → out | Gas | Edge cases |
|---|---|---|---|---|
| `and(a, b)` | `0x16` | a, b → a & b | 3 | — |
| `or(a, b)` | `0x17` | a, b → a \| b | 3 | — |
| `xor(a, b)` | `0x18` | a, b → a ^ b | 3 | — |
| `not(a)` | `0x19` | a → ~a | 3 | `not(0) = 2^256 − 1` (−1) |
| `byte(i, x)` | `0x1a` | i, x → byte `i` of `x`, counting from the **most significant** byte | 3 | `byte(0, x)` is the top byte; `byte(31, x)` the lowest; `i ≥ 32` gives 0 |
| `shl(s, v)` | `0x1b` | s, v → v << s | 3 | **shift first**; `s ≥ 256` gives 0 |
| `shr(s, v)` | `0x1c` | s, v → v >> s (logical) | 3 | `s ≥ 256` gives 0 |
| `sar(s, v)` | `0x1d` | s, v → v >> s (arithmetic) | 3 | `s ≥ 256` gives 0 for v ≥ 0, −1 for v < 0; rounds toward −∞ |
| `clz(x)` | `0x1e` | x → number of leading zero bits | 5 | `clz(0) = 256`. Osaka and later only |

### Shifts

`shl`, `shr` and `sar` arrived in Constantinople (EIP-145). Before that, compilers used `mul` and `div` by powers of two, which is why very old code is full of `exp(2, n)`. All three take the shift amount first. All three accept any 256-bit shift amount:

```text
shl(255, 1)          = 0x8000…0000
shl(256, 1)          = 0x0
shr(256, 0xff…ff)    = 0x0
shr(2^200, 0xff…ff)  = 0x0
sar(256, −1)         = 0xff…ff   (−1)
sar(300, −8)         = 0xff…ff   (−1)
sar(256, 5)          = 0x0
sar(1, −7)           = 0xff…fc   (−4)
sdiv(−7, 2)          = 0xff…fd   (−3)
```

The last two lines are a classic trap. `sar(1, x)` is **not** `sdiv(x, 2)` for negative odd `x`. An arithmetic shift rounds toward minus infinity (floor); `sdiv` truncates toward zero. For non-negative `x` they agree. The optimizer respects the difference: in a Yul object, 0.8.38 turned `div(x, 2)` into `shr(1, x)` but left `sdiv(x, 2)` and `sdiv(x, 4)` as `SDIV`. Do not make that swap by hand either, unless floor rounding is what you want.

> [!warning] `shl(value, shift)` compiles
> `shl` and `shr` are two-argument builtins with no types, so swapping the arguments is not an error. `and(shr(x, 160), 0xffffffff)` (meant: "bits 160 and up of x") shifts the constant 160 right by `x` bits. I ran it: for a real 256-bit `x` it returned 0, and for `x = 3` it returned `0x14` (160 >> 3 = 20). Both look like plausible numbers in a test that does not check exact values. Read every shift as "shift **by** first, **what** second".

### `byte`

`byte(i, x)` returns one byte of `x` as a number from 0 to 255. Index 0 is the **most significant** byte, the leftmost two hex digits when you write the word out. That matches how a word sits in memory: `byte(0, mload(p))` is the byte at address `p`. It is the opposite of how bits are numbered for `shr` and `and`.

```text
x = 0x0102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f20
byte(0, x)     = 0x01
byte(31, x)    = 0x20
byte(32, x)    = 0x00
byte(2^255, x) = 0x00     (any index ≥ 32 gives 0)
```

For any `i` below 2^253, `byte(i, x)` equals `and(shr(sub(248, shl(3, i)), x), 0xff)`. I checked every `i` from 0 to 299 in py-evm: identical. (For `i ≥ 32` the subtraction wraps to a huge shift, and huge shifts give 0, so the formula even matches the "out of range" case.) For `i = 2^253 + 1`, `shl(3, i)` wraps to 8, and the formula returned 2 while `byte` returned 0. The builtin is cheaper and has no such hole: use it.

### `not(0)` and masks

Masks are the bread and butter of packed storage ([[3.6 Storage, transient storage and bit packing]]). Useful constants:

| Mask | Expression | Value |
|---|---|---|
| All ones | `not(0)` | `0xff…ff` |
| Low `n` bits (n < 256) | `sub(shl(n, 1), 1)` | e.g. n = 160 gives the address mask |
| Address mask | `0xffffffffffffffffffffffffffffffffffffffff` | low 160 bits |
| Clear bits `[k, k + n)` | `not(shl(k, sub(shl(n, 1), 1)))` | then `and` with it |
| Top 4 bytes | `shr(224, x)` | the function selector from `calldataload(0)` |

The optimizer agrees with this taste: in the compiled MSB code below, solc 0.8.38 wrote the constant `0xffffffffffffffffffffffffffffffff` as `PUSH1 0x01 DUP1 PUSH1 0x80 SHL SUB`, that is `sub(shl(128, 1), 1)`, because those six bytes are shorter than a `PUSH16`.

### Count leading zeros (Osaka)

EIP-7939 added `CLZ` at byte `0x1e` in the Osaka fork (Fusaka, live on mainnet since 3 Dec 2025). From the EIP: it pops `x` and pushes "the number of zeros preceding the most significant one bit"; "If `x` is zero, pushes 256." It costs 5 gas, the same as `MUL`. The EIP says the price was "raised from 3 to avoid under-pricing DoS risk".

```text
clz(1)        = 255
clz(2^255)    = 0
clz(2^160−1)  = 96     (an address-sized value)
clz(0)        = 256
```

Solidity added the Yul builtin `clz(x)` in **0.8.31** (3 Dec 2025, the same day Fusaka activated), and made `osaka` the default EVM version in that release. In 0.8.38 it compiles only for `osaka` or later. With `evmVersion: "prague"` I got:

```text
TypeError: The "clz" instruction is only available for Osaka-compatible VMs
(you are currently compiling for "prague").
```

The name is reserved too, and the reservation depends on the target. With `osaka` (the default), both `let clz := 1` and a user function `function clz(x) -> y { … }` fail with `ParserError: Cannot use builtin function name "clz" as identifier name.` With `prague` they compile, with the warning `"clz" will be promoted to Yul reserved identifier in the future and will not be allowed anymore as an identifier.` So an old library with its own `clz` helper breaks the moment it is compiled for the default target.

The compiler never emits `CLZ` on its own (Solidity has no `clz` operator), so a contract only contains `0x1e` if its assembly asks for it. A contract compiled with the default `osaka` target and no `clz` in assembly runs on Prague chains too. A contract that uses `clz` does not: on a chain without Osaka, `0x1e` is an undefined opcode and the call fails, consuming all gas. Many L2s and sidechains adopt forks late, so check before deploying there ([[1.11 Hard forks that changed contract code]]).

The [[#Question ladder]] uses `clz` to build "most significant bit" and compares its gas with a binary search.

## Hashing: `keccak256`

| Builtin | Byte | Stack in → out | Gas | Edge cases |
|---|---|---|---|---|
| `keccak256(p, n)` | `0x20` | p, n → Keccak-256 of memory `[p, p + n)` | 30 + 6 per word of `n` (rounded up), plus memory expansion | `n = 0` hashes the empty string and does not touch memory |

`keccak256` hashes **memory**, not a value. You write the input into memory first (usually scratch space `0x00–0x3f`, see [[2.4 Memory layout]]) and pass a pointer and a length. Measured on fresh memory, so the expansion part is included:

| Call | Words hashed | Hash cost | Memory expansion | Measured |
|---|---|---|---|---|
| `keccak256(0, 0)` | 0 | 30 | 0 | 30 |
| `keccak256(0, 1)` | 1 | 36 | 3 (1 word) | 39 |
| `keccak256(0, 32)` | 1 | 36 | 3 | 39 |
| `keccak256(0, 33)` | 2 | 42 | 6 | 48 |
| `keccak256(0, 64)` | 2 | 42 | 6 | 48 |
| `keccak256(0, 1024)` | 32 | 222 | 98 | 320 |
| `keccak256(4096, 0)` | 0 | 30 | **0** | 30 |
| `keccak256(4096, 32)` | 1 | 36 | 419 (129 words) | 455 |

Three things to take from the table. A partial word costs a full word: 33 bytes cost as much as 64. A zero length never expands memory, wherever the pointer points. And the expensive part of a far-away hash is the memory, not the hash.

The hash of the empty input is `0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`. You will see it again as the `extcodehash` of an account that exists but has no code.

Mapping slots, `abi.encodePacked` hashing and namespaced storage all reduce to "write 64 bytes to scratch space, `keccak256(0, 0x40)`". [[3.6 Storage, transient storage and bit packing]] does that in detail; [[4.6 On-chain cryptography]] covers what the hash is good and bad for.

> [!warning] Hash exactly what you mean
> `keccak256` sees bytes, not types. Hash an address that still has dirty high bits, or pass `0x40` when you wrote only 52 bytes, and you get a perfectly valid, perfectly wrong hash. Nothing fails; the mapping lookup simply reads a different slot. Mask addresses with `and(a, 0xffffffffffffffffffffffffffffffffffffffff)` before hashing them if they came from outside ([[3.9 Cleanup, dirty bits and safety]]).

## Environment, block and transaction context

These builtins read the call frame, the transaction or the block. Most cost 2 gas. Those that look at **another account** pay the EIP-2929 access cost: 2,600 gas the first time an address is touched in the transaction ("cold"), 100 after that ("warm"). The block-context ones are covered in depth in [[1.10 Block and chain context]]; the call-frame ones in [[1.3 Execution model]] and [[1.6 Calldata, returndata and logs]].

The edge cases I ran: `calldataload` past the end gives 0; `calldatacopy` of 32 bytes from 1-byte calldata gave `ab00…00`; `codecopy` past the end zero-filled; `extcodehash` of a never-used address gave 0 and of a funded EOA gave `keccak256("")`; `blockhash` of a block too far away gave 0; `blobhash(0)` with no blobs gave 0; and `returndatacopy(0, 0, 1)` with empty return data halted with `OutOfBoundsRead` and used all 100,000 gas it had.

### `caller`, `origin`, `callvalue`

`caller()` is the one you want for authorisation. `origin()` is the account that signed the transaction, which is the wrong thing to authorise on (a malicious contract the user calls can call you with the user's `origin`), and since EIP-7702 it is not even guaranteed to be code-free ([[5.11 New attack surfaces - transient storage, EIP-7702, account abstraction]]).

`callvalue()` is not checked for you in assembly. Solidity inserts `if callvalue() { revert(0, 0) }` at the top of non-payable functions (it is the first line of every non-payable branch of the via-IR dispatcher). A standalone Yul contract must write it itself, or it will silently accept Ether ([[3.10 Yul objects and standalone contracts]]).

### `gas()`

`gas()` returns the gas still available **after** the `GAS` opcode has charged its own 2 gas. I ran a contract whose first instruction is `GAS`, with exactly 100,000 gas: it returned 99,998.

The value depends on everything before it: the transaction's gas limit, the intrinsic cost, how much the caller forwarded (at most 63/64 of what it had, EIP-150, see [[1.7 Message calls and precompiles]]) and every instruction so far. So:

- **Use it to forward gas**: `call(gas(), …)` is the idiom. The EVM caps the forwarded amount at 63/64 for you ([[3.7 External calls in assembly]]).
- **Use it to measure**: `let g := gas() … let used := sub(g, gas())`. The result includes a small fixed overhead for the second `GAS` and the stack shuffling. I measured `exp` this way in a 0.8.38 contract: the bracket reported 23, 73, 123 and 1,623 gas for 0, 1, 2 and 32 exponent bytes. That is the true `exp` cost (10, 60, 110, 1,610) plus 13 gas of overhead (`DUP`, `DUP`, `SWAP`, `POP`, `GAS`). Subtract a bracket around nothing to calibrate.
- **Do not make correctness depend on it.** Code that behaves differently when `gas()` is below some threshold behaves differently on mainnet, in tests, and under a relayer that sets a different gas limit. That is how "insufficient gas griefing" works ([[5.7 Denial of service and griefing]]).

### `selfbalance` versus `balance(address())`

`selfbalance()` costs 5 gas, always. `balance(address())` pays the access-list price; the executing contract is warm in a real transaction, so that is 100 gas. Use `selfbalance()`. It has existed since Istanbul.

## Termination

| Builtin | Byte | Gas | Effect |
|---|---|---|---|
| `stop()` | `0x00` | 0 | Ends the call successfully with empty return data. Same as `return(0, 0)` |
| `return(p, s)` | `0xf3` | 0 + memory | Ends the call successfully, returning memory `[p, p+s)` |
| `revert(p, s)` | `0xfd` | 0 + memory | Ends the call, undoes its state changes, returns `[p, p+s)` as revert data, **refunds the remaining gas** |
| `invalid()` | `0xfe` | all remaining gas | Exceptional halt: undoes state, no return data, **consumes all gas** |

Measured with 100,000 gas: `revert(0, 0)` used 4 gas (two `PUSH0`); `invalid()` used all 100,000; an undefined opcode (`0x0c`) also used all 100,000. `return(2^255, 0)` succeeded using 5 gas: with a zero size, the offset is never used, so no memory is expanded.

`invalid()` is how Solidity before 0.8.0 implemented `assert`, which is why old failed asserts burned all gas. Today you see it as the `0xfe` byte that separates runtime code from metadata, and in hand-written code that wants a "this can never happen" trap. For anything a user might trigger, use `revert` so that the caller keeps its gas and gets an error message ([[2.8 Errors and reverts]]).

> [!warning] `return` ends the whole call
> In inline assembly, `return(p, s)` does not return from the Solidity function. It ends the **entire external call**, skipping everything after it: the rest of the caller's code, modifiers' trailing code, and Solidity's own return encoding. To leave just a Yul function, use `leave`. [[3.4 Interop with Solidity]] covers this in detail.

## Builtins that are not opcodes, and opcodes that are not builtins

Yul's EVM dialect is almost, but not exactly, the opcode list.

### Builtins that are not opcodes

These exist only in Yul **objects** (standalone Yul, or the compiler's own IR). I tried each one in Solidity inline assembly with 0.8.38: every one failed with `DeclarationError: Function "<name>" not found.` I then compiled a Yul object that uses all of them; it compiled.

| Builtin | What it becomes | Purpose |
|---|---|---|
| `datasize("name")` | A `PUSH` of a sub-object's size | Copying runtime code in a constructor ([[3.10 Yul objects and standalone contracts]]) |
| `dataoffset("name")` | A `PUSH` of a sub-object's offset | same |
| `datacopy(t, f, s)` | `CODECOPY` | same |
| `setimmutable(p, "name", v)` | Memory writes into the runtime code copy | Filling `immutable` values at deployment |
| `loadimmutable("name")` | A `PUSH32` placeholder in runtime code | Reading an `immutable` |
| `linkersymbol("file:Lib")` | A 20-byte placeholder (`__$…$__`) the linker fills in | External library addresses |
| `memoryguard(size)` | A `PUSH` of a literal | A promise that memory below `size` is reserved; lets via-IR move variables to memory ([[2.4 Memory layout]]). In my object, `memoryguard(0x80)` compiled to `PUSH1 0x80` |
| `verbatim_<n>i_<m>o("hex", …)` | The raw bytes you give it | Opcodes the compiler does not know. The optimizer treats them as a black box; misuse is undefined behaviour |

One opcode builtin is also special: `pop(x)` (`POP`, `0x50`, 2 gas) discards a value. Yul requires every returned value to be used, so `pop(call(…))` is how you deliberately ignore a result (usually a bad idea for calls).

### Opcodes that are not builtins

| Opcode(s) | Why not | What you write instead |
|---|---|---|
| `JUMP`, `JUMPI`, `JUMPDEST` | Yul has structured control flow so it can be analysed and optimised | `if`, `switch`, `for`, functions ([[3.2 Syntax and control flow]]) |
| `PUSH0`–`PUSH32` | Literals are pushed for you | `0x80`, `"abc"`, `true` |
| `DUP1`–`DUP16`, `SWAP1`–`SWAP16` | Variables are managed for you | `let`, assignment |
| `PC` (`0x58`) | Disallowed. Even in inline assembly with the optimizer off I got `SyntaxError: PC instruction is a low-level EVM feature. Because of that PC is disallowed in strict assembly.` | Nothing; code positions are meaningless after optimization |
| `DIFFICULTY` (`0x44`) as `difficulty()` | Renamed at Paris. With target `osaka`, `difficulty()` is `Function "difficulty" not found.` | `prevrandao()` (same byte) |
| `MSIZE` with optimizer on | Its value depends on what the optimizer removes | Track sizes yourself; or turn the optimizer off |
| `CLZ` before Osaka, `SLOTNUM` before Amsterdam | Version-gated | Set `evmVersion` |

The verbatim builtin is the escape hatch for the rest. In a standalone Yul object compiled for `prague`, `mstore(0, verbatim_1i_1o(hex"1e", calldataload(0)))` compiled to `5f351e5f5260205ff3`: a `CLZ` the compiler does not believe exists on that target. That is how a Yul object could use a new opcode before the compiler supported it (and how you can deploy code a chain cannot run). In Solidity inline assembly, `verbatim` is not available.

### Scheduled for Amsterdam

The Glamsterdam upgrade (EIP-7773; live on Sepolia since 6 Oct 2026; no mainnet date) has new opcodes scheduled:

| Opcode | Byte | Gas | Meaning | Solidity status (0.8.38) |
|---|---|---|---|---|
| `SLOTNUM` (EIP-7843) | `0x4b` | 2 | Beacon-chain slot number of the current block, as a `uint64` | Yul builtin `slotnum()` and `block.slotnum` since 0.8.37, only with `evmVersion: "amsterdam"` (experimental, needs `settings.experimental: true`). I compiled it: the runtime contains `4b` |
| `DUPN` (EIP-8024) | `0xe6` | 3 | Duplicate stack item 17–235, chosen by a one-byte immediate | Not a builtin. Name reserved with a warning |
| `SWAPN` (EIP-8024) | `0xe7` | 3 | Swap with stack item 17–235 | same |
| `EXCHANGE` (EIP-8024) | `0xe8` | 3 | Swap two items deeper in the stack | same |

DUPN, SWAPN and EXCHANGE exist for compilers: they reach stack slots below the 16 that `DUP`/`SWAP` can see, which is the root of "stack too deep". Like `DUP` and `SWAP`, 0.8.38 does not expose them to Yul code: `dupn(1)` is `Function "dupn" not found.` even for the `amsterdam` target. But their names are being reserved. Since 0.8.38, using them as identifiers gives:

```text
Warning: "dupn" will be promoted to Yul reserved identifier in the future and will not be allowed anymore as an identifier.
```

I got the same warning for `swapn`, `exchange` and (on the default `osaka` target) `slotnum`. On the experimental `amsterdam` target, `let slotnum := 1` is already an error (`Cannot use builtin function name "slotnum" as identifier name.`), exactly like `clz` on `osaka`. Rename such variables now.

## Solidity and Yul in practice

### A bit-field toolkit

Packed words are where shifts, masks and `signextend` meet. This library reads, writes and sign-reads a field. Compiled with 0.8.38 and run on both pipelines:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

/// Read and write a bit field [offset, offset + width) of a word.
/// Requires 0 < width < 256 and offset + width <= 256 (not checked).
library Fields {
    function get(uint256 word, uint256 offset, uint256 width) internal pure returns (uint256 r) {
        assembly {
            r := and(shr(offset, word), sub(shl(width, 1), 1))
        }
    }

    /// Same field, read as a signed integer of `width` bits (width a multiple of 8).
    function getSigned(uint256 word, uint256 offset, uint256 width) internal pure returns (int256 r) {
        assembly {
            r := signextend(sub(shr(3, width), 1), shr(offset, word))
        }
    }

    function set(uint256 word, uint256 offset, uint256 width, uint256 value) internal pure returns (uint256 r) {
        assembly {
            let mask := sub(shl(width, 1), 1)
            r := or(and(word, not(shl(offset, mask))), shl(offset, and(value, mask)))
        }
    }
}

contract C {
    function demo(uint256 word) external pure returns (uint256 a, int256 s, uint256 w2) {
        a = Fields.get(word, 160, 32);         // bits 160..191
        s = Fields.getSigned(word, 160, 32);   // same bits as int32
        w2 = Fields.set(word, 160, 32, 0x1234); // replace them
    }
}
```

With `word = 0xaaaaaaaaaaaaaaaadeadbeef0000…0001`:

```text
a  = 0xdeadbeef
s  = -559038737          (0xdeadbeef as int32; its top bit is 1)
w2 = 0xaaaaaaaaaaaaaaaa00001234000000000000000000000000000000000000000001
```

`getSigned` shows why `signextend` takes a byte index: `width / 8 − 1` is `shr(3, width)` minus one. `getSigned` does not need to mask first, because `signextend` overwrites everything above the field. `set` masks the new value, so an oversized `value` cannot spill into neighbouring fields. Production versions of these live in [[3.6 Storage, transient storage and bit packing]].

### Signed helpers

The signed opcodes come in handy for small helpers that Solidity would otherwise check expensively:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

library Signed {
    function max(int256 a, int256 b) internal pure returns (int256 r) {
        assembly { r := xor(a, mul(xor(a, b), sgt(b, a))) } // branchless select
    }

    /// Absolute value as uint256. Correct for type(int256).min too: 2**255.
    function abs(int256 x) internal pure returns (uint256 r) {
        assembly {
            let m := sar(255, x)          // 0 if x >= 0, all ones if x < 0
            r := sub(xor(x, m), m)        // (x ^ m) - m
        }
    }

    function isNegative(int256 x) internal pure returns (bool r) {
        assembly { r := slt(x, 0) }       // or: shr(255, x)
    }
}

contract S {
    function t(int256 a, int256 b) external pure returns (int256, uint256, bool) {
        return (Signed.max(a, b), Signed.abs(a), Signed.isNegative(a));
    }
}
```

`sar(255, x)` is the sign mask: it smears the sign bit over the whole word. `xor(x, m) − m` is two's complement negation when `m` is all ones and the identity when it is zero. `xor(a, mul(xor(a, b), cond))` selects `b` when `cond` is 1 and `a` when it is 0, with no jump. I tested `t` on both pipelines against Python on 2,140 input pairs (including 0, ±1, ±7, `type(int256).max` and `type(int256).min`): no mismatches. `abs(type(int256).min)` returned `0x8000…0000` = 2^255, which fits in `uint256`; the same expression in checked Solidity (`uint256(-x)`) would panic.

### Measuring an opcode with `gas()`

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

contract C {
    function expCost(uint256 b, uint256 e) external view returns (uint256 used, uint256 r) {
        assembly {
            let g := gas()
            r := exp(b, e)
            used := sub(g, gas())
        }
    }
}
```

This returned 23 / 73 / 123 / 1,623 for exponents of 0 / 1 / 2 / 32 bytes, on both optimizer settings. The bytecode between the two `GAS` instructions is `DUP4 DUP6 EXP SWAP2 POP`, so the overhead is a constant 13 gas. A bracket is a quick way to compare two snippets inside one contract; [[6.6 Debugging and tracing]] shows the proper tool (a trace).

## Pitfalls and incidents

**Swapped shift arguments.** `shl(x, 8)` is "8 shifted left by `x`". The compiler cannot catch it. Write the shift amount as a literal where you can (`shl(8, x)`), because a literal in the second position is an obvious smell.

**Unsigned comparison of signed values.** `lt(x, 0)` is always 0. `gt(x, 0)` is true for every negative `x`. For anything that is an `intN`, use `slt`/`sgt`, and sign-extend narrow values first: `slt(0xff, 1)` is 0 (255 is not below 1), while `slt(signextend(0, 0xff), 1)` is 1. I ran both.

**Silent division by zero.** `div`, `mod`, `sdiv`, `smod`, `addmod`, `mulmod` with a zero divisor return 0 instead of failing. In pricing code, that turns a missing oracle value into a zero price rather than a revert. Check the divisor.

**`sdiv(−2^255, −1)`.** Returns −2^255. Any signed division by a user-controlled divisor must consider it.

**`sar` is floor, `sdiv` is truncation.** `sar(1, −7) = −4`, `sdiv(−7, 2) = −3`. Rounding direction bugs are the root of many DeFi exploits ([[5.4 Arithmetic, rounding and precision]]); replacing one with the other "for gas" changes the rounding.

**`byte` counts from the left.** `byte(0, x)` is the **most** significant byte. If you want the lowest byte, write `and(x, 0xff)` or `byte(31, x)`.

**`signextend` takes a byte index.** `signextend(8, x)` is `int72`, not `int8`.

**`exp` with user-controlled exponents.** Cost grows to 1,610 gas, and the result wraps silently. Bound the exponent or use `shl` for powers of two.

**`returndatacopy` past the end burns all gas.** Unlike `calldatacopy` and `codecopy`, which zero-fill, `returndatacopy` beyond `returndatasize()` is an exceptional halt. Check the size first ([[3.7 External calls in assembly]]).

**`clz` on chains without Osaka.** `0x1e` is an undefined opcode there; the call consumes all gas. The compiler will not stop you if you set `evmVersion` to `osaka` for a chain that has not upgraded.

**Reserved names.** `clz` (on `osaka`) and `slotnum` (on `amsterdam`) are now builtins and cannot be identifiers. `dupn`, `swapn`, `exchange` warn. Code that compiled for years can stop compiling after a target bump.

### Compiler bugs involving these opcodes

The optimizer reasons about opcode semantics, so it has had bugs exactly at the edges this note covers. From the Solidity bug list (newest first):

| Bug | Versions | Severity | What went wrong |
|---|---|---|---|
| StorageWriteRemovalBeforeConditionalTermination (SOL-2022-7) | 0.8.13 – 0.8.16 (fixed 0.8.17) | medium/high | Storage writes before a conditional `return()`/`stop()` in inline assembly could be removed by the optimizer |
| KeccakCaching (SOL-2021-1) | fixed 0.8.3 | medium | The bytecode optimizer reused a `keccak256` result for a hash of the same memory with a different **length** |
| IncorrectByteInstructionOptimization (SOL-2019-2) | 0.5.5 – 0.5.6 (fixed 0.5.7) | very low | Wrong optimization of `byte` when its second argument was 31 or a constant evaluating to 31 |
| DoubleShiftSizeOverflow (SOL-2019-1) | 0.5.5 (fixed 0.5.6) | low | Nested constant shifts summing to 256 or more were combined into one shift, which wraps instead of giving 0 |
| ExpExponentCleanup (SOL-2018-4) | fixed 0.4.25 | medium/high | `**` with a narrow exponent type did not clean the exponent's high bits |

The pattern: shift amounts ≥ 256, lengths in `keccak256`, the last byte of `byte`, and dirty high bits. Those are the cases you should fuzz in your own assembly ([[6.2 Unit, fuzz and invariant testing]]).

## Question ladder

> [!question]- **B** What does `div(x, 0)` return in Yul, and what does `x / 0` do in Solidity?
> **`div(x, 0)` returns 0.** No revert, no flag, no gas penalty. The same holds for `sdiv`, `mod`, `smod`, and for `addmod`/`mulmod` with modulus 0. I ran all six in py-evm; all returned 0.
>
> **`x / 0` in Solidity reverts with `Panic(0x12)`**, the "division or modulo by zero" panic. This check is not removed by `unchecked { }`: the docs say it cannot be disabled. In 0.8.38, `unchecked { return x / y; }` with `y = 0` reverted with `0x4e487b71…0012` on both pipelines, while `assembly { r := div(x, y) }` in the same contract returned 0.
>
> So when you move a division into assembly, you drop the check. If a zero divisor is possible, put it back. To keep the same error as Solidity:
>
> ```solidity
> // SPDX-License-Identifier: MIT
> pragma solidity 0.8.38;
>
> contract C {
>     function divChecked(uint256 x, uint256 y) external pure returns (uint256 r) {
>         assembly {
>             if iszero(y) {
>                 mstore(0x00, shl(224, 0x4e487b71)) // Panic(uint256) selector
>                 mstore(0x04, 0x12)                 // division or modulo by zero
>                 revert(0x00, 0x24)
>             }
>             r := div(x, y)
>         }
>     }
> }
> ```
>
> `divChecked(7, 0)` returned exactly `4e487b71` followed by the word `0x12`, the same 36 bytes as Solidity's own panic; `divChecked(7, 2)` returned 3. A cheaper custom error is often better ([[3.8 ABI, errors and events by hand]]).
>
> The interview follow-up is usually "and signed division?". Two edge cases: `sdiv(x, 0) = 0`, and `sdiv(−2^255, −1) = −2^255` (the true result does not fit). Solidity panics with `0x11` on the second; assembly does not.

> [!question]- **B** When must you use `slt`/`sgt` instead of `lt`/`gt`?
> Whenever the two words are meant as **two's complement** signed numbers. `lt` and `gt` compare as unsigned, so every negative number looks larger than every positive one: −1 is `0xff…ff` = 2^256 − 1. Measured:
>
> ```text
> lt(−1, 1)  = 0      slt(−1, 1) = 1
> gt(−1, 1)  = 1      sgt(−1, 1) = 0
> ```
>
> The cases in practice:
>
> 1. **Values of `int` types**: `int256`, `int24` ticks, signed prices, PnL. "Is it negative?" is `slt(x, 0)` (or `shr(255, x)`); `lt(x, 0)` is always 0.
> 2. **Differences that may have gone below zero.** The compiler's own calldata check is `slt(add(calldatasize(), not(3)), 32)`: `calldatasize() − 4` would wrap to a huge unsigned number for short calldata, and `slt` sees it as negative. If you subtract two unsigned values and compare the result, ask whether it can underflow, and use the signed compare if a "negative" result must count as small.
> 3. **Narrow signed types, after sign extension.** `slt` only works on full-width two's complement. An `int8` −1 held as `0xff` is 255 to `slt` as well: `slt(0xff, 1)` returned 0. Sign-extend first: `slt(signextend(0, 0xff), 1)` returned 1. Values that come from Solidity variables are already extended; values you unpack from a packed slot are not.
>
> Equality does not care: `eq` compares bits, and two's complement has one representation per number (as long as both are clean). `iszero` doesn't care either.
>
> Mixed comparisons (signed against unsigned) have no single right answer. Decide what a negative value means, then convert explicitly.

> [!question]- **I** Extract bits 160–191 of a word using shifts and masks.
> Number bits from 0 (least significant). Bits 160–191 inclusive are 32 bits, sitting just above an address in the low 160 bits: the typical layout of `address owner; uint32 timestamp;` packed in one slot.
>
> **Shift down, then mask:**
>
> ```solidity
> // SPDX-License-Identifier: MIT
> pragma solidity 0.8.38;
>
> contract C {
>     function bitsA(uint256 x) external pure returns (uint256 r) {
>         assembly { r := and(shr(160, x), 0xffffffff) }
>     }
>     function bitsB(uint256 x) external pure returns (uint256 r) {
>         assembly { r := shr(224, shl(64, x)) }
>     }
> }
> ```
>
> `bitsA`: `shr(160, x)` moves bit 160 to bit 0; `and(…, 0xffffffff)` keeps the 32 bits we want and drops bits 192–255 that came down with them.
>
> `bitsB`: `shl(64, x)` pushes bits 192–255 off the top (256 − 192 = 64), so bit 191 becomes bit 255; then `shr(224, …)` brings the top 32 bits down (256 − 32 = 224). No mask constant needed.
>
> With `x = 0xaaaaaaaaaaaaaaaadeadbeef` followed by 20 zero bytes, both returned `0xdeadbeef` on both pipelines. Both cost 12 gas of opcodes (two `PUSH`es and two 3-gas operations each). `bitsA` is easier to read and generalises to "offset, width"; `bitsB` is handy when the width is not a nice mask.
>
> **The general form** is in [[#A bit-field toolkit]]: `and(shr(offset, word), sub(shl(width, 1), 1))`. For a signed field, replace the mask with `signextend(width / 8 − 1, shr(offset, word))`; for this field that gave −559,038,737, which is `0xdeadbeef` as an `int32`.
>
> **The classic bug** is the argument order. `and(shr(x, 160), 0xffffffff)` compiles and shifts the constant 160 right by `x`. It returned 0 for the test word and `0x14` for `x = 3`. A second classic is an off-by-one in the width: bits 160–191 is 32 bits, not 31.
>
> To **write** the field: `or(and(x, not(shl(160, 0xffffffff))), shl(160, and(v, 0xffffffff)))`. Clear the hole, mask the new value, OR it in. Forgetting to mask `v` lets a large value overwrite the neighbouring field.

> [!question]- **I** What are `addmod` and `mulmod` for, and why do they not overflow?
> **What they compute.** `addmod(a, b, n) = (a + b) mod n` and `mulmod(a, b, n) = (a · b) mod n`, where the sum and the product are taken over the **mathematical integers**, not modulo 2^256. The EVM computes the sum with 257 bits and the product with 512 bits, then reduces. The result is below `n`, which fits in a word, so nothing can overflow. That is the whole reason they exist: with `mod(mul(a, b), n)` the product wraps before the reduction.
>
> ```text
> mulmod(2^255, 4, 7)            = 4    correct (2^257 mod 7)
> mod(mul(2^255, 4), 7)          = 0    wrong: mul wrapped to 0
> addmod(2^256−1, 2^256−1, 7)    = 2    correct
> mod(add(2^256−1, 2^256−1), 7)  = 0    wrong
> mulmod(x, y, 0) = addmod(x, y, 0) = 0
> ```
>
> Both cost 8 gas, regardless of input.
>
> **What they are for:**
>
> - **Field arithmetic** with a modulus near 2^256: BN254 and secp256k1 field and scalar operations, Poseidon/MiMC hashes, ZK verifiers. Without `mulmod`, each field multiplication would need a hand-written 512-bit product.
> - **Full-precision `mulDiv`.** `mulmod(x, y, not(0))` is the product modulo 2^256 − 1. Together with `mul(x, y)` (modulo 2^256) it gives the high word of the 512-bit product by the Chinese remainder theorem. Then `mulmod(x, y, d)` gives the remainder to subtract before dividing. [[2.9 Arithmetic and numeric pitfalls]] builds this step by step.
> - **Rounding up**: `add(div(mul(x, y), d), gt(mulmod(x, y, d), 0))` adds 1 when there is a remainder (when `x · y` fits in a word).
> - **Checking for overflow of a product**: the product fits iff the high word is zero.
>
> **Pitfalls.** A zero modulus returns 0, not an error, so check `n` if it is user-supplied. And they are unsigned only: there is no signed `mulmod`.

> [!question]- **A** Explain `signextend` and `byte` precisely, with examples.
> **`signextend(b, x)`.** Let `t = 8b + 7`. If `b < 31`: if bit `t` of `x` is 1, set every bit above `t` to 1; if it is 0, set every bit above `t` to 0. Bits `0…t` are unchanged. If `b ≥ 31`, return `x` unchanged (bit 255 is already the sign bit). In words: "read the low `b + 1` bytes of `x` as a signed integer and return it as an `int256`."
>
> | Call | Result | Why |
> |---|---|---|
> | `signextend(0, 0xff)` | `0xff…ff` (−1) | bit 7 is 1 |
> | `signextend(0, 0x7f)` | `0x7f` (127) | bit 7 is 0 |
> | `signextend(0, 0x1280)` | `0xff…ff80` (−128) | the `0x12` above byte 0 is overwritten |
> | `signextend(1, 0xab7fff)` | `0x7fff` (32,767) | bit 15 is 0: garbage cleared to zeros |
> | `signextend(30, 0x80 << 240)` | `0xff80…00` | bit 247 copied into bits 248–255 |
> | `signextend(31, 0xdead)`, `signextend(32, 0x80)`, `signextend(1000, 0x80)` | unchanged | `b ≥ 31` |
>
> All measured in py-evm. The same thing built from shifts, for `b ≤ 31`: `let s := sub(248, shl(3, b))  r := sar(s, shl(s, x))`. Shift the field to the top, then arithmetic-shift it back down. I compared it with `signextend` for 200 random words and every `b` from 0 to 31: identical. For `b = 32` the formula breaks (`sub` wraps, `shl` by a huge amount gives 0), and returned 0 where `signextend` returned `0x80`. That is why the opcode exists: one 5-gas instruction with no out-of-range hole.
>
> Where it is used: the compiler cleans every `intN` with it (`signextend(0, v)` for `int8` in the via-IR ABI decoder, then `eq` against the original to reject dirty input); you use it to read signed fields out of packed slots (Uniswap-style `int24` ticks: `signextend(2, …)`).
>
> **`byte(i, x)`.** Returns byte `i` of `x`, where byte 0 is the **most significant**: `byte(i, x) = (x >> (248 − 8i)) & 0xff` for `i < 32`, and 0 for `i ≥ 32`.
>
> ```text
> x = 0x0102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f20
> byte(0, x) = 0x01    byte(31, x) = 0x20    byte(32, x) = 0    byte(2^255, x) = 0
> ```
>
> This is memory order: `byte(k, mload(p))` is the byte at address `p + k`. It is the reverse of bit numbering, where bit 0 is the least significant. The shift formula above matched `byte` for every `i` from 0 to 299, but not for `i = 2^253 + 1`, where `shl(3, i)` wraps.
>
> Common uses: reading a single character of a string or the first byte of calldata (`byte(0, calldataload(0))` is the first selector byte); building lookup tables in a constant (`byte(i, 0x…table…)` picks entry `i` of a 32-entry table for 3 gas, a common trick in gas-optimised libraries).
>
> The two opcodes count from opposite ends. `signextend`'s `b` counts bytes from the **least** significant end ("how many bytes wide minus one"); `byte`'s `i` counts from the **most** significant end. Mixing them up is the single most common way to misuse either.

> [!question]- **E** Implement "most significant bit" with a binary search and with `clz`. Compare the gas.
> Define `msb(x)` as the index of the highest set bit, 0–255, which is `floor(log2(x))`. It is undefined for `x = 0`; each implementation below documents what it returns there.
>
> **Code.** Three versions: a branchless binary search, a branching binary search (the shape of Uniswap V3's `BitMath.mostSignificantBit`), and one `clz`.
>
> ```solidity
> // SPDX-License-Identifier: MIT
> pragma solidity 0.8.38;
>
> library Msb {
>     /// Index of the highest set bit (0..255). Branchless binary search.
>     /// Returns 0 for x == 0 (caller must treat 0 separately).
>     function search(uint256 x) internal pure returns (uint256 r) {
>         assembly {
>             r := shl(7, lt(0xffffffffffffffffffffffffffffffff, x))
>             r := or(r, shl(6, lt(0xffffffffffffffff, shr(r, x))))
>             r := or(r, shl(5, lt(0xffffffff, shr(r, x))))
>             r := or(r, shl(4, lt(0xffff, shr(r, x))))
>             r := or(r, shl(3, lt(0xff, shr(r, x))))
>             r := or(r, shl(2, lt(0xf, shr(r, x))))
>             r := or(r, shl(1, lt(0x3, shr(r, x))))
>             r := or(r, lt(0x1, shr(r, x)))
>         }
>     }
>
>     /// Same search with branches: shift x down as we go.
>     function branchy(uint256 x) internal pure returns (uint256 r) {
>         assembly {
>             if gt(x, 0xffffffffffffffffffffffffffffffff) { x := shr(128, x) r := 128 }
>             if gt(x, 0xffffffffffffffff) { x := shr(64, x) r := add(r, 64) }
>             if gt(x, 0xffffffff) { x := shr(32, x) r := add(r, 32) }
>             if gt(x, 0xffff) { x := shr(16, x) r := add(r, 16) }
>             if gt(x, 0xff) { x := shr(8, x) r := add(r, 8) }
>             if gt(x, 0xf) { x := shr(4, x) r := add(r, 4) }
>             if gt(x, 0x3) { x := shr(2, x) r := add(r, 2) }
>             if gt(x, 0x1) { r := add(r, 1) }
>         }
>     }
>
>     /// Osaka and later: one CLZ. Returns 2**256 - 1 for x == 0 (255 - 256 wraps).
>     function withClz(uint256 x) internal pure returns (uint256 r) {
>         assembly {
>             r := sub(255, clz(x))
>         }
>     }
> }
>
> contract C {
>     function msbSearch(uint256 x) external pure returns (uint256) { return Msb.search(x); }
>     function msbBranchy(uint256 x) external pure returns (uint256) { return Msb.branchy(x); }
>     function msbClz(uint256 x) external pure returns (uint256) { return Msb.withClz(x); }
>     function id(uint256 x) external pure returns (uint256) { return x; }
> }
> ```
>
> **How the search works.** Each line asks one yes/no question: "is the top set bit at or above `r + 2^k`?". `lt(0xff…ff (2^k bits), shr(r, x))` is 1 if, after discarding the `r` bits already accounted for, more than `2^k` bits remain. `shl(k, …)` turns the answer into 2^k or 0, and `or` adds it to `r` (the bits never collide, so `or` is `add`). Eight questions for 2^8 = 256 positions. The branchy version asks the same eight questions with `if`, and shifts `x` instead of re-shifting it.
>
> **The `clz` version** compiles only with `evmVersion: "osaka"`. Its core, as a standalone Yul object `mstore(0, sub(255, clz(calldataload(0)))) return(0, 32)` with solc 0.8.38:
>
> ```text
> 5f351e60ff035f5260205ff3
> PUSH0 CALLDATALOAD CLZ PUSH1 0xff SUB PUSH0 MSTORE PUSH1 0x20 PUSH0 RETURN
> ```
>
> The algorithm is `CLZ PUSH1 0xff SUB`: 5 + 3 + 3 = **11 gas**, from the opcode costs.
>
> **Testing.** py-evm cannot run `CLZ`. I tested the two searches unmodified on 509 inputs (edge values and random bit lengths) against Python's `x.bit_length() − 1`: all correct on both pipelines. To run the `clz` version, I added `0x1e` to a copy of py-evm's Prague opcode table, implemented from the EIP text (pop `x`, push `256 − bitlength(x)`, 5 gas). With that, all three versions agreed on every non-zero input, and the measured cost of the `clz` core matched the 11 gas computed from opcode costs. (That patch is my reading of the EIP, not a reference client.)
>
> **Gas, the algorithm alone.** Each version as a minimal Yul object (optimizer on), minus a baseline object that just returns `x` (18 gas):
>
> | Version | Runtime size | Gas over baseline | Data-dependent? |
> |---|---|---|---|
> | Branchless search | 96 bytes | **201** | No |
> | Branching search | 172 bytes | **211–435** | Yes: each taken branch costs extra |
> | `clz` | 12 bytes | **11** | No |
>
> **Gas, end to end** (external call to the Solidity contract above, 0.8.38, optimizer 200 runs, target `osaka`, execution gas):
>
> | Function | Legacy | Via-IR |
> |---|---|---|
> | `id` (no work) | 277 | 198 |
> | `msbSearch` | 468 | 338 |
> | `msbBranchy` | 533–664 | 377–601 |
> | `msbClz` | 346 | 228 |
>
> The end-to-end differences include dispatcher noise (each selector is found at a different point of the dispatch), so trust the first table for the algorithm. The headline: **`clz` is about 18 times cheaper than the best search (11 versus 201 gas), and its whole test object is 8 times smaller (12 versus 96 bytes)**, and the branchless search beats the branching one on every input.
>
> **What an interviewer listens for:**
>
> - **Zero.** The search returns 0 for both `x = 0` and `x = 1`. `sub(255, clz(0))` wraps to 2^256 − 1. `BitMath` uses `require(x > 0)`. A library has to choose: revert, return a sentinel (256 or `type(uint256).max`), or document "undefined". The worst choice is silent ambiguity, because `log2`, `sqrt` initial guesses and tick math all feed `msb` into further arithmetic.
> - **Related functions fall out of `clz`.** Bit length is `sub(256, clz(x))` (0 for 0). Count trailing zeros is `sub(255, clz(and(x, sub(0, x))))`: `x & −x` isolates the lowest set bit. I tested both with the patched VM on 200 random inputs.
> - **Constant gas matters.** The branchless search and `clz` cost the same for every input. The branching version varies by 224 gas, which makes gas estimates input-dependent and is slower on average for large numbers.
> - **Portability.** `clz` needs Osaka. Mainnet has it (since 3 Dec 2025). On a chain that has not adopted it, `0x1e` is undefined and every call to `msbClz` fails, consuming all gas, while the contract deploys fine. A library that must run everywhere ships the search, or picks at compile time with the EVM version; it cannot detect the opcode at run time cheaply.
> - **Measurement method.** Measure the algorithm in isolation (a minimal object or a `gas()` bracket calibrated with an empty bracket), not by comparing whole external calls, because dispatch order and ABI work are larger than the thing you measure.
> - **The win is real but small in absolute terms.** 190 gas per call matters inside loops (bitmap scans, tick searches, `log2` in pricing curves). It is noise next to one cold `SLOAD` (2,100). Say both.
